# Серия видеообзоров по разделам Kingside

Документ описывает план продуктовой серии коротких видеообзоров (по 2–4
минуты) на каждый активный раздел сайта. Образцы готовых обзоров —
KS-3062 (генерация пазлов) и KS-4055/4056 (окно анализа). По итогам
этого документа координатор нарезает QA-тикеты по одному на раздел,
каждый ссылается на нужный пункт этого файла; QA копирует шаблон
скриптов из готового обзора и адаптирует под сцены своего раздела.

Архитектор код не пишет — описанные ниже фрагменты `record.mjs`/
`narration.txt`/`segments.json` это описание контракта, а не исходники.

---

## 1. Общие принципы серии

### 1.1. Тон озвучки
- Повествовательный, спокойный, объясняет смысл функции, а не
  пересказывает «нажмите кнопку».
- Без сленга («задеплоить», «прокинуть», «зафейлилось»), без
  Given/When/Then, без бодрых маркетинговых оборотов.
- Слово «Kingside» произносится один раз во вступлении и одно — в
  заключении; внутри обзора — «платформа», «сервис» или прямой
  термин («окно анализа», «лекция»).
- Каждая фраза — 1–3 предложения, длительность одного клипа piper —
  7–15 секунд (см. KS-4055 `segments.json` как референс).

### 1.2. Длительность
| Тип обзора                          | Длительность | Сегментов |
|-------------------------------------|--------------|-----------|
| Лёгкий (одна страница, один поток)  | ~2 мин       | 8–10      |
| Средний (вся функция)               | ~3 мин       | 12–16     |
| Расширенный (комплексный раздел)    | ~4 мин       | 16–20     |

### 1.3. Технический стек (общий для всех обзоров)
- **Playwright** — `/project/node_modules/playwright-core` (НЕ
  `npx playwright`). Браузер — Chromium из
  `~/.cache/ms-playwright/chromium-1223/chrome-linux64/chrome`.
- **Озвучка** — `piper`
  (`/usr/local/bin/piper --model /opt/piper-voices/ru_RU-irina-medium.onnx`).
- **Склейка** — `ffmpeg` БЕЗ `-shortest`. Тайминги вставки клипов
  берутся из `narration-timeline.json`, записанного `record.mjs` по
  реально замеренным длительностям WAV.
- **Auth для записи** — `POST /auth/dev-bypass` с секретом
  `kingside-dev-bypass-2026` (создаёт одноразового пользователя; на
  prod-сервер не идёт).

### 1.4. Viewport
| Назначение                       | Размер   |
|----------------------------------|----------|
| Десктоп (по умолчанию)           | 1920×1200 |
| Мобильный обзор (если нужен)     | 390×844 (iPhone 13) |
| Wide-страница с двумя досками    | 1440×1200 |

Высота 1200 (а не классические 720/900) выбрана в KS-4056, чтобы в
правой колонке окна анализа все 7 блоков метрик и переключатель
режима помещались в кадр без скролла. Для большинства обзоров эта
высота подходит и для других страниц.

### 1.5. HUD (накладные подсказки)
Тот же CSS-инжект, что в `/tmp/KS-4055/record.mjs` (блок `HUD_CSS`):
- Верхняя полоса с тегом раздела (оранжевый, 12pt, ВЕРХНИЙ РЕГИСТР) и
  фразой текущего шага (белый, 16pt).
- Splash-экраны на intro/outro: тёмно-синий градиент, заголовок 28pt,
  подзаголовок 18pt. Длительность splash — 2500 мс.
- HUD-полоса остаётся видна на всех сценах, кроме splash; меняется
  через `setHud(page, {feature, scenario})` в начале каждой сцены.

### 1.6. Сборка аудиодорожки (конвейер v2, см. ADR-123)

Принцип: **аудио первично, видео подгоняется**. Действия Playwright
привязаны к словам-якорям из текстов сегментов, а не к секундам от
старта записи. Это даёт автоматическую ре-синхронизацию при замене
озвучки без правки `record.mjs`.

Шаги:
- Каждый сегмент сценария — отдельный файл `segment-NN.txt` в
  `/tmp/voiceover/KS-XXXX/`.
- Декларация действий — `/tmp/KS-XXXX/scene-actions.json`. Поля:
  `anchor` (подстрока из текста сегмента), `type` (`hover` / `click` /
  `type` / `drag` / `flash`), `selector` (Playwright-локатор),
  `leadMs` (сдвиг от слова-якоря), `side` (A или B для двух контекстов).
- `synth-eleven.py` (в `tools/video-overview/`) синтезирует mp3 для
  каждого сегмента через ElevenLabs API endpoint
  `/v1/text-to-speech/{voice_id}/with-timestamps` и сохраняет
  посимвольные тайминги в `NN.timestamps.json`. ELEVENLABS_API_KEY
  живёт в env-переменной webhook-контейнера.
- `measure-segments.py` пробегает mp3 через `ffprobe` и собирает
  `segments.json` с `durMs` для каждой сцены.
- `record.mjs` (универсальный, в `tools/video-overview/`) читает
  `scene-actions.json` + `*.timestamps.json` и для каждой сцены:
  планирует действия на `sceneStartMs + anchorMs + leadMs`,
  выполняет их в порядке возрастания времени, затем удерживает
  кадр до `durMs + 400 мс` (BUFFER). Записывает реальный `startMs`
  в `placements`.
- `build-track.py` собирает `voice.wav`, расставляя mp3 по
  `placements` и заполняя промежутки тишиной.
- `ffmpeg` склеивает `videos/*.webm` (raw без звука) с `voice.wav`
  без `-shortest`. Полная длительность видео = max(audio_end, video).

Единственная точка фиксации тайминга — синтез ElevenLabs (шаг 4
конвейера). Все последующие шаги — функции от его выхода. Замена
одного сегмента: правка `segment-NN.txt` → `make video KEY=KS-XXXX`
→ конвейер пересинтезирует только изменённый сегмент (по хешу),
пересчитывает `segments.json`, пере-записывает видео под новые
длительности, делает финальный микс. Ручных шагов в типовом цикле —
ноль.

Полное описание контракта — ADR-123.

### 1.7. Артефакты каждого обзора
В каталоге `/tmp/KS-XXXX/` (KS-XXXX — ID тикета QA):
```
scenario-vN.md              — сценарий (архитектор)
scene-actions.json          — декларация действий с словами-якорями (архитектор + QA)
segments.json               — длительности сегментов (генерируется, см. ADR-123)
placements.json             — реальные startMs сцен (генерируется при записи)
videos/*.webm               — сырое видео без звука
voice.wav                   — итоговая голосовая дорожка (генерируется)
<slug>-overview.webm        — финальное видео со звуком (целевой артефакт)
report.html                 — кратко: что показано, тайминги, версии
```

В `/tmp/voiceover/KS-XXXX/`:
```
segment-NN.txt              — тексты сегментов (архитектор)
NN.mp3                      — синтез ElevenLabs (генерируется)
NN.timestamps.json          — посимвольные тайминги (генерируется ElevenLabs)
```

### 1.8. Долговременное хранение
До настройки общего хранилища — `/tmp/KS-XXXX/` на сервере вебхуков
(как сейчас). Когда координатор согласует постоянное место, целевой
артефакт `<slug>-overview.webm` будет копироваться в общий каталог
(вариант — `s3://kingside-presentations/` или
`/project/docs/architecture/video-overview-series/videos/`). Это
решение принимается отдельно — сейчас НЕ блокирует серию.

### 1.9. Шаблонные скрипты (конвейер v2)
По ADR-123 общие скрипты живут в `tools/video-overview/`:
- `synth-eleven.py` — синтез через ElevenLabs API + сохранение
  посимвольных таймингов;
- `measure-segments.py` — `ffprobe` по mp3 → `segments.json`;
- `record.mjs` — универсальный интерпретатор `scene-actions.json`,
  применим ко всей серии без правок под конкретный тикет;
- `build-track.py` — сборка `voice.wav` по `placements`.

Под конкретный тикет копируются только: `scenario-vN.md`,
`scene-actions.json` и тексты сегментов. Сами инструменты — общие.

## 2. Каталог разделов

Источник правды по списку маршрутов — `apps/web/src/App.tsx`.
Маршруты, скрытые feature-флагами или admin-only, и dev-only
песочницы (`/__dev/*`, `/dev/*`) в серию НЕ входят.

Каждая карточка ниже — заготовка для отдельного тикета QA. В тикете
QA указывает свой `KS-XXXX`, копирует пункты «Сценарий» и
«Демо-данные» сюда же, остальное (стек, HUD, viewport) берёт из
раздела 1.

### Группа A — основа продукта

#### A1. Главная страница / онбординг гостя
**URL:** `/` (для гостя — `FeaturesPage`; для авторизованного —
редирект на `/play`).
**Цель:** за 2 минуты гость должен понять, что Kingside умеет (игра,
тренировки, анализ, лекции) и как зарегистрироваться.
**Длительность:** ~2 мин, 10 сегментов.
**Сценарий:**
1. *intro* — splash «Kingside — онлайн-платформа для шахмат».
2. *features-hero* — главная для гостя, hero-блок и кнопка «Начать».
3. *features-list* — короткая прокрутка по плиткам разделов.
4. *register-open* — переход на `/register`, форма регистрации.
5. *register-skip* — упоминание входа через Google (`/oauth/...`).
6. *first-login* — после dev-bypass попадаем на `/play`, видим лобби.
7. *nav-tour* — заголовок Nav: «Играть · Тренировка · Анализ ·
   Лекции · Профиль».
8. *outro* — splash «Регистрация бесплатна, играть можно сразу».

**Демо-данные:** ничего, кроме dev-bypass пользователя. Возможен
показ свежесозданного аккаунта без партий — пусть `/play` выглядит
«пустым», это и есть стартовая ситуация.
**Внешние зависимости:** `lessonsEnabled`, `puzzlesEnabled`,
`broadcastsEnabled`, `tournamentsEnabled` — все включены на dev,
иначе в hero-блоке часть тайлов недоступна.

#### A2. Игра против соперника (матчмейкинг + live-партия)
**URL:** `/play` → `/lobby` (если используется) → `/game/:id`.
**Цель:** показать путь «нажал играть → нашёл соперника → играю на
часах».
**Длительность:** ~3 мин, 14 сегментов.
**Сценарий:**
1. *intro* — splash «Игра против соперника».
2. *play-page* — `/play`, плитки лимитов (bullet/blitz/rapid).
3. *time-picker* — клик по лимиту, выбор «3+0», старт поиска.
4. *queue* — экран ожидания, индикатор поиска.
5. *game-start* — переход на `/game/:id`, расстановка, часы пошли.
6. *first-moves* — несколько ходов мышью, видны нотация и часы.
7. *premove* — демонстрация премува (тёмная стрелка ожидания).
8. *resign-menu* — выпадающее меню «Сдаться / Предложить ничью».
9. *game-end* — финальный экран с результатом.
10. *outro* — splash «Партия сохранена и доступна в Архиве».

**Демо-данные:** нужно два dev-bypass пользователя в двух
параллельных контекстах Playwright — один ищет, второй принимает.
Альтернатива — фикстурный бот в `apps/api` (если уже есть,
проверить `apps/api/src/matchmaking/`).
**Внешние зависимости:** WebSocket-gateway `/game` и matchmaking
запущены, Redis жив.

#### A3. Live-партии (просмотр чужих)
**URL:** `/games/live`, `/games/:id/watch`.
**Цель:** объяснить, как зритель смотрит чужие партии, переключает
доски, читает чат.
**Длительность:** ~2 мин, 9 сегментов.
**Сценарий:**
1. *intro* — splash «Просмотр живых партий».
2. *live-list* — `/games/live`, плитки активных партий с превью.
3. *open-game* — клик по плитке, переход на `/games/:id/watch`.
4. *board-view* — доска, ходы появляются в реальном времени, часы.
5. *spectator-chat* — окно чата зрителей (если есть).
6. *engine-overlay* — короткое включение Stockfish-оценки зрителем.
7. *outro* — splash «Смотри партии других — это бесплатно».

**Демо-данные:** нужны 1–2 «живые» партии в фоне. Снимать после
A2 — там как раз создаётся партия, которую видно в `/games/live`.
**Внешние зависимости:** WebSocket подключение `/game` на чтение.

#### A4. Архив партий
**URL:** `/archive`, `/archive/games/:id`, `/archive/players/:slug`.
**Цель:** показать, как пользователь находит свою старую партию по
фильтру и открывает её для разбора.
**Длительность:** ~2.5 мин, 11 сегментов.
**Сценарий:**
1. *intro* — splash «Архив партий».
2. *archive-open* — `/archive`, видны фильтры и список.
3. *filter-time* — фильтр по контролю времени.
4. *filter-result* — фильтр по результату (победа / поражение).
5. *filter-position* — поиск по позиции (FEN).
6. *open-game* — клик по партии, переход на `/archive/games/:id`.
7. *analyze-button* — кнопка «Разобрать» уводит в окно анализа.
8. *player-profile* — переход на `/archive/players/:slug`.
9. *outro* — splash «Архив хранит все партии».

**Демо-данные:** dev-bypass пользователь с 10–20 архивными
партиями. Фикстура — `apps/api/prisma/seed*.ts` (проверить наличие
функции «создать N архивных партий» — если нет, координатор заведёт
отдельный тикет backend).
**Внешние зависимости:** by-position search (вектор-сервис) — нужно
проверить, что включён.

#### A5. Мастерская (импорт партии)
**URL:** `/workshop`, `/workshop/pgn-files`, `/workshop/pgn-files/:id`.
**Цель:** показать, как пользователь импортирует PGN, видит список
своих PGN-файлов, открывает партию в анализе.
**Длительность:** ~2.5 мин, 11 сегментов.
**Сценарий:**
1. *intro* — splash «Мастерская — личная библиотека партий».
2. *workshop-open* — `/workshop`, видны разделы.
3. *paste-pgn* — поле «Вставить PGN», вставка партии (Карлсен —
   Нэпо или любая известная).
4. *parse-preview* — после Parse: доска, ходы, метаданные партии.
5. *save-file* — кнопка «Сохранить», переход в `/workshop/pgn-files`.
6. *file-list* — список файлов с превью.
7. *open-game* — открытие партии из файла.
8. *analyze-jump* — кнопка «Открыть в анализе» уводит на `/analysis`.
9. *outro* — splash «Импортированные партии остаются у тебя».

**Демо-данные:** готовый PGN на 20–30 ходов с понятными именами,
лежит в `narration.txt` как константа. Никаких сервер-фикстур не
нужно — всё происходит у залогиненного пользователя.
**Внешние зависимости:** PGN-парсер и `/workshop/pgn-files` API
живы.

#### A6. Окно анализа партии
**Готово в KS-4055/4056.** Финальное видео:

тикет «KS-XXXX — окно анализа v2», и в нём добавляются ТОЛЬКО

#### A7. Game Review — исключено из серии
В продукте нет отдельной страницы Game Review. Маршрут
`/game/:gameId/review` рендерит ту же `AnalysisPage`, а сам разбор
запускается пунктом «Разобрать партию» в меню анализа
(`AnalysisActionsMenu`, ADR-100 §9). Это уже показано в A6 (окно
анализа, KS-4055). Отдельного обзора не делаем.

Решение зафиксировано в KS-4494 (сверка плана с продуктом) и
KS-4511 (вычеркивание раздела). Если позже появится самостоятельный
flow «после партии — отдельная страница разбора с экраном
точности» — добавится как A7 v2 отдельным тикетом.

### Группа B — тренировки и задачи

#### B1. Лобби тренировок и анализа
**URL:** `/train`, `/analyze`.
**Цель:** объяснить группировку: что лежит на каждой странице и
зачем их разделили.
**Длительность:** ~2 мин, 9 сегментов (один обзор на обе страницы,
не два отдельных).
**Сценарий:**
1. *intro* — splash «Где искать тренажёры и где — инструменты
   разбора».
2. *train-page* — `/train`, плитки: классические задачи, точность,
   puzzle rush, drills, opening trainer, blind board.
3. *train-pick* — клик по «Точность» → переход на `/precision`
   (без углубления в саму страницу — это B3).
4. *back-to-train* — возврат на `/train`.
5. *analyze-page* — `/analyze`, плитки: окно анализа, мастерская,
   архив, разбор партии.
6. *analyze-pick* — клик по «Мастерская».
7. *outro* — splash «Тренировка — слева, разбор — справа».

**Демо-данные:** пустой dev-bypass пользователь.
**Внешние зависимости:** `drillsEnabled`, `puzzlesEnabled`,
`lessonsEnabled` — все включены, иначе плитки исчезают.

#### B2. Классические задачи (Puzzles)
**URL:** `/puzzles`, `/puzzle/:id`, `/puzzles/stats`,
`/puzzles/mistakes`, `/puzzles/mistakes-practice`.
**Цель:** показать решение задач, рейтинг, ошибочный лог

**Длительность:** ~3 мин, 14 сегментов.
**Сценарий:**

3. *open-puzzle* — открытие задачи, ход за нужную сторону.
4. *solve-correct* — правильный ход, оценка «+15 рейтинга».
5. *solve-wrong* — намеренно неправильный ход в другой задаче,

6. *mistakes-page* — переход на `/puzzles/mistakes`, видим список.
7. *mistakes-practice* — клик «Повторить», переход на
   `/puzzles/mistakes-practice`.
8. *stats-page* — `/puzzles/stats`, рейтинг и распределение по
   темам.
9. *outro* — splash «Решай, ошибайся, возвращайся к ошибкам».

**Демо-данные:** dev-bypass пользователь с подгруженными задачами
(база lichess). Дневник ошибок начнётся пустым — наполняется
прямо в сценарии (шаг 5).
**Внешние зависимости:** puzzle-сервис и puzzle-rating API живы.

#### B3. Тренировка точности (Precision)
**URL:** `/precision`, `/precision/stats`, `/precision/history`,
`/precision/attempts/:id`.

#### B4. Puzzle Rush
**URL:** `/puzzle-rush`, `/puzzle-rush/leaderboard`,
`/puzzle-rush/review/:scoreId`.
**Цель:** показать формат «реши максимум задач за фиксированное
время; ошибки расходуют жизни», лидерборд по контролю времени,
разбор после.

**Фактическая механика (актуализировано KS-4512 по сверке KS-4315):**

* Два режима по контролю времени: **3 минуты** (`timeMode: '3'`, 180 c)
  и **5 минут** (`timeMode: '5'`, 300 c). Режима survival в продукте
  нет (`PuzzleRushPage.tsx:14` — `type TimeLimitOption = 180 | 300`).
* **3 жизни** на сессию (`PuzzleRushPage.tsx:16` —
  `const MAX_LIVES = 3`). Сессия заканчивается по истечении таймера
  ИЛИ по третьей ошибке — что наступит раньше.
* Лидерборд (`/puzzle-rush/leaderboard`) — табы **по контролю
  времени**: «3 мин» / «5 мин»
  (`PuzzleRushLeaderboardPage.tsx` — `TimeMode`, `tc-btn` для '3' и
  '5'). Фильтра по периоду (день/неделя/всё время) нет.
* Отдельной стат-страницы режима нет; статистика сессии — секция на
  финальном экране (число задач, ошибок, времени) и доступ к
  `/puzzle-rush/review/:scoreId` для разбора всех ходов с пометками.

**Длительность:** ~2 мин, 9 сегментов.
**Сценарий:**
1. *intro* — splash «Puzzle Rush — реши максимум за отведённое
   время. Три ошибки — конец сессии».
2. *start-screen* — `/puzzle-rush`, кнопка «Start» и выбор режима
   (3 мин / 5 мин). Показать обе кнопки, выбрать 3 мин.
3. *lives-and-timer* — в кадре HUD сессии: таймер сверху, три
   значка-сердца справа (жизни), счётчик решённых.
4. *play* — несколько решённых задач подряд, видно растущий счёт.
5. *miss-and-lose-life* — намеренная ошибка: ход помечается «X»,
   один из значков-сердец гасится (осталось 2 жизни). Дикторская
   подсказка про правило трёх жизней.
6. *finish* — конец сессии (по времени или после третьей ошибки —
   снимаем по времени, чтобы показать выживание); финальный экран
   со счётом, числом ошибок и затраченным временем.
7. *review* — кнопка «Review», переход на
   `/puzzle-rush/review/:id`, просмотр всех ходов с пометками.
8. *leaderboard* — переход на `/puzzle-rush/leaderboard`,
   переключение табов «3 мин» ↔ «5 мин» — показать, что лидерборд
   ведётся отдельно по каждому контролю времени.
9. *outro* — splash «Реши больше, чем в прошлый раз».

**Демо-данные:** dev-bypass пользователь. Для лидерборда нужно
хотя бы 5–10 фейковых записей в каждом из двух режимов — фикстура
`seed-puzzle-rush-scores` (проверить наличие; если нет — content

**Внешние зависимости:** puzzle-rush сервис

  в шапке профиля. В C1 переход не делаем — это C5.

**Длительность:** ~2:30, 10 сегментов. Допуск контракта QA — ±20 с

**Сценарий:**

  broadcast viewer, ADR-110); CTA с лендинга при `status=live`
  ведёт сразу туда.
- Каталог `/lectures` — это не «Мои лекции», а смешанный список:
  гость видит публичный каталог; авторизованный — три секции
  «As a coach / As a student / Discover».
- В плеере записи нет глав/сегментов с переходами — только
  сплошной слайдер с управлением скоростью (×1 / ×1.5 / ×2).

**Длительность:** ~2.5 мин, 11–12 сегментов.
**Сценарий:**
1. *intro* — splash «Лекции тренеров».
2. *catalog* — `/lectures`, каталог лекций. Авторизованным —
   развилка по роли: «As a coach», «As a student», «Discover»;
   гостю — публичный каталог. В кадре показать секцию «Discover»
   и кликнуть по карточке лекции.
3. *open-landing* — `/lectures/:id`, лендинг с заголовком, статусом
   (badge), описанием и временем начала (`scheduledAt`). Цена и
   панель покупки в этом разделе пока не показываются.
4. *go-live* — клик по CTA на лендинге (для `status=live`) ведёт на
   публичный `/live/:slug`. Это общий live-viewer (ADR-110): видна
   доска ведущего, ходы обновляются в реальном времени.
5. *chat* — чат лекции (KS-4009) — встроен в live-viewer и в
   replay через общий компонент.
6. *back-to-replay* — после окончания эфира — `/lectures/:id/replay`,
   плеер записи.
7. *replay-timeline* — сплошной слайдер записи, кнопки play/pause и
   переключатель скорости ×1 / ×1.5 / ×2. Глав/меток нет.
8. *outro* — splash «Лекции — это уроки в живом эфире».

**Демо-данные:** опубликованная лекция со статусом
`scheduled`/`live`/`recorded`. Фикстура — `seed-lecture-demo`.
**Внешние зависимости:** Lecture-backend (ADR-119) живой,
видеосервис, чат-сервис, public broadcast viewer (ADR-110).
**Зависит от:** обзор D2 (Live Analysis Viewer) — `/live/:slug`
снят там самостоятельно; в D1 на этой странице задерживаемся
коротко и при озвучке можно сослаться «подробнее про этот экран
— в обзоре №…».

**Что снять, когда появится UI оплаты:** отдельным тикетом
«D1 v2 — покупка лекции» добавятся сцены `pricing-block` (цена на
лендинге) и `access-panel` («Купить / Уже есть»). Сейчас этих
элементов в продукте нет — в кадр ставить нечего.

#### E1. Уроки и курсы
**URL:** `/lessons`, `/lessons/discover`, `/lessons/my-active`,
`/lessons/:courseSlug`, `/lessons/:courseSlug/:lessonSlug`,
`/lessons/my/:slug/edit`.
**Цель:** показать путь ученика: нашёл курс → прошёл урок → вернулся

**Что НЕ снимаем:**
- `/lessons/editor` — внутренний редактор фикстур команды Kingside
  за email-whitelist `VITE_LESSON_EDITOR_EMAILS` (`LessonEditorPage.tsx:31-45`,
  экспорт `CourseFixture` в `.ts` для seed). К пути автора как
  user-функция не относится. Настоящий редактор автора —
  `/lessons/my/:slug/edit` (`UserCourseEditor`).
- `/lessons/my` (редирект на `/lessons?tab=mine`), `/lessons/my/:slug[/...]`
  (редиректы на унифицированные `/lessons/:slug[/...]`, KS-2645),
  `/lessons/mistakes[/mistakes-practice]` (301 → `/puzzles/...`,
  ADR-032) — все промежуточные/редирект-маршруты в кадр не попадают.

**Длительность:** ~3:20, 14 сегментов. Допуск контракта QA — ±20 с
от плана (см. §4 «Контракт тикета QA»). Финальная разбивка
зафиксирована в KS-4547 (утверждённый сценарий).
**Сценарий:**
1. *intro* — splash «Уроки и курсы».
2. *lessons-home* — `/lessons`, hero + curriculum pillar +
   community strip.
3. *discover* — переход на `/lessons/discover`, сетки последних
   public-курсов и авторов.
4. *open-course* — клик по карточке, `/lessons/:slug`, заголовок,
   прогресс-бар, список уроков.
5. *open-lesson-text* — `/lessons/:slug/:lessonSlug?step=1`,
   текстовый шаг с markdown и встроенной диаграммой; «Готово».
6. *interactive-step* — следующий шаг типа `puzzle` или `quiz`
   (см. ниже про требования к курсу).
7. *complete-lesson* — кнопка «Завершить урок», оверлей «Урок
   пройден!», возврат к списку.
8. *my-active* — таб «Мои курсы» на `/lessons` + страница
   `/lessons/my-active` с relative-time бейджем.
9. *create-cta* — клик «+ Создать свой курс» в `CreateCourseCta`,
   редирект на `/lessons/my/<slug>/edit`.
10. *editor-rename* — inline-редактирование заголовка курса,
    `SaveStatusPill`.
11. *add-lesson* — добавление первого урока в outline.
12. *add-step* — `AddStepPicker`, выбор «Лекция», ввод текста,
    автосейв.
13. *publish* — `PublishToggle` → public, переход на
    `/lessons/discover`, курс появился в `LatestCoursesBlock`.
14. *outro* — splash «Учись по чужим курсам — собирай свои».

**Демо-данные:** dev-bypass пользователь + **один публичный
user-курс**, который content готовит вручную **до съёмки** через
`/lessons` → «+ Создать свой курс» → редактор. В курсе один урок
с двумя шагами: `text` (с одной диаграммой) для сегмента 5 и
`puzzle` или `quiz` для сегмента 6. **Системных seed-курсов нет**
(`apps/api/src/lessons/seed/courses/index.ts:12` — `COURSES = []`,
KS-1958: раздел «Уроки» стартует пустой и ждёт настоящего
контента). Второй курс — «Тактика для начинающих» или аналогичный —
создаётся в кадре в сегментах 9–13. После съёмки content удаляет
оба demo-курса (`OwnerActionsMenu` → «Удалить» или
`DELETE /lessons/courses/:id`), чтобы они не висели в публичном
каталоге.
**Внешние зависимости:** `lessonsEnabled=true`, `puzzlesEnabled=true`
(для шага `puzzle` в сегменте 6), lessons API (REST), без WebSocket.

## 4. Контракт тикета QA

Каждый тикет в Jira/Yougile от координатора на QA содержит:

1. Ссылку на раздел этого документа (например
   «по разделу 2 / B3 Precision»).
2. Целевой `/tmp/KS-XXXX/` для артефактов.
3. Slug финального файла (например `precision-overview.webm`).
4. Параметры записи из раздела 1 (viewport, голос, HUD) — не
   повторять, ссылаться на раздел 1 этого документа.
5. Acceptance — стандартный:
   - все сегменты сценария показаны в порядке списка;
   - ни одна фраза не обрезается на переходе сцены;
   - HUD-подсказка синхронна с тем, что на экране;
   - длительность совпадает с целевой ±20 с;
   - `report.html` сгенерирован.

QA НЕ переписывает сценарий — берёт пункты как есть. Если на
этапе записи обнаруживает, что сцена не получается (например,
кнопки нет, API падает), оставляет комментарий в своём тикете
и тегает `@architect` для правки этого документа.

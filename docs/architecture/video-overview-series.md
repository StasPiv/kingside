# Серия видеообзоров по разделам Kingside

Документ описывает план продуктовой серии коротких видеообзоров (по 2–4
минуты) на каждый активный раздел сайта. Образцы готовых обзоров —
KS-3062 (генерация пазлов) и KS-4055/4056 (окно анализа). По итогам
этого документа координатор нарезает QA-тикеты по одному на раздел,
каждый ссылается на нужный пункт этого файла; QA копирует шаблон
скриптов из готового обзора и адаптирует под сцены своего раздела.

Архитектор код не пишет — описанные ниже фрагменты `record.mjs`/
`narration.txt`/`segments.json` это описание контракта, а не исходники.

---

## 1. Общие принципы серии

### 1.1. Тон озвучки
- Повествовательный, спокойный, объясняет смысл функции, а не
  пересказывает «нажмите кнопку».
- Без сленга («задеплоить», «прокинуть», «зафейлилось»), без
  Given/When/Then, без бодрых маркетинговых оборотов.
- Слово «Kingside» произносится один раз во вступлении и одно — в
  заключении; внутри обзора — «платформа», «сервис» или прямой
  термин («окно анализа», «лекция»).
- Каждая фраза — 1–3 предложения, длительность одного клипа piper —
  7–15 секунд (см. KS-4055 `segments.json` как референс).

### 1.2. Длительность
| Тип обзора                          | Длительность | Сегментов |
|-------------------------------------|--------------|-----------|
| Лёгкий (одна страница, один поток)  | ~2 мин       | 8–10      |
| Средний (вся функция)               | ~3 мин       | 12–16     |
| Расширенный (комплексный раздел)    | ~4 мин       | 16–20     |

### 1.3. Технический стек (общий для всех обзоров)
- **Playwright** — `/project/node_modules/playwright-core` (НЕ
  `npx playwright`). Браузер — Chromium из
  `~/.cache/ms-playwright/chromium-1223/chrome-linux64/chrome`.
- **Озвучка** — `piper`
  (`/usr/local/bin/piper --model /opt/piper-voices/ru_RU-irina-medium.onnx`).
- **Склейка** — `ffmpeg` БЕЗ `-shortest`. Тайминги вставки клипов
  берутся из `narration-timeline.json`, записанного `record.mjs` по
  реально замеренным длительностям WAV.
- **Auth для записи** — `POST /auth/dev-bypass` с секретом
  `kingside-dev-bypass-2026` (создаёт одноразового пользователя; на
  prod-сервер не идёт).

### 1.4. Viewport
| Назначение                       | Размер   |
|----------------------------------|----------|
| Десктоп (по умолчанию)           | 1280×1200 |
| Мобильный обзор (если нужен)     | 390×844 (iPhone 13) |
| Wide-страница с двумя досками    | 1440×1200 |

Высота 1200 (а не классические 720/900) выбрана в KS-4056, чтобы в
правой колонке окна анализа все 7 блоков метрик и переключатель
режима помещались в кадр без скролла. Для большинства обзоров эта
высота подходит и для других страниц.

### 1.5. HUD (накладные подсказки)
Тот же CSS-инжект, что в `/tmp/KS-4055/record.mjs` (блок `HUD_CSS`):
- Верхняя полоса с тегом раздела (оранжевый, 12pt, ВЕРХНИЙ РЕГИСТР) и
  фразой текущего шага (белый, 16pt).
- Splash-экраны на intro/outro: тёмно-синий градиент, заголовок 28pt,
  подзаголовок 18pt. Длительность splash — 2500 мс.
- HUD-полоса остаётся видна на всех сценах, кроме splash; меняется
  через `setHud(page, {feature, scenario})` в начале каждой сцены.

### 1.6. Сборка аудиодорожки
- В `narration.txt` каждая фраза — отдельный сегмент `[NN / tag]`,
  где `tag` совпадает с именем сцены в `record.mjs`.
- `synth-segments.py` синтезирует все клипы и пишет `segments.json`
  с замеренными `durMs`.
- `record.mjs` в каждой сцене ждёт минимум `durMs + 400 мс` (BUFFER)
  и записывает реальный `startMs` в `placements`.
- `build-track.py` собирает `voice.wav`, расставляя клипы по
  `placements` и заполняя промежутки тишиной.
- `ffmpeg` склеивает `videos/*.webm` (raw без звука) с `voice.wav`
  без `-shortest`. Полная длительность видео = max(audio_end, video).

### 1.7. Артефакты каждого обзора
В каталоге `/tmp/KS-XXXX/` (KS-XXXX — ID тикета QA):
```
record.mjs                  — Playwright сценарий
synth-segments.py           — копия общего скрипта
build-track.py              — копия общего скрипта
narration.txt               — повествовательный текст
segments.json               — длительности клипов (генерируется)
narration-timeline.json     — реальные тайминги (генерируется)
audio/seg-NN-<tag>.wav      — отдельные piper-клипы
voice.wav                   — итоговая голосовая дорожка
videos/*.webm               — сырое видео без звука
<slug>-overview.webm        — финальное видео со звуком (целевой артефакт)
report.html                 — кратко: что показано, тайминги, версии
```

### 1.8. Долговременное хранение
До настройки общего хранилища — `/tmp/KS-XXXX/` на сервере вебхуков
(как сейчас). Когда координатор согласует постоянное место, целевой
артефакт `<slug>-overview.webm` будет копироваться в общий каталог
(вариант — `s3://kingside-presentations/` или
`/project/docs/architecture/video-overview-series/videos/`). Это
решение принимается отдельно — сейчас НЕ блокирует серию.

### 1.9. Шаблонные скрипты
`synth-segments.py` и `build-track.py` идентичны во всех обзорах
(см. `/tmp/KS-4055/`). При нарезке очередного тикета QA их просто
копирует. Когда серия будет наполовину готова, имеет смысл вынести
их в `tools/video-overview/` отдельной задачей — это снимет
дублирование и зафиксирует версии piper/ffmpeg. Пока — копия рядом
с записью.

## 2. Каталог разделов

Источник правды по списку маршрутов — `apps/web/src/App.tsx`.
Маршруты, скрытые feature-флагами или admin-only, и dev-only
песочницы (`/__dev/*`, `/dev/*`) в серию НЕ входят.

Каждая карточка ниже — заготовка для отдельного тикета QA. В тикете
QA указывает свой `KS-XXXX`, копирует пункты «Сценарий» и
«Демо-данные» сюда же, остальное (стек, HUD, viewport) берёт из
раздела 1.

### Группа A — основа продукта

#### A1. Главная страница / онбординг гостя
**URL:** `/` (для гостя — `FeaturesPage`; для авторизованного —
редирект на `/play`).
**Цель:** за 2 минуты гость должен понять, что Kingside умеет (игра,
тренировки, анализ, лекции) и как зарегистрироваться.
**Длительность:** ~2 мин, 10 сегментов.
**Сценарий:**
1. *intro* — splash «Kingside — онлайн-платформа для шахмат».
2. *features-hero* — главная для гостя, hero-блок и кнопка «Начать».
3. *features-list* — короткая прокрутка по плиткам разделов.
4. *register-open* — переход на `/register`, форма регистрации.
5. *register-skip* — упоминание входа через Google (`/oauth/...`).
6. *first-login* — после dev-bypass попадаем на `/play`, видим лобби.
7. *nav-tour* — заголовок Nav: «Играть · Тренировка · Анализ ·
   Лекции · Профиль».
8. *outro* — splash «Регистрация бесплатна, играть можно сразу».

**Демо-данные:** ничего, кроме dev-bypass пользователя. Возможен
показ свежесозданного аккаунта без партий — пусть `/play` выглядит
«пустым», это и есть стартовая ситуация.
**Внешние зависимости:** `lessonsEnabled`, `puzzlesEnabled`,
`broadcastsEnabled`, `tournamentsEnabled` — все включены на dev,
иначе в hero-блоке часть тайлов недоступна.

#### A2. Игра против соперника (матчмейкинг + live-партия)
**URL:** `/play` → `/lobby` (если используется) → `/game/:id`.
**Цель:** показать путь «нажал играть → нашёл соперника → играю на
часах».
**Длительность:** ~3 мин, 14 сегментов.
**Сценарий:**
1. *intro* — splash «Игра против соперника».
2. *play-page* — `/play`, плитки лимитов (bullet/blitz/rapid).
3. *time-picker* — клик по лимиту, выбор «3+0», старт поиска.
4. *queue* — экран ожидания, индикатор поиска.
5. *game-start* — переход на `/game/:id`, расстановка, часы пошли.
6. *first-moves* — несколько ходов мышью, видны нотация и часы.
7. *premove* — демонстрация премува (тёмная стрелка ожидания).
8. *resign-menu* — выпадающее меню «Сдаться / Предложить ничью».
9. *game-end* — финальный экран с результатом.
10. *outro* — splash «Партия сохранена и доступна в Архиве».

**Демо-данные:** нужно два dev-bypass пользователя в двух
параллельных контекстах Playwright — один ищет, второй принимает.
Альтернатива — фикстурный бот в `apps/api` (если уже есть,
проверить `apps/api/src/matchmaking/`).
**Внешние зависимости:** WebSocket-gateway `/game` и matchmaking
запущены, Redis жив.

#### A3. Live-партии (просмотр чужих)
**URL:** `/games/live`, `/games/:id/watch`.
**Цель:** объяснить, как зритель смотрит чужие партии, переключает
доски, читает чат.
**Длительность:** ~2 мин, 9 сегментов.
**Сценарий:**
1. *intro* — splash «Просмотр живых партий».
2. *live-list* — `/games/live`, плитки активных партий с превью.
3. *open-game* — клик по плитке, переход на `/games/:id/watch`.

5. *spectator-chat* — окно чата зрителей (если есть).

A2 — там как раз создаётся партия, которую видно в `/games/live`.
**Внешние зависимости:** WebSocket подключение `/game` на чтение.

#### A4. Архив партий
**URL:** `/archive`, `/archive/games/:id`, `/archive/players/:slug`.
**Цель:** показать, как пользователь находит свою старую партию по

**Длительность:** ~2.5 мин, 11 сегментов.
**Сценарий:**
1. *intro* — splash «Архив партий».
2. *archive-open* — `/archive`, видны фильтры и список.
3. *filter-time* — фильтр по контролю времени.
4. *filter-result* — фильтр по результату (победа / поражение).
5. *filter-position* — поиск по позиции (FEN).
6. *open-game* — клик по партии, переход на `/archive/games/:id`.
7. *analyze-button* — кнопка «Разобрать» уводит в окно анализа.
8. *player-profile* — переход на `/archive/players/:slug`.
9. *outro* — splash «Архив хранит все партии».

**Демо-данные:** dev-bypass пользователь с 10–20 архивными
партиями. Фикстура — `apps/api/prisma/seed*.ts` (проверить наличие
функции «создать N архивных партий» — если нет, координатор заведёт
отдельный тикет backend).
**Внешние зависимости:** by-position search (вектор-сервис) — нужно
проверить, что включён.

#### A5. Мастерская (импорт партии)
**URL:** `/workshop`, `/workshop/pgn-files`, `/workshop/pgn-files/:id`.

3. *paste-pgn* — поле «Вставить PGN», вставка партии (Карлсен —

5. *save-file* — кнопка «Сохранить», переход в `/workshop/pgn-files`.
6. *file-list* — список файлов с превью.
7. *open-game* — открытие партии из файла.
8. *analyze-jump* — кнопка «Открыть в анализе» уводит на `/analysis`.
9. *outro* — splash «Импортированные партии остаются у тебя».

**Демо-данные:** готовый PGN на 20–30 ходов с понятными именами,
лежит в `narration.txt` как константа. Никаких сервер-фикстур не
нужно — всё происходит у залогиненного пользователя.
**Внешние зависимости:** PGN-парсер и `/workshop/pgn-files` API
живы.

#### A7. Game Review (разбор последней партии)
**URL:** `/game/:gameId/review`.
**Цель:** показать функцию «после партии — автоматический разбор с

**Длительность:** ~2 мин, 10 сегментов.
**Сценарий:**

   «Разобрать партию».

4. *accuracy-overview* — итоговая оценка точности по двум сторонам.

7. *generate-puzzle* — кнопка «Сгенерировать пазл из позиции».
8. *outro* — splash «Каждую партию можно разобрать в один клик».

**Демо-данные:** партия с известным зевком — можно подгрузить из
фикстуры или из готовой A2 (но там может не быть зевка). Лучше
подготовить PGN-фикстуру специально (короткая партия 15–25 ходов
с одним явным «??»).
**Внешние зависимости:** Game Review API (анализ Stockfish на
сервере) включён.

### Что в серию НЕ входит

- `/__dev/*`, `/dev/*` — dev-only песочницы для скриншотов
  компонентов; в продуктовой серии не нужны.
- `/admin/feature-flags` — admin-only страница; обзор не для
  широкой аудитории.
- `/help/external-engine`, `/credits`, `/terms`, `/terms-of-
  service`, `/docs/user-courses` — статические/служебные
  страницы; обзор не оправдан.
- `/oauth/callback`, `/lectures/:id/unavailable` — технические
  промежуточные экраны.
- `/lobby` — старая страница, при `user→/play` перехватывается;
  отдельный обзор не нужен.
- Studies (`/studies/*`) — модуль удалён в KS-3130 (ADR-067).
- Daily, `/puzzles/play-vs-engine` — редиректы.

## 4. Контракт тикета QA

Каждый тикет в Jira/Yougile от координатора на QA содержит:

1. Ссылку на раздел этого документа (например
   «по разделу 2 / B3 Precision»).
2. Целевой `/tmp/KS-XXXX/` для артефактов.
3. Slug финального файла (например `precision-overview.webm`).
4. Параметры записи из раздела 1 (viewport, голос, HUD) — не
   повторять, ссылаться на раздел 1 этого документа.
5. Acceptance — стандартный:
   - все сегменты сценария показаны в порядке списка;
   - ни одна фраза не обрезается на переходе сцены;
   - HUD-подсказка синхронна с тем, что на экране;
   - длительность совпадает с целевой ±20 с;
   - `report.html` сгенерирован.

QA НЕ переписывает сценарий — берёт пункты как есть. Если на
этапе записи обнаруживает, что сцена не получается (например,
кнопки нет, API падает), оставляет комментарий в своём тикете
и тегает `@architect` для правки этого документа.

## 5. Обновление документа

При каждом изменении продуктового UI (новая страница, удаление
старой, переименование маршрута) — этот документ обновляет
архитектор отдельным коммитом. Не дублировать сценарии в
тикетах — единый источник правды только здесь.

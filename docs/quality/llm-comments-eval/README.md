# Eval-фикстуры — LLM-комментарии к ходам (ADR-103 §9 / KS-3626)

Набор из 12 PGN-партий для прогона MVP-2 LLM-комментариев. Без эталонных комментариев — оцениваем содержательность ярлыков и причинности на глаз и автоматическими метриками.

Подбирал architect (KS-3620, ADR-103 rev 2). Chess-expert из плана убран.

### Покрытие мотивов и ярлыков

- **Тактические мотивы (`tactical_motifs`)** — fork (07), pin (06), discovered_attack (03), back_rank_weak (09).
- **Hanging piece расширенный** — 08.
- **Mate / mate-угрозы** — 01, 02, 03, 09.
- **Positional shifts** — king_exposed (01, 02, 05, 10), pawn_structure_weakened (06, 10), bishop_passive (04, 11), mobility_decreased (11), rook_on_open_file (12), threats_grew (03, 05, 07, 09), material_lost (08), material_gained (07, 08).
- **NAG-only ловушка** (модель не должна сводиться к пересказу знака): 01, 02, 09, 10, 11, 12 — там, где `classification` ставит «лёгкую» NAG-метку, но ход требует развёрнутого объяснения.

## Шапка PGN

Каждая фикстура содержит специальные теги:

- `[ExpectedFocusPly "<N1,N2,...>"]` — полуходы, на которых критично оценить комментарий.
- `[ExpectedMotifs "<motif_or_false_on_plyN>"]` — какие тактические мотивы ожидаем в `tactical_motifs[]` (или явное `:false` если мотив не должен сработать ложно).
- `[ExpectedShifts "<shift_id_on_plyN>"]` — какие `PositionalShiftId` ярлыки ожидаем после применения SF eval в backend.
- `[Note]` — что хочется увидеть в тексте комментария на каждом из focus-полуходов.

## Метрики (ADR-103 §9.2)

| Метрика | Цель | Метод |
|---|---|---|
| % комментариев, отсеянных post-валидацией | ≤ 5 % на партию | автомат, по логу `ReviewCommentService` |
| % комментариев с глаголом-причиной | ≥ 80 % | автомат, regex по тексту: `(выигрывает\|теряет\|атакует\|угрожает\|защищает\|улучшает\|ослабляет\|открывает\|связывает\|уходит\|возникает\|жертвует\|размен\|пропустил\|упустил)` |
| % галлюцинаций (упоминание мотива/фигуры/мата, которых нет в фактах) | ≤ 5 % | вручную, выборочная сверка 5 партий |
| Subjective 5-балл (architect, 1 ревьюер) | ≥ 3.5/5 | 5 случайных партий |

## Методика прогона

1. После готовности F1+F2+B1 локально:
   - `cd apps/api && REVIEW_COMMENT_V2=on npm run start:dev`,
   - `cd apps/web && npm run dev`.
2. Для каждой `*.pgn`:
   - Загрузить в Analysis-странице (импорт PGN).
   - Нажать «Разобрать партию».
   - Дождаться завершения дубля, сохранить выход `Analysis.pgn` дубля в `runs/<git-sha>/<fixture>.pgn` (для воспроизводимости).
3. Собрать комментарии из дубля, прогнать через автоматические метрики (скрипт в `tools/eval-llm-comments/` — будет написан в рамках A1, заглушка пока пуста).
4. Открыть 5 случайных дублей вручную, поставить 1–5 баллов по содержательности.
5. Отчёт в KS-3620 с таблицей метрик + ссылки на гитфолдер `runs/<git-sha>/`.

## Воспроизводимость

- Все PGN валидируются `chess.js` v1.4 (тот же что в `apps/web`):
  ```bash
  mkdir -p /tmp/pgn-validator && cd /tmp/pgn-validator && npm init -y && npm install chess.js@1.4
  node -e "const {Chess}=require('chess.js'); const fs=require('fs'); for (const f of fs.readdirSync('/project/docs/quality/llm-comments-eval').filter(x=>x.endsWith('.pgn'))) { try { const c=new Chess(); c.loadPgn(fs.readFileSync('/project/docs/quality/llm-comments-eval/'+f,'utf8')); console.log('OK',f); } catch(e){ console.log('FAIL',f,e.message); } }"
  ```
- На текущий коммит — 12/12 валидны.

## Расширение

3. Обновить таблицу состава в этом README.

Если набор окажется слишком узким после A1 — добавить ещё 5–10 фикстур по обратной связи (что прошло слабо).

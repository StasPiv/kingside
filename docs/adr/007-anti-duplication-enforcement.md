# ADR-007: Технический enforcement предотвращения дублирования работы агентов

## Статус

Принято (2026-03-08)

## Контекст

ADR-006 установил процессные правила координации агентов (Jira-статусы, последовательное выполнение, комментарии). Однако эти правила зависят от дисциплины промптов и не имеют технического enforcement. Анализ KS-199 выявил нерешённые проблемы:

1. **Нет защиты от параллельного запуска** — ничто технически не мешает запустить двух агентов на одну задачу
2. **Зависшие задачи** — при сбое агента задача остаётся "В работе" и блокирует других
3. **Нет валидации при merge** — ветка может быть смержена без проверки конфликтов и актуальности

## Решение

Три скрипта, реализующие технический enforcement поверх ADR-006:

### 1. Проверка конфликтов перед началом работы (`scripts/check-agent-conflict.sh`)

Агент ОБЯЗАН запускать эту проверку перед началом работы над задачей:

```bash
./scripts/check-agent-conflict.sh KS-201
```

Проверяет:
- **Worktree uniqueness** — нет ли другого worktree для той же задачи (KS-XX). Git гарантирует, что одна ветка не может быть checkout в двух worktrees, но разные агенты могут создать ветки с вариациями имён (feature/KS-201, feature/KS-201-wt, worktree-feature/KS-201). Скрипт ищет все варианты.
- **Jira status** — если задача уже "В работе", значит другой агент над ней работает (опциональная проверка, требует JIRA_* env vars).

Exit code 1 = конфликт обнаружен, работа запрещена.

### 2. Обнаружение зависших задач (`scripts/detect-stuck-tasks.sh`)

Координатор запускает периодически для обнаружения зависших задач:

```bash
./scripts/detect-stuck-tasks.sh [TTL_HOURS]
```

Логика: если worktree существует, но последний коммит старше TTL (по умолчанию 2 часа) — задача потенциально зависла. Агент мог упасть, а задача осталась "В работе".

Действия при обнаружении:
1. Проверить Jira-статус задачи
2. Если агент действительно упал — перевести задачу обратно в "К выполнению"
3. Удалить зависший worktree: `git worktree remove <path>`

### 3. Pre-merge валидация (`scripts/pre-merge-check.sh`)

Агент ОБЯЗАН запускать перед merge в main:

```bash
./scripts/pre-merge-check.sh
```

Проверяет:
- Branch naming convention (feature/KS-XX)
- Актуальность относительно main (нет ли отставания)
- Dry-run merge для обнаружения конфликтов

### Интеграция в workflow агента

```
┌─────────────────────────────────────────────────────┐
│ 1. Агент получает задачу KS-XX                     │
│ 2. ./scripts/check-agent-conflict.sh KS-XX          │
│    └─ exit 1? → СТОП, конфликт                     │
│ 3. Создать worktree, начать работу                  │
│ 4. Jira → "В работе", комментарий "ROLE: начал"    │
│ 5. ... работа ...                                   │
│ 6. Коммит                                           │
│ 7. ./scripts/pre-merge-check.sh                     │
│    └─ exit 1? → rebase, решить конфликты            │
│ 8. Merge в main                                     │
│ 9. Jira → "Done", комментарий "ROLE: завершил"     │
└─────────────────────────────────────────────────────┘
```

## Почему не git hooks

Git hooks (pre-commit, pre-merge-commit) были рассмотрены, но отклонены:
- **Worktree-специфика**: hooks в `.git/hooks/` разделяются между всеми worktrees. Hook, подходящий для одного агента, может блокировать другого.
- **Хрупкость**: hook, падающий с ошибкой, блокирует всю работу. Скрипт с exit 1 можно проигнорировать в экстренном случае.
- **Отладка**: скрипты проще тестировать и отлаживать изолированно.
- **Гибкость**: скрипты вызываются явно, координатор решает когда их запускать.

Скрипты — это "проверки по запросу" (advisory), а не "жёсткие блокировки" (mandatory). Это осознанный выбор: в проекте с одним разработчиком жёсткие блокировки создают больше проблем, чем решают (ложные срабатывания, deadlock при сбое).

## Последствия

### Положительные
- Техническое обнаружение конфликтов до начала работы
- Автоматическое обнаружение зависших задач
- Валидация ветки перед merge
- Инструменты не зависят от дисциплины промптов

### Отрицательные
- Advisory, не mandatory — агент может проигнорировать результат скрипта
- Jira-проверка требует настройки env vars
- Дополнительный шаг в workflow агента

### Компромисс
Advisory-скрипты вместо mandatory-hooks — осознанный trade-off. Для текущего масштаба (1 разработчик, 5 агентов) advisory-подход достаточен. При масштабировании можно обернуть скрипты в git hooks.

## Связь с ADR-006

ADR-007 дополняет ADR-006, не заменяя его:
- ADR-006 (правила 1-5) — процессные правила координации
- ADR-006 (правила 6-8) — архитектурные механизмы (worktrees, rebase, shared-код)
- **ADR-007** — скрипты, реализующие технический enforcement правил 1, 6, 7

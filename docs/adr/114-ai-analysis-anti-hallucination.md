# ADR-114: AI-анализ — снижение галлюцинаций конкретных ходов

**Статус:** Предложено
**Дата:** 2026-06-06
**Задача:** KS-3808
**Связанные ADR:** [ADR-102](./102-llm-move-comments-mvp1.md), [ADR-103](./103-llm-move-comments-mvp2.md), [ADR-108](./108-ai-position-comment-ux.md), [ADR-108b](./108b-ai-position-comment-board-overlay.md)

## 1. Контекст

### Симптом (скриншот KS-3808-hallucination.jpg)

В анализе партии вкладка «AI» показывает комментарий к ходу `Qf2`: «Лучше было пешечным ходом g3 защитить фланг и удержать баланс». На доске у белых пешка стоит на f4 — ход `g2-g3` ничему не помогает (не защищает f4, не закрывает фланг), это типичная **галлюцинация конкретного хода**. Похоже это «g3» подсказано первой линией Stockfish (sf18_pv), которую модель видит, но не понимает шахматный смысл.

### Где сейчас формируется запрос к модели

В системе три AI-endpoint'а:

1. **`POST /analyses/position/comment`** (`apps/api/src/position-comment/`) — статическая оценка одной позиции. Фронт собирает `{ fen, factors[], eval? }` и шлёт. `factors` — массив объектов `positionalSubterms` + `sf18_eval` + `sf18_pv` (KS-3721 уже вырезает `sf18_pv` на бэке для этого эндпоинта).
2. **`POST /analyses/review/move-comment`** (`apps/api/src/analysis-review/move-comment.service.ts`, KS-3711) — комментарий к одному ходу в «Полном разборе». Фронт шлёт `{ move, before: {fen, factors[], eval?}, after: {fen, factors[], eval?}, language }`. `factors[]` в обоих снимках содержат subterms + `sf18_eval` + **`sf18_pv`** — pv НЕ вырезается. Это и есть основной источник симптома KS-3808.
3. **`POST /assistant/chat`** (`apps/api/src/ai-chat/`) — чат-ассистент с MCP-инструментами, к KS-3808 отношения не имеет.

### Что уходит в prompt (move-comment)

- **Системная инструкция** ≈ 200 строк (RU), включая:
  - правила про `sf18_eval` (что приоритет, какие пороги cp);
  - правила про `sf18_pv` («НЕ пересказывай ходы из sf18_pv буквально», но `sf18_pv` всё ещё подан как факт);
  - словарь подкомпонент: **59 id** в glossary с человеческими именами;
  - запрет шаблонных зачинов, требования по формату JSON;
  - правила пересчёта `value` ↔ `terminal_value`.
- **Glossary дублируется в payload-поле `systemPrompt` и в userMessage** (KS-3694: webhook-сервер использует `claude --resume`, и `--system` применяется только на создание сессии, поэтому весь prompt продублирован в `userMessage`).
- **JSON-данные**: `move` (san/uci/check/mate/castling/promotion/classification) + `before.fen` + `before.factors[]` (десятки subterms × 4-6 числовых полей каждый + sf18_eval + sf18_pv UCI-список) + `after.{...}` симметрично.

Грубая оценка: системная инструкция + glossary ≈ 6–8 KB, два JSON-снимка ≈ 4–10 KB. Итого 10–18 KB текста на каждый ход. Полный разбор партии на 30 интересных ходов = 30 таких вызовов, каждый с тем же огромным контекстом.

### Корень проблемы

Три фактора, каждый вкладывается в галлюцинации:

1. **`sf18_pv` подан в факты.** Модель видит первую линию Stockfish как массив UCI: `["g2g3","e2e4",...]`. Промпт говорит «не пересказывай буквально», но это инструкция, а не гарантия. Модель регулярно срывается, особенно на длинной 200-строчной инструкции — внимание к запретам падает к концу контекста.
2. **Шум — почти весь glossary неинформативен для конкретной позиции.** Из 59 id в `SUBTERM_LABELS` в типичном `factors[]` присутствует ~10–20, остальные 40+ описаны в glossary впустую. Модель видит длинный «учебник» и пытается приклеить его к фактам.
3. **На выходе нет фильтра.** Модель может предложить любой ход в свободной форме («лучше было g3», «следовало сыграть Nf3»), ничего на бэке не проверяет легальность этого хода в исходной позиции.

### Что НЕ в скоупе ADR-114

- Замена модели (Claude → другая) — отдельный продуктовый вопрос.
- Полная переработка факторов Stockfish-trace (KS-3650/3648) — модель факторов остаётся.
- Дообучение/file-tuning — у нас нет подходящего пайплайна.
- Структурированный chat-mode (multi-turn refinement) — слишком дорого по токенам.
- Замена webhook-архитектуры (KS-3694, claude-resume) — это инфраструктура.

## 2. Решение

### 2.1 Гипотеза в первый удар (минимально, безболезненно)

Три точечных правки, каждая режет канал галлюцинаций без переписывания фронта/модели:

1. **Удалить `sf18_pv` из payload move-comment** (как уже сделано для position-comment, KS-3721). Модель не видит UCI-линий — нечего цитировать.
2. **Серверная валидация конкретных ходов в ответе.** Парсим текст комментария, извлекаем кандидатов на ходы (SAN: `Nf3`, `e4`, `Qxf7+`, русская нотация `Кf3`, и UCI `e2e4`), валидируем через `chess.js` в исходной позиции (`before.fen` для move-comment, `fen` для position-comment). Нелегальные — вычищаем/отмечаем, либо запрос ретраится.
3. **Сжать glossary до релевантных id.** На бэке перед отправкой берём из `factors[]` множество реально присутствующих `id` и в glossary оставляем только их. Уменьшает контекст и фокусирует модель.

Эти три шага дают (по оценке) **70%+ снижения галлюцинаций без потери качества комментариев**. Делаются за один backend-релиз, без миграций фронта.

### 2.2 Что именно убираем из контекста (§3 задачи — «что можно убрать»)

| Что | Сейчас | Решение | Почему |
| --- | --- | --- | --- |
| `sf18_pv` (UCI-линия) | Подаётся в move-comment в обоих снимках | **Убрать** | Прямой источник цитирования модели; промпт-запрет недостаточен |
| `sf18_eval` (cp/mate) | Подаётся | Оставить | Источник истины вердикта; модель должна знать перевес |
| `positionalSubterms[]` (~30 id) | Все шлются как есть | Оставить структуру, но (а) урезать glossary до присутствующих id, (б) опционально — top-N по значимости (см. §2.4) | Это и есть «факторы», ради которых LLM подключаем |
| Длинная инструкция «не выдумывай ходы» | 8–10 строк | Сокращаем до одной строки + structured-validation страхует | Лишнее текст — лишнее внимание |
| Glossary 59 id | Все 59 | Только id из текущего payload | См. §2.1.3 |
| `eval` (итоговая числовая) | Опционально | Оставить — модель и так не должна её цитировать | Промпт уже запрещает цитировать числа |

### 2.3 Серверная валидация ходов в ответе (§4 задачи)

Алгоритм после получения текста от модели и до возврата фронту:

1. **Extract candidates.** Поиск в `comment` по regex'ам:
   - SAN английский: `(?:[KQRBN])?[a-h]?[1-8]?x?[a-h][1-8](?:=[QRBN])?[+#]?` плюс рокировка `O-O(?:-O)?`.
   - SAN русский: `(?:[КФЛСК])?[a-h]?[1-8]?[x:]?[a-h][1-8](?:=[ФЛСК])?[+#]?` плюс рокировка `0-0(?:-0)?`.
   - UCI: `[a-h][1-8][a-h][1-8][qrbn]?` строго на границах слова.
2. **Validate each candidate** через `new Chess(fen).move(candidate, {strict: false})` для каждой формы. На совпадении хотя бы одной — кандидат легален, ничего не делаем.
3. **На нелегальный кандидат — две стратегии:**
   - **A. Soft-strip (рекомендация для MVP).** В тексте заменяем нелегальный кандидат на маркер `[ход недоступен]` (RU) / `[move unavailable]` (EN). Пользователь видит, что модель ошиблась с конкретикой, но общий комментарий остаётся. Логируем factor `move_validation_dropped_total{lang, endpoint}` для метрик.
   - **B. Retry с подсказкой.** При наличии нелегальных кандидатов делаем второй запрос с инструкцией «Previous response contained illegal moves: X, Y. Repeat without naming concrete moves». Стоимость — +1 запрос ≈ удвоение latency для ~10–20% ходов. Включать опционально через env (`POSITION_COMMENT_RETRY_ON_ILLEGAL=true`).
4. **Метрика и алерт.** Если >5% ответов содержат нелегальные ходы — вернуться к промпту/факторам (это сигнал, что промпт деградировал).

Для **position-comment** валидация по `dto.fen`. Для **move-comment** — по `before.fen` (модель комментирует «лучше было сыграть X» в позиции ДО хода).

**Граничный случай: cтрелка с UCI в `arrows`.** Уже валидируется на legal-square уровне (KS-3690 / `parseModelOutput`). Дополнительно проверяем легальность хода `arrow.from → arrow.to` через `chess.js`; если нелегален — стрелку отбрасываем (а не комментарий целиком).

### 2.4 Узкий контекст: pre-filter факторов на фронте (§3 задачи)

Frontend гипотеза от пользователя верна: меньше факторов → меньше шума → меньше галлюцинаций. Но не каждое сужение оправдано — некоторые subterms критичны для верного вердикта (king_safety, hanging_piece).

**Решение в два слоя:**

1. **Hard-include всегда:** `sf18_eval`, `hanging_piece`, `mate_threat_after`, `threats_created`, `threats_missed`, `material_change`, `sf_best.square` (без UCI ходов из sf_best.line), `tactical_motifs` (короткий список ярлыков). Это «обязательные сигналы».
2. **Soft-filter позиционных подкомпонент:**
   - Сортируем по `max(|value_mg|, |value_eg|, |terminal_value_mg - value_mg|, |terminal_value_eg - value_eg|)`. Берём топ-N (например, N=8).
   - Отбрасываем subterms с обоими `< 0.1` и без terminal-движения — статистически шумовые.

Эти эвристики — на фронте в `extractFacts.ts` / `buildSnapshotFactors.ts`. Бэк никаких новых проверок не делает (factors остаётся `unknown[]`, whitelist не вводится — фронт умнее бэка по этому домену, тестировано в KS-3650).

**Метрика для калибровки порога N и значимости:**
- `factors_count_before_filter` (histogram)
- `factors_count_after_filter` (histogram)
- A/B сравнение «с фильтром» vs «без» — после A/B видим, не упало ли качество комментариев (subjective rating).

### 2.5 Сжатие glossary (§2.1.3)

В `MoveCommentService.buildSystemPrompt`/`PositionCommentService.buildSystemPrompt` подмена:

```ts
private buildSubtermGlossary(language, factors): string {
  const presentIds = new Set<string>();
  for (const f of factors) {
    if (typeof f === 'object' && f && 'id' in f && typeof (f as any).id === 'string') {
      presentIds.add((f as any).id);
    }
  }
  return Object.entries(SUBTERM_LABELS)
    .filter(([id]) => presentIds.has(id))
    .map(([id, label]) => `- ${id} → ${label[language]}`)
    .join('\n');
}
```

В пустом случае (нет совпадений) — пустая строка; промпт остаётся валидным. Это сокращает glossary с ~59 строк до ~10–15 для типичной позиции.

**Безопасность.** Sf18_eval / sf18_pv / прочие «не-subterm» id (если есть) не попадут в glossary, потому что их нет в `SUBTERM_LABELS` — это и так уже было. Никакой регрессии.

### 2.6 Сжатие промпта

Сейчас инструкция 200+ строк дублируется в `systemPrompt` и `userMessage` (хак KS-3694). После KS-3808:

1. **Сократить инструкцию** до 60–80 строк: оставляем сводный mapping cp→вердикт, требование json-формата, основной запрет на конкретные ходы (одной строкой, с явным указанием «server validates moves, illegal will be stripped»), цветовую конвенцию. Все «учебные кейсы» (длинный пример про cp=-665) — убираем; держим в кодовой базе как комментарий для разработчиков, не модели.
2. **Удалить дубль.** В `userMessage` шлём ТОЛЬКО факты: `JSON.stringify({fen, factors, eval?})`. Инструкция — в payload-поле `systemPrompt`. Если webhook-server не доносит её до модели на resumed-сессии (KS-3694), решаем это **на стороне webhook-сервера**: либо новая сессия на каждый AI-comment запрос, либо `--append-system-prompt` для resume. Это инфра-фикс, не код API.

**Без шага «удалить дубль» эффект сжатия будет половинчатым** — модель всё равно увидит огромный текст. Но шаг 1 один даёт ощутимый выигрыш и без шага 2.

### 2.7 Альтернатива: structured output через Claude tool_use

Claude API поддерживает `tools` с JSON Schema. Заставить модель вернуть структуру с явным полем `recommended_move?: { uci, san }`, которое сразу можем валидировать. На webhook-уровне это не реализовано (мы используем `claude` CLI без явных tools). **Не на MVP**, но как стратегический шаг — отдельный ADR.

Польза: модель не может «свободно» вписать ход в текст — структура заставляет ход быть в строго определённом поле, валидация на бэке тривиальна.

Цена: webhook-server переписать, протестировать совместимость с двумя другими AI-endpoint'ами.

### 2.8 Риски и подводные камни

1. **Cтрипанный текст «[ход недоступен]» сбивает с толку пользователя.** Альтернатива: вычищать целиком фразу-носитель (склейка «лучше было X сыграть» → удалить всю фразу до точки/запятой). Сложнее, но чище UX. Решение: на MVP soft-strip с заменой; в KS-NXX добавить эвристику «удаления предложения, если в нём ≥1 ход и оно осталось без основной информации».

2. **False-positive: модель назвала легальный ход, но плохой по смыслу.** Валидатор не отличает «легальный, но бессмысленный» от «легальный и точный». Это уже выход за рамки KS-3808 — там симптом именно нелегальные ходы. Если в будущем понадобится дополнительная фильтрация — сверка с `sf18_eval` ДО и ПОСЛЕ предложенного хода (запускать chess.js + Stockfish, не дёшево).

3. **Регрессия по «полезности» комментария после убирания `sf18_pv`.** Возможно. Митигация: в `move-comment` для классов `blunder`/`mistake`/`inaccuracy` оставить из `sf_best` поле `to: square` (без `line`) — модель будет знать, что лучший ход направлен в клетку X, но не сможет назвать сам ход. После релиза смотрим subjective-rating; если просядет — возвращаем `sf_best.line[0]` (только первый ход), не больше.

4. **Pre-filter на фронте может отбросить значимый subterm.** Хорошо настроенный topN+threshold должны избежать; но потребуется A/B. До A/B-валидации не катить на 100% — раскат через feature-flag.

5. **Производительность бэка на retry-стратегии.** Удвоенная задержка для 10–20% запросов = +20–40% средней. Откладываем retry на отдельный feature-flag, не на MVP.

6. **Cтрелки `arrows` с нелегальными ходами уже отбраковываются?** Нет — KS-3690 проверяет только «клетки и палитру», не легальность хода. Добавляем chess.js-валидацию `arrow.from → arrow.to`. Если ход нелегален, отбрасываем стрелку (не весь ответ).

7. **Локаль и регистр SAN.** Русские «Кf3» (К — кириллица) и английские «Nf3» — разные regex. Покрываем оба. UCI стандартный.

8. **Шахматная нотация в тексте может быть не указанием хода, а упоминанием клетки.** Например, «слон на e4 силён» — это не ход. Regex должен отличать: SAN-кандидат должен быть в контексте «сыграть/X должен/лучше было», или просто все валидируем — если ход легален → ОК, если нелегален → правим. Принимаем «все, кто проходит chess.js — пропускаем»; ложные срабатывания не вредят.

## 3. Последствия

- **Backend.** Правки в `position-comment.service.ts` и `move-comment.service.ts`: убрать `sf18_pv` в move-comment, сжать glossary до присутствующих id, сократить промпт. Новый утильный модуль `apps/api/src/common/move-validator.ts` (или в `position-comment/`) — извлечение кандидатов на ходы из текста и валидация через `chess.js`. Применение валидатора в `parseModelOutput` (расширение существующего парсера) или после него.
- **Frontend.** Опциональный pre-filter в `extractFacts.ts`/`buildSnapshotFactors.ts` под feature-flag. Метрики `factors_count_*`.
- **Webhook-server** (`webhook-server.py`). Опционально (после KS-3808 main): починить доставку `systemPrompt` на resumed-сессии (см. §2.6 п.2). Не блокирующее.
- **DevOps.** Никаких изменений инфраструктуры. Возможны env-переменные: `MOVE_COMMENT_VALIDATE_MOVES=true` (по умолчанию true), `POSITION_COMMENT_RETRY_ON_ILLEGAL=false`.
- **QA.** Чеклист:
  - Воспроизведение симптома KS-3808 (партия PozitiFF_Chess vs HelllBorg, позиция после Qf2) → проверить, что нелегальный «g3» либо вычищен, либо отсутствует;
  - Разбор партии на 30 ходов — все ответы валидны (нет нелегальных в comment);
  - Glossary в payload (debug-log) — содержит только id, присутствующие в factors;
  - Стрелки нелегальные → отбрасываются, comment не теряется.

## 4. Предлагаемая разбивка на подзадачи

### Backend (приоритет 1, MVP закрытия KS-3808)

- **KS-N01 [backend]** — `move-comment.service.ts`: убрать `sf18_pv` из `before.factors`/`after.factors` перед сериализацией (аналог KS-3721 в position-comment). Unit-тест: factors не содержат `sf18_pv` в финальном `dataJson`.
- **KS-N02 [backend]** — общий утильный модуль `apps/api/src/common/move-validator/`:
  - `extractMoveCandidates(text, language): string[]` — regex SAN-en + SAN-ru + UCI.
  - `validateMoveInFen(candidate, fen): boolean` — через `chess.js`.
  - `stripIllegalMoves(text, fen, language): { sanitized: string, dropped: string[] }`.
  - Unit-тесты: разные формы, ложные срабатывания на «слон на e4», вложения в предложение.
- **KS-N03 [backend]** — интеграция валидатора:
  - `PositionCommentService.comment()` — после `parseModelOutput` пропускает `comment` через `stripIllegalMoves(text, dto.fen, language)`.
  - `MoveCommentService.comment()` — то же с `dto.before.fen`.
  - Метрики: `ai_move_validation_dropped_total{endpoint, language}`, `ai_move_validation_candidates_total`.
- **KS-N04 [backend]** — chess.js валидация `arrows[]` в `parseModelOutput`: для каждой стрелки `Chess(fen).move({from, to, promotion: 'q'})`, нелегальные — отбрасываем. Тест: легальная стрелка проходит, нелегальная отбрасывается, comment не задет.
- **KS-N05 [backend]** — сжатие glossary: `buildSubtermGlossary(language, factors)` принимает `factors[]` и оставляет только присутствующие id. Применяется в обоих сервисах. Тест: glossary в build = подмножество всех известных id, при пустых factors — пустая строка.
- **KS-N06 [backend]** — сжатие системного промпта: сократить инструкцию до 60–80 строк, убрать длинные обучающие примеры. Сохранить mapping cp→вердикт, format-rules, цветовую конвенцию, одну фразу про запрет конкретных ходов. Тест: smoke-eval по эталонным позициям.

### Frontend (приоритет 2, после стабилизации MVP)

# ADR-085. Разметка мотивов PVE-задач — применимость lichess-tagger

Статус: предложен (2026-05-29, ревизия 2) — аналитический документ
Связано: KS-3402 (этот ADR), KS-3399 (диагностика генерации),
ADR-080 (PRECISION_RELEVANT_THEMES), ADR-044 (PVE-парадигма),
ADR-070 (puzzle-gen-pipeline), KS-2406/2408/2419 (computeTags),
ADR-083 (двухфазная генерация — на паузе).

> **Ревизия 2 (2026-05-29).** Детали lichess-tagger подтверждены

> (`ornicar/lichess-puzzler`) через web (GitHub из песочницы
> архитектора блокируется). §2.1 (вход) и §2.4 (список тем) ниже —

## 1. Контекст и диагноз

В фильтре precision-задач по темам много пустых тем. Диагностика
(KS-3399) выявила **две корневые причины** в нашем
`computeTags` (`apps/tactic-worker/src/puzzle-generator/tagging.ts`):

1. **Тэггер смотрит только первый ход** (`moves[0]`) на стартовой
   FEN. Распознаёт узкий набор: `fork`, `pin`, `hangingPiece`,
   `hangingCreation` (через drill-predicates), `sacrifice` (SEE),
   фигуру/стадию, objective. Десятки lichess-мотивов (вскрытое
   нападение, отвлечение, завлечение, мат-паттерны и т.д.) не
   покрыты.
2. **Hardcoded `endsInMate: false`** (`generator-pipeline.ts:~351`).
   Матовые мотивы (`mate`, `mateIn1/2/3`) сгенерированным PVE-задачам
   НИКОГДА не присваиваются, потому что генератор не строит полную
   линию для проверки мата.

Пользователь поручил изучить применимость готового lichess-tagger.
**Главный вопрос (его выделил пользователь): формат ВХОДА** —
lichess-tagger размечает по полной линии решения, а у наших
play-vs-engine задач фиксированной линии нет.

## 2. Главный вопрос — вход тэггера vs наши данные

### 2.1 Что требует lichess-tagger на входе

Lichess puzzle = **форсированная тактическая линия**. От FEN пазла
решатель играет единственный хороший ход → у соперника
вынужденный ответ → решатель снова → … пока преимущество/мат не
очевидны. Эта `mainline` — единственное решение. Tagger (`cook.py`)
итерирует по всей mainline.

**Фактический вход `cook(puzzle)` (поля, которые читает код):**
- `id` — идентификатор.
- `cp` — оценка в центипешках (для `crushing`/`advantage`/`equality`).
- `pov` — сторона решателя.
- **`mainline`** — ВСЯ линия ходов решения (последовательность
  узлов). Большинство детекторов итерируют по ней.
- `game` — полная исходная партия (для фазы/метаданных/мата).

**Мат-логика (факт из кода):**
- Мат определяется через `game.end().board().is_checkmate()` —
  то есть требуется, чтобы линия физически **заканчивалась матом
  на доске**.
- `mateInN = len(mainline) // 2` — число ходов решателя до мата.

Эти два факта — корень проблемы у нас: PVE-задача не имеет линии,
заканчивающейся матом (генератор обрезает на N полуходов, не
доигрывает до мата), и `len(mainline)` для неё неопределён.

### 2.2 Что есть у нашей PVE-задачи

PVE-задача (ADR-044) = **«реализуй/удержи преимущество против
движка»**. От позиции (после зевка) решатель играет N полуходов
против Stockfish; успех = WDL не падает ниже tolerance.

- `Puzzle.moves` для `solutionMode='play-vs-engine'` — **пустая
  строка** (нет фиксированной линии).
- `sourceMetadata` — `blunderMove`, `wdlBefore/After`, `deltaW/D`,
  `puzzlePhase`, `firstMovePV1`. Линии решения НЕТ.
- Генератор смотрит только `bestMove[0]` (PV1) стартовой позиции.

**Вывод по главному вопросу:** у PVE-задачи **нет** фиксированной
линии решения в lichess-смысле — это игра против движка, много
допустимых продолжений, без вынужденной последовательности. Прямое
применение lichess-tagger «из коробки» **невозможно** — нечем
заполнить обязательный вход `mainline`.

### 2.3 Можно ли собрать суррогат линии — и почти бесплатно

**Да.** Stockfish в нашем генераторе (`stockfish.service.ts`,
`MultiPvLine`) уже возвращает **полную PV-строку** (`pv: string` —
последовательность UCI через пробел), а генератор берёт из неё
только `bestMove[0]` и **выбрасывает остальное**.

Значит суррогатную mainline (движковая главная линия на 10-20
полуходов + оценки) можно получить **без дополнительных прогонов
движка** — просто перестать выбрасывать `pv` при генерации новых
задач. Это даёт вход, структурно пригодный для tagger-подобной
логики.

**Важная оговорка о природе задач.** Движковая PV — это «лучшая
игра обеих сторон», НЕ «форсированный выигрыш материала/мата».
Для значительной доли PVE-задач (особенно `convertAdvantage` /
`saveEquality` позиционного типа) PV не содержит острого мотива —
это просто хорошие позиционные ходы. Для них тэги останутся
пустыми даже у идеального тэггера — **и это корректно**: у таких
задач нет тактического мотива, а objective (`convertAdvantage`/
`saveEquality`) уже сам является осмысленной темой.

Для PVE-задач, которые ДА содержат тактику (а зевок часто =
пропущенная тактика), суррогатная PV позволит детектировать мотив
и мат.

### 2.4 Фактический список тем cook.py (по исходнику)

Подтверждено координатором по `ornicar/lichess-puzzler` `cook.py`:

**Маты (требуют линию, заканчивающуюся матом):**
`mateIn1..5`, `smotheredMate`, `backRankMate`, `anastasiaMate`,
`hookMate`, `arabianMate`, `bodenMate`/`doubleBishopMate`,
`dovetailMate`.

**Оценка (по `cp`):** `crushing` (cp > 600), `advantage`
(cp > 200), `equality`.

**Мотивы (по линии + позициям):** `attraction`, `deflection`,
`advancedPawn`, `doubleCheck`, `quietMove`, `defensiveMove`,
`checkEscape`, `sacrifice` (материальный дефицит ≥ 2 после хода,
кроме промоций), `xRayAttack`, `fork`, `hangingPiece`,
`trappedPiece`, `discoveredAttack`, `exposedKing`, `skewer`,
`collinearMove`, `interference`/`selfInterference`, `intermezzo`,
`pin`, `attackingF2F7`, `kingsideAttack`/`queensideAttack`,
`clearance`, `enPassant`, `castling`, `promotion`,
`underPromotion`, `capturingDefender`.

**Эндшпили:** `pawnEndgame`, `queenEndgame`, `rookEndgame`,
`bishopEndgame`, `knightEndgame`, `queenRookEndgame`.

**Длина (по `len(mainline)`, в полуходах):** `oneMove` (2),
`short` (4), `long` (5-7), `veryLong` (8+).

**Важные факты для нашего порта:**
- `overloading` в коде **НЕ реализован** (всегда False) — НЕ
  тратить силы на него.
- `sacrifice` = чисто материальный критерий (дефицит ≥ 2 после
  хода, исключая промоции) — легко портируется через SEE/материал,
  у нас уже частично есть.
- Длина (`oneMove`/`short`/`long`/`veryLong`) и `mateInN` зависят
  от `len(mainline)`. Для суррогат-PV длина = глубина PV, что НЕ
  семантически эквивалентно «длине форсированного решения». Эти
  темы для PVE-задач малоинформативны — в порт НЕ включаем (длина
  PV не несёт тактического смысла, см. §2.3).
- Эндшпиль-типы и оценка (`crushing`/`advantage`/`equality`) —
  определяются по позиции/cp без линии, переносятся тривиально (и
  у нас частично есть).

## 3. Срез по нашему коду (проверено)

- `computeTags` — только первый ход + стартовая FEN + cp + флаг
  `endsInMate`. Drill-predicates (`findFork/findPin/
  findHangingPiece/findUndefendedAttack`) — FEN-only, без движка.
- `endsInMate: false` зашит → нет мат-тем (главный второй дефект).
- `Puzzle.moves=''` для PVE; `MultiPvLine.pv` содержит полную PV,
  но генератор её игнорирует.
- `PuzzleTheme` (`packages/shared/src/types/puzzle.ts`) — наша
  таксономия, пересекается с lichess по именам (`fork`/`pin`/
  `mate`/…) + наши (`playVsEngine`, `reactive`, `preventive`,
  `convertAdvantage`, `saveEquality`). Не копия кода lichess.
- Импорта `lichess-puzzler` в проекте нет.

## 4. Варианты интеграции

### A. Запуск lichess-puzzler tagger как Python-сервис/batch

Переиспользуем точную логику lichess.
- Минусы: (1) AGPL — серая зона (§5); (2) Python + python-chess в
  TS-стек (отдельный рантайм/деплой); (3) всё равно нужен
  суррогатный mainline-вход (§2.3); (4) расхождение версий
  chess-движков.
- Плюс: максимальное покрытие тем «из коробки».

### B. Полный порт tagger на TypeScript

Переписать ~1500 строк python-chess логики на chess.js.
- Минусы: большой объём, риск расхождений, поддержка.
- Плюс: нет AGPL-рантайм-проблемы (чистая реализация по
  алгоритмам), единый стек.

### C. Расширить наш computeTags на TS + суррогатная PV (рекомендуется)

Чинит обе корневые причины и наращивает покрытие инкрементально:
1. **Захватить движковую PV** при генерации (перестать выбрасывать
   `MultiPvLine.pv`) → суррогатная mainline **бесплатно**.
2. **Починить `endsInMate`**: вычислять из PV — если score типа
   `mate` или синтезированная линия кончается матом, ставить
   `mate`/`mateInN`.
3. **Прогонять мотив-детекторы по всей линии**, а не только по
   первому ходу.
4. **Нарастить TS-детекторы** инкрементально, портируя
   *алгоритмы* lichess (вилка/связка/шомпол/вскрытое/мат-паттерны
   геометрией) — алгоритмы не охраняются авторским правом, в
   отличие от конкретного кода.
5. **Принять**, что позиционные convert/save задачи легитимно
   имеют только objective-тег.

- Плюсы: лицензионно чисто, единый стек, чинит ровно
  диагностированные дефекты, инкрементально.
- Минусы: мотив-детекторы пишем сами (но часть уже есть как
  drill-predicates).

## 5. Лицензия lichess-puzzler (AGPL-3.0)

- AGPL — copyleft + сетевой пункт (§13): при *распространении*
  модифицированной версии ИЛИ взаимодействии пользователей с ней
  *по сети* нужно открыть исходники.
- **Внутренний offline-batch** (наш генератор зовёт tagger,
  складывает строки-теги в БД; пользователи НЕ взаимодействуют с
  AGPL-кодом по сети — видят только теги) — это «internal use».
  §13 триггерится на взаимодействии пользователя с *программой*
  удалённо; хранение производных данных (ярлыков тем) — не
  распространение программы. Это стандартное прочтение, но
  **юридически серая зона** — строгая трактовка может не
  согласиться.
- Имена тем (таксономия) — не объект авторского права; уже
  частично используем.
- **Безопасный путь** — реализовать алгоритмы на TS самим (вариант
  C/B), не тащить AGPL-код в рантайм.

## 6. Backfill (существующие ~1530 задач)

- У существующих PVE-задач `moves=''` и сохранённой PV нет.
- **Новые задачи** получают богатые теги сразу — захват PV при
  генерации бесплатен (§2.3).
- **Backfill старых** требует повторного прогона Stockfish на
  каждой задаче (получить PV) → дорого (сопоставимо с генерацией).
  Рекомендация: backfill — отдельный опциональный batch на 1530
  задач (re-analyze сохранённых FEN → PV → tagger). Не блокирует
  основной путь; можно отложить или прогнать одноразово.

## 7. Рекомендация

**Вариант C** — расширить наш TS-тэггер с суррогатной PV. НЕ
интегрировать lichess-puzzler как сервис.

Обоснование:
- Прямое применение lichess-tagger невозможно (нет mainline-входа,
  §2.2); суррогат PV всё равно надо строить самим.
- Суррогат PV — бесплатен при генерации (Stockfish уже возвращает
  `pv`, §2.3).
- AGPL добавляет лицензионный риск при сетевом использовании (§5).
- Вариант C чинит ровно диагностированные дефекты (первый-ход-only
  + endsInMate=false) и наращивается инкрементально.
- Значительная доля PVE-задач объективно без мотива — ни один
  тэггер этого не изменит; objective уже их «тема».

Приоритет покрытия (наибольшая отдача первой):
1. **Мат-темы** (`mate`, `mateInN`) — починка `endsInMate`,
   самый частый дефект, дёшево.
2. **Тэггинг по всей линии** для уже имеющихся детекторов
   (fork/pin/hanging) — ловят мотив не только на первом ходу.
3. **Новые детекторы** (skewer, discoveredAttack, deflection,
   мат-паттерны) — инкрементально, порт алгоритмов.

## 9. Риски

1. **Глубина PV.** При высоком nodes-лимите PV обычно 10-20
   полуходов — достаточно для мотива/мата. При низком (если
   ADR-083 двухфазность вернётся) — PV короче, мат-детект может
   страдать. Митигация: для tagging использовать PV из deep-прогона.
2. **Суррогат ≠ форсированная линия.** PV — лучшая игра, не
   форсированный выигрыш. Некоторые lichess-темы (intermezzo,
   quietMove), завязанные на «вынужденность», на суррогате могут
   давать ложные/пропуски. Митигация: начинать с надёжных
   (мат-паттерны, fork/pin/skewer/discovered), осторожно с
   «линейными» темами.
3. **Доля без мотива.** Часть PVE-задач объективно без тактики —
   тэги останутся пустыми. Это не дефект; objective — их тема.
   Зафиксировать в продукте (UI не должен внушать, что «должна быть
   тема»).
4. **AGPL при варианте A/B.** Снят выбором C (свой TS-код).
5. **Расхождение с lichess.** Наш порт может расходиться с
   эталоном — приемлемо, мы под свою таксономию и природу задач.

## 10. Что НЕ делаем

- НЕ интегрируем lichess-puzzler как Python-сервис (AGPL + вход).
- НЕ строим отдельную «линию решения» в БД для PVE (парадигма
  ADR-044 её не предполагает) — PV только для tagging, в
  sourceMetadata.
- НЕ переписываем весь cook.py разом (вариант B) — инкрементально
  (вариант C).
- НЕ трогаем frontend — фильтр уже готов (ADR-080).

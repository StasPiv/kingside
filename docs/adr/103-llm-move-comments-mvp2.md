# ADR-103. Качество LLM-комментариев к ходам (MVP-2)

Статус: предложен (KS-3620).
Дата: 2026-06-03.
Связано: ADR-102 (MVP-1), KS-3614 / KS-3615 / KS-3616 (реализация MVP-1).

## 1. Контекст

ADR-102 / KS-3614+3615+3616 завели MVP-1: фронт собирает 15–25 фактов о ходах с NAG-метками (`extractFacts.ts`), бэк (`ReviewCommentService.batchComment`) шлёт батч в существующий `AI_CHAT_WEBHOOK_URL`, ответ применяется к PGN-дублю.

На живой партии видно, что качество комментариев низкое в трёх повторяющихся сценариях:

1. **Тавтология NAG.** На `?!` модель пишет «неточность», на `?` — «ошибка», на `!` — «сильный ход». Это пересказ поля `classification`, которое пользователь уже видит как знак на доске. Содержания нет.
2. **«Фигура висит» без причины.** При наличии `hanging_piece` модель говорит «конь висит на f6». Не указано кем атакован, есть ли защита, что произойдёт при взятии, почему вообще оказался под боем.
3. **Молчание о тактике.** Prompt запрещает выдумывать вилки/связки/рентгены, если их нет в фактах — а в фактах их вовсе нет (детектора мотивов нет). Даже когда мотив очевиден (после хода — вилка коня на короля и ферзя), модель про него молчит.

Причины:
- **Бедные факты.** `FactsInput` (ADR-102 §3.4) содержит `classification`, `delta_e`, `sf_best`, `hanging_piece {square, piece, side}`. Нет: что выигрывает ход, что упускает слабый ход, какие тактические мотивы в позиции, кем атакована и защищена висящая фигура.
- **Жёсткие ограничения prompt'а.** `buildSystemPrompt` (`review-comment.service.ts:212`): «ONE short sentence (max 20 words)», `CRITICAL RULES` запрещают любую оценку сверх `classification`. В 20 русских слов осмысленное объяснение причины не помещается. Few-shot примеров «плохо / хорошо» нет.
- **Нет post-валидации.** Бессодержательные ответы пропускаются на фронт как есть.

## 2. Граница MVP-2

### Входит

1. **Обогащение `FactsInput`** — `tactical_motifs[]`, `threats_created`, `threats_missed`, расширение `hanging_piece` (attackers/defenders/net), `sf_best.line` (2–3 хода SAN).
2. **Дешёвые детекторы мотивов** на frontend: вилка, связка, сквозное нападение, вскрытое нападение, мат «по последней горизонтали», двойное нападение.
3. **Переписать prompt** — запрет NAG-тавтологии, требование причины, лимит 30–40 слов, 5–8 few-shot пар, расширенная калибровка по ELO.
4. **Post-валидация** — backend: чёрный список NAG-фраз, минимальная длина, замена пустой строкой.
5. **Eval-набор** — 20–30 разобранных партий с эталонными комментариями (chess-expert), методика ручной оценки.
6. **Feature-flag rollout** — ENV `REVIEW_COMMENT_V2=on|off`, откат на MVP-1 одним переключателем.

### НЕ входит (за пределы MVP-2)

- Перегруженный защитник, отвлечение, завлечение, промежуточный ход — требуют мини-поискового движка.
- Дообучение LLM на корпусе мастеров.
- Streaming SSE.
- TTS / voice.
- Endgame tablebase facts.
- Кэширование комментариев в БД (повторный «Разобрать» обновляет дубль).

## 3. Решение по детектору мотивов

### 3.1. Где реализуем — frontend (extractFacts.ts)

`extractFacts` уже работает с `chess.js`, получает `fenBefore` / `fenAfter` / `sfBestPv` и делает `c.attackers()` для `hanging_piece`. Перенос детектора мотивов на backend требует слать ту же информацию повторно (FEN + PV) и дублировать `chess.js`-логику.

Frontend:
- Имеет `chess.js`-инстансы уже сформированными.
- Несёт CPU нагрузку SF/Maia — детектор на 15–25 ply × ≤2 мс каждый = ≤50 мс на партию, незаметно.
- Backend остаётся stateless: «facts in → comments out».

Решение: **детекторы в `extractFacts.ts`** (frontend).

### 3.2. Дёшевые мотивы — реализуем

| Мотив | Алгоритм | Стоимость |
|---|---|---|
| `fork` | После played-хода: ходившая фигура атакует ≥2 фигуры противника, net по ценности > 0. `c.attackers()` от целевого square + scan атакованных фигур. | O(1) |
| `double_attack` | Обобщение fork — любые два атакованных объекта (включая поля рядом с королём). | O(1) |
| `pin` | Ray-scan от слона/ладьи/ферзя нашей стороны в сторону короля противника: если по лучу одна фигура противника между атакующим и королём — pin. | O(линий × 7) |
| `skewer` | То же что pin, но впереди стоит более ценная фигура противника, сзади — менее. | O(линий × 7) |
| `discovered_attack` | Сравнить `attackers` целевой фигуры до и после played-хода. Если появился новый атакующий, не двигавшийся на этом ходу — discovered. | O(scan board) |
| `back_rank` | Король на 1/8 горизонтали, перед ним пешки своего цвета, нет фигуры противника на этой горизонтали — мотив `back_rank_weak`. | O(8) |

Все шесть детектируются без обращения к движку.

### 3.3. Сложные мотивы — НЕ делаем в MVP-2

- `overloaded_defender` — нужно знать, что фигура защищает ≥2 угрозы и одна разрушает баланс. Требует мини-поиска.
- `deflection`, `decoy`, `interference` — требуют расчёта вариантов.
- `zwischenzug` — требует анализа порядка ходов.

Включаем позже, если eval-набор покажет, что отсутствие критично.

## 4. Расширенная схема `FactsInput`

```ts
type TacticalMotif =
  | 'fork' | 'pin' | 'skewer'
  | 'discovered_attack' | 'double_attack' | 'back_rank_weak';

type ThreatTarget = {
  /** Что атакуется/защищается. */
  piece: 'p' | 'n' | 'b' | 'r' | 'q' | 'k';
  square: string;
};

type FactsInput = {
  // ── из MVP-1 (без изменений) ─────────────────────────────────────
  ply: number;
  fen: string;
  side: 'white' | 'black';
  move: { san; uci; capture; check; mate; castling; promotion; en_passant };
  classification: MoveClass;
  delta_e: number;
  maia_alternative: { uci; san; probability; classification } | null;
  stage: 'opening' | 'middlegame' | 'endgame';
  opening_name: string | null;
  material_balance: number;
  material_change: { piece; side } | null;
  mate_threat_after: number | null;
  user_elo: number;
  user_language: 'en' | 'ru';

  // ── расширения MVP-2 ─────────────────────────────────────────────

  /** sf_best дополнен короткой линией 2–3 хода SAN — для «надо было X Y Z». */
  sf_best: {
    uci: string;
    san: string;
    /** SAN-нотация продолжения 2–3 хода (без played-хода), может быть пустой. */
    line: string[];
  } | null;

  /** Висящая фигура с контекстом «кем и кем защищается». */
  hanging_piece: {
    square: string;
    piece: 'p' | 'n' | 'b' | 'r' | 'q';
    side: 'white' | 'black';
    /** Атакующие фигуры противника (мин. ценность первой). */
    attackers: Array<{ piece; square }>;
    /** Защитники той же стороны (если есть — фигура защищена). */
    defenders: Array<{ piece; square }>;
    /** Net в пешках, если оптимальная серия разменов пройдёт. + = ходивший выигрывает. */
    net_material_if_taken: number;
  } | null;

  /** Что создаёт played-ход. Все поля optional — фронт заполняет что обнаружил. */
  threats_created: {
    mate_in?: number;
    /** Готовится выиграть материал (после оптимального ответа противника). */
    wins_material?: ThreatTarget & { net: number };
    /** На сколько объектов нацелен ход (для fork/double_attack). */
    targets?: ThreatTarget[];
  } | null;

  /** Что упустил слабый ход — сравнение с sf_best на той же позиции. */
  threats_missed: {
    mate_in?: number;
    wins_material?: ThreatTarget & { net: number };
    /** Чем грозит противник в ответ — мат / выигрыш материала. */
    counter_threat?: { mate_in?: number; wins_material?: ThreatTarget & { net: number } };
  } | null;

  /** Тактические мотивы, реализованные played-ходом или возникшие после него. */
  tactical_motifs: TacticalMotif[];
};
```

Backend DTO (`batch-comment.dto.ts`) повторяет shape 1:1 с class-validator-декораторами (`@IsArray`, `@IsIn`, вложенные `@ValidateNested @Type`).

## 5. Новый промпт

### 5.1. Системный prompt (RU-вариант, EN зеркальный)

```
Ты — шахматный тренер. Комментируешь ходы конкретного учащегося.
Язык ответа: {language}. ELO ученика: {userElo}.

ВХОД: JSON-массив фактов о ходах. Каждый факт — один полуход.

ВЫХОД: JSON-массив строк той же длины, в том же порядке. Каждая строка — один комментарий.

ТРЕБОВАНИЯ К КАЖДОМУ КОММЕНТАРИЮ:
- 1–2 предложения, 15–40 слов.
- Объясни ПРИЧИНУ: что выигрывает / что теряет / какую угрозу создаёт / какой мотив реализован.
- Если есть hanging_piece — назови атакующую фигуру и есть ли защита; если защищена — короткая оценка размена (`net_material_if_taken`).
- Если есть tactical_motifs — назови мотив (вилка / связка / вскрытое нападение и т.п.) и какие фигуры он атакует.
- Если есть threats_created — опиши угрозу.
- Если есть threats_missed.wins_material — кратко покажи правильный план: используй `sf_best.line` ("надо было Nxe5 Qxe5 d4").

ЧТО ЗАПРЕЩЕНО:
- Не дублировать NAG словами: фразы «сильный ход», «лучший ход», «отличный ход», «хороший ход», «слабый ход», «неточность», «ошибка», «грубая ошибка», «зевок» — БЕЗ объяснения причины ЗАПРЕЩЕНЫ. Если факта недостаточно для комментария — верни пустую строку "".
- Не выдумывать тактические мотивы, которых нет в `tactical_motifs`.
- Не упоминать оценку движка в сантипешках.
- Не давать общих советов («играй активнее», «развивай фигуры»).

КАЛИБРОВКА ПО ELO:
- userElo < 1500: простые слова — «теряет ферзя», «вилка на короля и ладью», «защищён конём, можно брать», «вскрытый шах».
- 1500 ≤ userElo < 2000: «инициатива», «темп», «упускает компенсацию», «связка».
- userElo ≥ 2000: «изолированная пешка», «слабый комплекс», «активность фигур», «жертва качества».

ПРИМЕРЫ (few-shot):

Факты:
{ "move": { "san": "Nxe5", "capture": "p", "check": false }, "classification": "best",
  "tactical_motifs": ["fork"],
  "threats_created": { "targets": [{ "piece":"q","square":"d7"}, {"piece":"r","square":"f7"}] } }
ПЛОХО: "Сильный ход."
ХОРОШО: "Конь забирает пешку и одновременно атакует ферзя и ладью — вилка с двойным выигрышем материала."

Факты:
{ "move": { "san": "Qd5" }, "classification": "blunder", "delta_e": -0.6,
  "hanging_piece": { "square":"d5","piece":"q","side":"white","attackers":[{"piece":"n","square":"f6"}],"defenders":[],"net_material_if_taken": -8 },
  "sf_best": { "san":"Qe2", "line": ["Qe2","O-O","Nf3"] } }
ПЛОХО: "Грубая ошибка."
ХОРОШО: "Ферзь становится под удар коня f6 без защиты — теряется фигура. Спокойнее Qe2 с рокировкой."

Факты:
{ "move": { "san": "Bxf7+", "capture": "p", "check": true }, "classification": "good",
  "tactical_motifs": ["discovered_attack"],
  "threats_created": { "wins_material": { "piece":"q","square":"d8","net": 6 } } }
ПЛОХО: "Хороший ход."
ХОРОШО: "Жертва слона со вскрытым шахом — после взятия открывается ферзь и теряется на следующем ходу."

Факты:
{ "move": { "san": "h6" }, "classification": "inaccuracy", "delta_e": 0.15,
  "threats_missed": { "wins_material": { "piece":"p","square":"e4","net": 1 } },
  "sf_best": { "san":"Nxe4", "line":["Nxe4","Bxe4","d5"] } }
ПЛОХО: "Неточность."
ХОРОШО: "Профилактика, но пропущен Nxe4 с выигрышем центральной пешки."

Факты:
{ "move": { "san": "Rxd1" }, "classification": "good", "material_change": { "piece":"r","side":"white" },
  "hanging_piece": null, "tactical_motifs": [] }
ПЛОХО: "Хорошо."
ХОРОШО: "Размен ладьи на ладью, упрощает позицию в эндшпиле без материальных потерь."

Факты:
{ "move": { "san": "Kg1" }, "classification": "best",
  "tactical_motifs": ["back_rank_weak"], "mate_threat_after": null }
ПЛОХО: "Лучший ход."
ХОРОШО: "Король уходит с задней линии — иначе мат ладьёй после размена на e1."

[... 1–2 примера для en, по аналогии]
```

### 5.2. Параметры запроса

- `temperature: 0.4` — без изменений.
- `max_tokens` per fact: 80 → **160** (поднимаем под 30–40 слов).
- Few-shot прибавит ~1500 input-tokens, но платится один раз на батч.

### 5.3. Калибровка по ELO

Помимо лексики (как в MVP-1) — глубина объяснения:
- <1500 — один мотив на ход, простыми словами.
- 1500–2000 — допускается короткая цепочка причина → следствие.
- ≥2000 — допустимы позиционные термины («плохой слон», «компенсация за пешку»).

## 6. Post-валидация

В `ReviewCommentService.parseAndValidate` после успешного парсинга — пройти по массиву и нормализовать.

### 6.1. Чёрный список NAG-тавтологий

Нормализация строки: `trim`, lowercase, убрать пунктуацию `.!?,:;`. Если результат точно совпадает с одной из фраз — заменить пустой строкой.

Список (RU):
- «сильный ход», «отличный ход», «лучший ход», «хороший ход»
- «слабый ход», «плохой ход»
- «ошибка», «грубая ошибка», «зевок»
- «неточность»

Список (EN — на случай, если модель не послушалась `language`):
- «strong move», «excellent move», «best move», «good move»
- «weak move», «poor move»
- «mistake», «big mistake», «blunder»
- «inaccuracy»

Регексы (ru):
```ts
const NAG_TAUTOLOGY_RU = /^(сильный|отличный|лучший|хороший|слабый|плохой)\s+ход[.!?]*$/i;
const NAG_SHORT_RU = /^(ошибка|грубая\s+ошибка|зевок|неточность)[.!?]*$/i;
```

Замена → `""`.

### 6.2. Минимальная содержательность

После очистки:
- Минимум **4 слова** или **25 символов** — иначе → `""`.
- Игнорируем `""` (валидно — модель сама вернула пустую строку).

### 6.3. Поведение фронта

KS-3616 уже умеет показывать дубль с пустыми комментариями — для отсеянных просто рисует NAG-знак без подписи. Никаких изменений на фронте не нужно.

## 7. Eval-набор

### 7.1. Состав

- **20–30 разобранных партий** разного уровня (1200 / 1500 / 1800 / 2100 ELO).
- В каждой — 15–25 ходов с NAG.
- Для каждого хода — **эталонный комментарий** от chess-expert (1–2 предложения, объяснение причины).
- Покрытие мотивов: вилка, связка, скрытое нападение, висящая фигура с/без защиты, упущенный материал, мат-угроза, back-rank, размен.

### 7.2. Метрики

| Метрика | Цель |
|---|---|
| Доля комментариев, отсеянных post-валидацией (черный список + min length) | ≤ 5 % на партию (резкое падение vs MVP-1, где «ошибка»/«неточность» прошли бы) |
| Доля комментариев, упоминающих причину (наличие глагола «выигрывает/теряет/атакует/защищает/угрожает») | ≥ 80 % |
| Доля комментариев, упоминающих несуществующий мотив (галлюцинация) | ≤ 5 % |
| Subjective rating (5-bal, 2 ревьюера независимо) на 5 случайных партий | ≥ 3.5/5 |

### 7.3. Процесс

1. После реализации фронта/бэка — chess-expert готовит набор партий с эталонами (`docs/quality/llm-comments-eval/`).
2. Architect прогоняет pipeline на наборе локально, собирает метрики.
3. Если метрики ниже целей — итерация над prompt'ом / детекторами.
4. Отчёт в комментарии KS-3620.

## 8. Бюджет токенов и rollout

### 8.1. Оценка токенов

| Часть | MVP-1 | MVP-2 |
|---|---|---|
| System prompt (фикс) | ~250 tokens | ~1800 tokens (с few-shot) |
| Один факт | ~150 tokens | ~325 tokens (+motifs, +threats, расш. hanging_piece, sf_best.line) |
| 25 фактов | ~3750 | ~8125 |
| Output (25 × 40 слов × ~1.5 tok/слово) | ~750 | ~1500 |
| **Total на партию** | ~4.75k | ~11.4k |

Рост ~2.4×. Claude Sonnet/Haiku — 200k контекст, не упираемся. Latency через webhook: ~5–15 с MVP-1 → ~10–25 с MVP-2. Целевой p50 «Разобрать партию» 70–130 с (ADR-101) → 80–145 с (укладываемся).

### 8.2. Стоимость

Pro/Max OAuth ноутбука — $0 для пользователя. Если когда-нибудь мигрируем на API tier — рост cost-per-partia ~2.4×, держим в уме.

### 8.3. Rollout

ENV:
```
REVIEW_COMMENT_V2=on   # default off в .env.example; on на проде после eval
```

`ReviewCommentService.buildSystemPrompt` ветвится по флагу:
- `off` → MVP-1 prompt (как сейчас).
- `on` → MVP-2 prompt с few-shot.

`extractFacts.ts` всегда отдаёт расширенный shape (старые поля присутствуют, новые — опциональные). Backend при `V2=off` игнорирует новые поля. Это упрощает откат.

Post-валидация всегда включена — независимо от флага. NAG-тавтология не должна попадать на фронт ни при MVP-1, ни при MVP-2.

### 8.4. Rate-limit

Без изменений: 10/мин per-user, 30/день per-user, 200/день global (`REVIEW_COMMENT_RATE_LIMIT_*` ENV). Расширение фактов не меняет частоту запросов — те же 1 батч на партию.

## 11. Резюме

MVP-2 добивает три явные проблемы MVP-1 (тавтология NAG, «висит» без причины, молчание о тактике) тремя ортогональными вложениями:

1. **Больше фактов** — детекторы 6 дёшевых мотивов + расширенные `hanging_piece` / `threats_created` / `threats_missed` / `sf_best.line` на frontend (`extractFacts.ts`).
2. **Лучше prompt** — переписан с запретом NAG-тавтологии, требованием причины, 5–8 few-shot пар, расширенным лимитом 30–40 слов.
3. **Post-валидация** — backend режет бессодержательные ответы (NAG-blacklist + min-length).

Eval-набор (chess-expert, 20–30 партий с эталонами) валидирует выкатку до prod. Rollout через `REVIEW_COMMENT_V2` ENV — откат на MVP-1 одним переключателем.

Decompose: F1 (frontend extractor 2 д) → F2 (shared 0.5 д) → B1 (backend 1.5 д) → C1 (chess-expert eval 1.5 д, параллельно) → A1 (architect eval-прогон 0.5 д) → D1 (devops rollout). Итого ~5–6 дней работы с учётом распараллеливания.

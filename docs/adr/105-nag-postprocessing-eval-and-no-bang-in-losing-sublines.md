# ADR-105 — NAG post-processing: eval-знак на ходе-ошибке и запрет `!`/`!?` в проигранных вариантах

Status: Proposed.
Дата: 2026-06-03.
Связано: KS-3636 (запрос пользователя), ADR-100 (NAG auto-annotation), ADR-066 (WDL classification), KS-3619 (`pickFinalEvalNag`).

## 1. Контекст

ADR-100 §3.2 ставит на сыгранный ход один quality-NAG из набора `!!/!/!?/?!/?/??`. KS-3619 добавил позиционный NAG (`=/⩲/⩱/±/∓/+−/−+`) **на финальную позицию вариантов** через `pickFinalEvalNag`. На самом ходе в основной линии позиционного знака не было.

В KS-3636 (PGN сицилианская c3 с ручной разметкой) пользователь указал две недоработки:

1. На ходе-ошибке в main-line, когда оценка качественно ухудшилась (например, `≈ → −+`), кроме `?`/`??` нужен позиционный NAG на том же ходе.
2. `!`/`!?` неуместны в subline-варианте, который заканчивается всё ещё проигранной за того же игрока позицией.

## 2. Текущее состояние

### 2.1. Пункт 1 — частично уже сделано

В `apps/web/src/lib/review/buildAnnotations.ts:374-393` уже есть пост-шаг: если `pickNag` вернул `NAG_DUBIOUS` (`?!`), `NAG_MISTAKE` (`?`) или `NAG_BLUNDER` (`??`), к массиву `nags` добавляется `pickFinalEvalNag(wdlStmPov, stmAfterIsWhite)`. То есть на `?`/`??` уже ставится позиционный знак.

Что осталось:
- зафиксировать поведение тестами (часть `buildAnnotations.test.ts` уже добавила `qualityOnly`-хелпер, но самостоятельной проверки eval-части на ходе-ошибке нет);
- проверить, что пороги `pickFinalEvalNag` соответствуют ожиданиям пользователя (см. §4.1);
- подавлять `=` (NAG 11) на ходе-ошибке: если eval не отличается от равного — позиционный NAG бесполезен, оставляем только `?/??`.

### 2.2. Пункт 2 — не реализовано

`maybeGreenVariation` ставит `NAG_GOOD` (`!`) на ход SF-best зелёной вариации, когда `sfBestProb < 0.10` (`buildAnnotations.ts:291-297`), независимо от того, чем заканчивается subline. Главная линия `pickNag` ставит `!` / `!?` через `playedClass === 'best'` (`samePlayed && playedProb < 0.10`) и `playedClass === 'good'` (`!samePlayed && playedProb ≥ 0.30`) — тоже без проверки итога.

Симметричный suppress `DECIDED_WDL_THRESHOLD = 0.95` гасит NAG только в полностью decided-позициях. В позиции с `wdlSigned ≈ −0.6` (явный проигрыш, но не decided) `!` всё ещё ставится — что и поймал пользователь.

## 3. Решение

### 3.1. Пункт 1 — позиционный NAG на ходе-ошибке

**Сохранить** существующий шаг постобработки в `buildAnnotation` (строки 374-393). Добавить два уточнения:

a) Если `pickFinalEvalNag` возвращает `NAG_EVAL_EQUAL` (11) — **не добавлять** его на ходе-ошибке. Знак `?`/`??` сам по себе означает «стало хуже»; добавлять `=` рядом — противоречиво. На финальной позиции варианта `NAG_EVAL_EQUAL` остаётся (там это полезная информация).

b) Тесты в `buildAnnotations.test.ts`: для всех веток `?!`/`?`/`??` добавить кейс «после хода — `+−`/`−+`/`±`/`∓`», проверить присутствие соответствующего NAG в `nags`. Один кейс «после `??` оценка осталась ≈» — проверить, что `NAG_EVAL_EQUAL` НЕ добавлен.

### 3.2. Пункт 2 — запрет `!`/`!?` при «всё ещё проигран»

Новые пороги (фиксируются в `buildAnnotations.ts` как именованные константы):

```ts
/** Игрок считается «проигрывающим» в позиции, если его E ≤ 0.25,
 *  то есть signed_pov ≤ −0.5. Порог выбран как нижняя граница «±»-
 *  диапазона pickFinalEvalNag, симметрично к 0.75 (которое уже считаем
 *  явно выигрывающим). */
const LOSING_E_THRESHOLD_POV = 0.25;

/** Минимальное улучшение E (POV игрока), которое разрешает поставить
 *  `!`/`!?`. Меньше — «оценка фактически не выросла», ход не заслуживает
 *  качественного знака. 0.10 — половина шага шкалы ± (0.20). */
const QUALITY_NAG_MIN_E_GAIN_POV = 0.1;
```

**Правило**: `!` (NAG 1) и `!?` (NAG 5) разрешены тогда и только тогда, когда **выполнено хотя бы одно** из:

- `E_before_pov > LOSING_E_THRESHOLD_POV` (исходная позиция не проигрышная для игрока), ИЛИ
- `E_after_pov − E_before_pov ≥ QUALITY_NAG_MIN_E_GAIN_POV` (оценка улучшилась минимум на 10 п.п.).

Иначе `!`/`!?` не ставятся — ни в main-line, ни в зелёной вариации.

Применение:

**Main-line** (`pickNag`):
- Для `playedClass === 'best'` (ветка `!`): после прохождения порога `playedProb < 0.10` — дополнительно проверить условие выше с `E_before = expectedScoreFromWdl(wdlBefore)` и `E_after = expectedScoreFromWdl(wdlAfterPlayed)`. Не прошло — вернуть `null` вместо `NAG_GOOD`.
- Для `playedClass === 'good'` (ветка `!?`): аналогично перед `return NAG_INTERESTING`.

**Green variation** (`maybeGreenVariation`):
- Для ветки `sfBestProb < 0.10`: проверить тем же правилом, но с `E_after = E_at_end_of_subline_pov` (см. §3.3 — новое поле).

**Red variation** (`maybeRedVariation`): сейчас `!`/`!?` не ставит, изменения не нужны.

### 3.3. Конец subline как новый вход

Чтобы проверить условие в зелёной вариации, нужен WDL **в конце subline** POV игрока, начинавшего вариант. Сейчас в `MoveInput` есть только `wdlAfterBest` (после первого хода SF-best).

**Изменения**:

1. `apps/web/src/lib/review/buildStabilizedLine.ts` — расширить возвращаемое значение: вместо `string[]` → `{ moves: string[]; finalWdl: Wdl }`, где `finalWdl` — POV того же игрока, что и `startFen`'s STM (т.е. POV игрока, начинавшего вариант). Caller-сайт инвертирует raw SF-output на каждом ply, конечный — POV нужного игрока.

2. `MoveInput` — добавить **необязательное** поле `sfBestSublineFinalWdl?: Wdl`. Если задано — используется для проверки в §3.2. Если не задано (legacy / тест) — fallback на `wdlAfterBest`. Это backward-совместимо.

3. `useGameReview` (caller) — после `buildStabilizedLine` положить новый `finalWdl` в `MoveInput.sfBestSublineFinalWdl`.

Аналогичное поле `maiaTopSublineFinalWdl?: Wdl` для красной вариации **не нужно в MVP** (красная не ставит `!`/`!?`), но логично добавить симметрично — возьмётся в follow-up.

### 3.4. Edge-case «ничья → ничья»

Вопрос пользователя из описания: разрешён ли `!?` за «удержание ничьей» в subline.

Решение: **да, разрешён** в main-line. Условие §3.2 пропускает кейсы, где `E_before_pov > 0.25` — ничейная позиция (E ≈ 0.5) проходит. Для зелёной subline, начинавшейся в ничейной и оставшейся в ничейной, тоже проходит — `!` остаётся, потому что критерий «удержать ничью неочевидным ходом» содержательный (это и есть `sfBestProb < 0.10`).

«Запрет» бьёт только когда позиция была проиграна **и** не улучшилась — содержательное толкование «`!` = заслуга».

### 3.5. Совместимость с `DECIDED_WDL_THRESHOLD` (KS-3617)

Существующий симметричный suppress (0.95) не пересекается с новым правилом: он гасит NAG в decided-позициях, не меняющих исход; новое правило режет `!`/`!?` в «частично проиграно». Оба остаются. Порядок проверок в `pickNag`: сначала `DECIDED`-suppress (как сейчас), затем — `LOSING`-suppress для `!`/`!?` (новый).

## 4. Пороги — обоснование

### 4.1. Пороги `pickFinalEvalNag` (без изменений)

Пользователь не указал на ошибку в шкале; текущие 0.05/0.15/0.35 (=/±/+−) соответствуют общепринятой шахматной шкале (≈/⩲/±/+−). Калибровка по 12 фикстурам — в acceptance F-тикета.

### 4.2. `LOSING_E_THRESHOLD_POV = 0.25`

Шкала `pickFinalEvalNag` POV white:
- E ≥ 0.85 → +−
- E ≥ 0.65 → ±
- E ≥ 0.55 → ⩲
- 0.45 ≤ E ≤ 0.55 → =
- ≤ 0.45 → симметрично

Граница 0.25 POV игрока = E_white ≤ 0.25 (если игрок чёрные — наоборот) = «решительное преимущество противника» (+− или −+). Это и есть «всё ещё проиграна».

Альтернатива — 0.35 (= нижняя граница ±). Считаем слишком мягкой: ход в позиции с ± может быть содержательным (есть шанс уравнять), запрещать `!` рано.

### 4.3. `QUALITY_NAG_MIN_E_GAIN_POV = 0.10`

10 п.п. — половина шага шкалы ±. Меньшие колебания — внутри одной категории оценки, «оценка не изменилась». Также: ADR-066 §3.2 порог `inaccuracy` = 0.05; рост 0.10 — заметное движение в обратную сторону.

## 6. Acceptance

1. На PGN-фикстуре пользователя (сицилианская c3, прикладывается к F-тикету) NAG-разметка совпадает с ожиданиями: на ходе-ошибке стоит `?`/`??` + позиционный NAG (но не `=`); в проигранной subline нет `!`/`!?`.
2. Регрессий нет на `docs/quality/llm-comments-eval/` 12 фикстурах — ручная проверка после прогона `useGameReview` локально, diff annotation массивов до/после.

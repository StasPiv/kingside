# ADR-025: SM-2 для повторения уроков

**Дата:** 2026-04-23
**Статус:** Предложено
**Задача:** KS-1797 (L-20)
**Связанные документы:**
- [ADR-024](./024-lessons-module.md) — схема уроков, прогресс-политика
- [lessons-module.md](../architecture/lessons-module.md) — общее видение
- [lessons-roadmap.md](../architecture/lessons-roadmap.md) §2 — итерация 2

---

## 1. Контекст

ADR-024 зафиксировал прогресс-политику: урок считается «пройденным»
при `score ≥ 70` и «освоенным» при повторном прохождении через
7–14 дней со `score ≥ 80`. Поле `UserLessonProgress.masteredAt`
заведено в схеме, но в MVP всегда `null`.

В итерации 2 (KS-1798 / L-21) нужно запустить собственно механику
повторения. Предмет этого ADR — выбор алгоритма интервального
повторения, его адаптация к уроку как единице повторения, модель
данных и выбор планировщика.

Что нужно решить **до миграции Prisma** (L-21):

1. Как считать интервал до следующего повтора.
2. Как мапить результат прохождения (score 0..100) в вход алгоритма.
3. Отдельная ли таблица или расширение `UserLessonProgress`.
4. Планировщик: BullMQ vs `@nestjs/schedule` vs самодельный
   `setInterval` (как `BotCleanupService` в `apps/game-service`).
5. Границы: когда урок вообще попадает в систему повторения.

## 2. Решение

### 2.1 Алгоритм SM-2, адаптация к уроку

Используем классический SM-2 (SuperMemo 2, Piotr Woźniak, 1987),
единица повторения — **урок целиком**, а не отдельная карточка/шаг.
Карточки/шаги внутри урока не моделируются как независимые элементы
SM-2: повторный прогон урока в режиме «повтора» — один атомарный акт,
результат — один `score` (0..100), мапится в одно `quality` (0..5).

Переменные на каждую пару `(userId, lessonId)`:

- `easiness` (float, «коэффициент лёгкости»): стартовое значение
  `2.5`, нижняя граница `1.3` (классический SM-2).
- `interval` (int, дней): сколько дней до следующего повтора.
- `repetitions` (int): сколько успешных повторов подряд (`quality ≥ 3`).
- `dueAt` (DateTime): когда урок назначен к повторению.
- `lastReviewedAt` (DateTime): когда был последний повтор.
- `lastQuality` (int 0..5): результат последнего повтора.

Формулы (после очередного повтора с входом `q = quality`):

```
if q < 3:
    repetitions_new = 0
    interval_new    = 1           # «с нуля», первый повтор завтра
else:
    if repetitions == 0:
        interval_new = 1
    elif repetitions == 1:
        interval_new = 6
    else:
        interval_new = round(interval * easiness)
    repetitions_new = repetitions + 1

easiness_new = easiness + (0.1 - (5 - q) * (0.08 + (5 - q) * 0.02))
if easiness_new < 1.3:
    easiness_new = 1.3

dueAt_new = now() + interval_new days
```

**Адаптации относительно классического SM-2:**

- Единица — урок, не карточка (в классике карточка с одним вопросом).
  Это допустимо: урок — педагогически атомарен (одна тема) и повторное
  прохождение воспринимается пользователем как одно «задание».
- Нет отдельного «режима репетиции» с отдельной шкалой (like vs pass):
  весь прогон идёт штатным фронтендом урока (`LessonPage`), просто
  запись результата идёт в `LessonReview`, а не только в
  `UserLessonProgress`.

### 2.2 Маппинг `quality` из `UserLessonProgress.score`

`score` в ADR-024 — `Int 0..100`. Описание задачи упоминает «балл
0..1» — имеется в виду нормализованная форма того же `score`.
Для единообразия везде в backend-коде считаем `score ∈ [0, 100]`,
нормализация при необходимости — на стороне фронта.

Маппинг `score → quality`:

| `score` (0..100) | `quality` | Интерпретация                                      |
|------------------|-----------|----------------------------------------------------|
| `0..49`          | `0`       | Провал, почти не вспомнил; сброс `repetitions = 0` |
| `50..59`         | `2`       | Слабый провал; сброс                               |
| `60..69`         | `3`       | Пограничный успех (не дотянул до «пройден»)        |
| `70..79`         | `3`       | «Пройден», но не «освоен»                          |
| `80..89`         | `4`       | «Освоен», уверенное прохождение                    |
| `90..100`        | `5`       | «Освоен» без ошибок                                |

Обоснование:
- `q = 1` пропущен осознанно: нет удобного диапазона score для
  «вспомнил, но с явной ошибкой, так что сбрасываем». В SM-2 `q ≤ 2`
  одинаково сбрасывают `repetitions`, шкала работоспособна без `q=1`.
- Граница `q ≥ 3` совпадает с границей «урок пройден» (`score ≥ 70`
  плюс «почти пройден» `60..69`): мягкий режим, чтобы случайная
  ошибка не обнуляла серию повторов, если в целом пользователь
  помнит тему.
- `q = 4` привязан к `score ≥ 80` — совпадает с критерием «освоен»
  из ADR-024.

### 2.3 Модель данных — `LessonReview`

Отдельная таблица, а не расширение `UserLessonProgress` (см. §3.1).

```prisma
model LessonReview {
  id              String   @id @default(uuid()) @db.Uuid
  userId          String   @map("user_id") @db.Uuid
  lessonId        String   @map("lesson_id") @db.Uuid
  easiness        Float    @default(2.5)                          // SM-2 EF, ≥ 1.3
  interval        Int      @default(1)                            // дней до следующего повтора
  repetitions     Int      @default(0)                            // серия успешных повторов (q ≥ 3)
  dueAt           DateTime @map("due_at")                         // когда урок пойдёт в «к повторению»
  lastReviewedAt  DateTime? @map("last_reviewed_at")              // null до первого повторного прохождения
  lastQuality     Int?     @map("last_quality")                   // 0..5, null до первого повтора

  user            User     @relation(fields: [userId], references: [id])
  lesson          Lesson   @relation(fields: [lessonId], references: [id], onDelete: Cascade)

  @@unique([userId, lessonId])
  @@index([userId, dueAt])
  @@map("lesson_reviews")
}
```

Индексы:
- `@@unique([userId, lessonId])` — один урок — один трек повторений
  у пользователя.
- `@@index([userId, dueAt])` — основной запрос «что у меня сегодня
  на повтор»: `WHERE user_id = ? AND due_at <= now() ORDER BY due_at`.

Связанные изменения в существующих моделях — **никаких**.
`UserLessonProgress.masteredAt` уже заведено в ADR-024 §2.1.

### 2.4 Жизненный цикл записи

**Создание `LessonReview`** — при первом прохождении урока со
`score ≥ 80`, одновременно с записью `UserLessonProgress.masteredAt`:

```
repetitions    = 1
interval       = 1                  # первый повтор — через 1 день
easiness       = 2.5 + EF-correction по q (обычно 2.6 для q=5)
dueAt          = now() + 1 day
lastReviewedAt = now()
lastQuality    = quality(score)
```

**Обновление `LessonReview`** — при каждом следующем прохождении
этого урока пользователем (неважно, попал ли он в «сегодня к
повторению» или решил сам): пересчитываем по формулам §2.1,
обновляем `lastReviewedAt = now()`, `lastQuality = quality(score)`,
`dueAt = now() + interval_new days`.

**Удаление** — каскад от `Lesson` (если урок удалён/депубликован
и запись мешает). Явного удаления по событиям пользователя нет.

### 2.5 Явная граница: когда урок попадает в SM-2

SM-2 применяется **только к уже пройденным урокам**:

- Запись в `LessonReview` создаётся только при **первом**
  `UserLessonProgress.completedAt != null` **и** `score ≥ 80`
  (одновременно с `masteredAt`).
- Урок, у которого `completedAt != null`, но `score < 80` (т. е.
  «пройден», но не «освоен»), **в SM-2 не попадает**. Повторить
  такой урок можно вручную, но он не будет в списке «к повторению
  сегодня» и не даёт уведомления.
- Урок со `completedAt = null` (никогда не пройденный) **в SM-2
  не попадает**. Первое прохождение — обычный путь.

Обоснование: интервальное повторение осмысленно только для
материала, который пользователь уже освоил. До этого — обычная
прогрессия курса.

### 2.6 Выбор планировщика: `@nestjs/schedule`

Сравнение вариантов (для одной периодической задачи «обновить
просроченные `dueAt` / отправить пуш»):

| Критерий                  | BullMQ + Redis       | `@nestjs/schedule`         | Самодельный `setInterval`   |
|---------------------------|----------------------|-----------------------------|-----------------------------|
| Новые зависимости         | `bullmq`, `@nestjs/bullmq` | `@nestjs/schedule`   | —                           |
| Инфраструктура            | Redis уже есть       | —                           | —                           |
| Точное время «03:00 UTC»  | Да (delayed jobs)    | Да (`@Cron('0 3 * * *')`)   | Нет, только интервал        |
| Retry, DLQ, UI            | Да                   | Нет                         | Нет                         |
| Кластеризация (несколько API-инстансов) | Да (job lock) | Нет, cron сработает на каждом инстансе | Нет |
| Overkill для 1 задачи/сутки | Да                 | Нет                         | Неудобно считать «до 03:00» |

**Выбираем `@nestjs/schedule` + `@Cron('0 3 * * *')` (03:00 UTC)**.

Обоснование:
- Ровно одна периодическая задача в сутки. BullMQ-очереди,
  worker'ы и retry — избыточная инфраструктура под кейс «1 cron-job».
- Redis задействован (`ioredis` для кэша и Socket.IO-адаптера),
  но добавление BullMQ тянет `@nestjs/bullmq` и `bullmq` — ещё две
  зависимости.
- `@nestjs/schedule` — официальный пакет NestJS, ~100 KB, простой
  декоратор `@Cron`.
- Сейчас в `apps/game-service` есть аналог (`BotCleanupService`
  через `OnModuleInit + setInterval`), но он работает «раз в
  5 минут», без привязки к времени суток. Для «раз в 03:00 UTC»
  декоратор `@Cron` удобнее, чем ручной расчёт первой задержки.
- **Кластеризация API.** Если в будущем API-инстансов станет >1,
  cron сработает на каждом. Митигация — distributed lock через
  Redis (SET NX EX с TTL 1 час): первый дошедший до БД обновляет,
  остальные — нет. Реализация — в рамках L-21.

Время `03:00 UTC` выбрано как:
- Ночь по UTC+3 (Россия: 06:00 MSK) — минимум активных
  пользователей и игровых сессий.
- Приложение и так просыпается/работает в это время (broadcast-sync
  идёт непрерывно) — дополнительной инфраструктурной нагрузки нет.

### 2.7 Что делает cron

**Обязательная часть (реализуется в L-21):**

- Ничего не пересчитывает в `LessonReview`: `dueAt` уже актуален
  (поставлен при последнем повторе). Запрос «что сегодня
  повторять» идёт **на лету** через индекс `(userId, dueAt)`.
- То есть: **без cron-job сам механизм повторений полностью
  функционален**. Запись создаётся/обновляется синхронно при
  завершении урока, выборка «на сегодня» — на лету при заходе
  пользователя в раздел «Уроки».

**Опциональная часть (может быть отложена):**

- Ежедневный агрегат «у вас N уроков к повторению» → рассылка в
  `Notification` (существующая таблица уведомлений) и/или
  Telegram-бот, если будет.
- Метрики в Prometheus: количество уроков с `due_at <= now()` по
  пользователям, среднее `easiness`, средний `interval`.

Эти пункты в L-21 **не блокирующие**. Если не успеваем — выносим
в отдельную задачу итерации 2. В ADR-025 фиксируем только контракт
cron (время, сигнатура метода сервиса, distributed lock).

### 2.8 Ограничения контекста «Уроки»: только Stockfish WASM

**В разделе «Уроки» используется только Stockfish WASM на клиенте.
Серверный движок (`useExternalEngine` / engine-сервис) не используется.**

Это общее правило для всего раздела «Уроки» (согласовано с
пользователем), SM-2 и механика повторений — частный случай.
Если какой-либо шаг урока в режиме повтора потребует движковой
подсказки или проверки — только wasm (`useEngine` / `useStockfish`).

Следствия:
- Никаких backend-эндпоинтов, проксирующих ходы движка, для шагов
  уроков.
- При падении wasm-сборки на конкретной версии — обновлять
  wasm-сборку, а не переключаться на сервер.

### 2.9 Обратная совместимость

- Существующие записи `UserLessonProgress` из MVP (`masteredAt = null`)
  продолжают работать без изменений. Миграции данных нет.
- `masteredAt` заполняется **по факту** следующего прохождения
  урока со `score ≥ 80` — это может быть и первый, и пятый прогон,
  логика одинаковая: «первый раз, когда пользователь прошёл урок
  на ≥ 80 %».
- `LessonReview` — новая таблица, не влияет на существующие
  запросы и UI MVP.
- Задачи фронта L-22 (UI «К повторению сегодня») — новый раздел,
  старые страницы не трогает.

## 3. Альтернативы, отвергнутые

### 3.1 Расширение `UserLessonProgress` вместо отдельной `LessonReview`

Добавить `easiness`, `interval`, `repetitions`, `dueAt` прямо в
`UserLessonProgress`. Отвергнуто:
- `UserLessonProgress` хранит прогресс **первого** прохождения
  (шаги, `completedAt`, `score`). Мешать туда историю повторений
  — нарушение SRP модели.
- Индекс `(userId, dueAt)` стоял бы на таблице с `dueAt = null`
  у всех неосвоенных уроков (большинство записей) — бесполезно
  широкий.
- Проще расширять SM-2 в будущем (добавить `lapses`, `leechCount`
  из SM-17/FSRS), не задевая `UserLessonProgress`.

### 3.2 SM-17 / FSRS (Free Spaced Repetition Scheduler)

Современный алгоритм на базе машинного обучения, лучше калибруется.
Отвергнуто:
- FSRS требует обучения на истории пользователя (≥ 1000 карточек /
  повторов). На старте раздела «Уроки» таких данных нет.
- Сложнее в реализации и отладке, больше полей в модели.
- SM-2 — стандарт де-факто (Anki, SuperMemo), есть общепринятая
  референсная реализация.

Вернёмся к FSRS, если через 6–12 месяцев накопим статистику и
SM-2 окажется слишком грубым.

### 3.3 Единица повторения — шаг (`LessonStep`), а не урок

Ближе к классике SM-2 (карточка). Отвергнуто:
- Шаги одного урока педагогически связаны: повторять «вопрос 3 из
  урока про вилки» в отрыве от теории урока бессмысленно.
- Взорвёт объём таблицы повторений (~30 * 5 шагов на курс
  «Начинающий» = 150 карточек на пользователя против 30 уроков).
- Интерфейс «сегодня повторить шаг X урока Y» запутан; «повторить
  урок Y» — понятен.

### 3.4 BullMQ

См. §2.6 — overkill для одной ежедневной cron-job.

### 3.5 Пересчёт `dueAt` в ежедневном cron

Идея: один раз в сутки пробегать все `LessonReview` и обновлять
`dueAt`. Отвергнуто: `dueAt` ставится один раз при записи повтора,
он уже корректен; cron-пересчёт был бы no-op для большинства строк.
Запрос «что повторять сегодня» делается on-demand через индекс.

### 3.6 Настройка интервалов пользователем

Отвергнуто в итерации 2 явно. Добавим при накоплении жалоб.

## 4. Последствия

### Положительные

- Алгоритм — широко известный, легко отлаживается против
  референсной реализации.
- Модель данных изолирована (`LessonReview`), не ломает MVP.
- Выборка «к повторению сегодня» — O(log N) по индексу, без cron.
- Планировщик — одна зависимость (`@nestjs/schedule`),
  инфраструктура (Redis/BullMQ) не добавляется.

### Отрицательные / компромиссы

- SM-2 — 1987 год, FSRS точнее. Митигация: SM-2 покрывает первые
  6–12 месяцев, переход на FSRS — отдельный ADR с миграцией
  `LessonReview`.
- Граница «`quality ≥ 3` если `score ≥ 60`» — субъективная шкала,
  подбирали руками. Митигация: пороги вынесены в §2.2 отдельной
  таблицей, меняются без миграции.
- В кластере (>1 API-инстанс) cron нужно защитить distributed
  lock. Реализация — в L-21.

### Нейтральные / задел на будущее

- Добавить `lapses` (число провалов подряд) в `LessonReview` —
  без миграции данных (default 0).
- Cron-job — опциональная часть, сейчас нужна только для
  уведомлений; механизм повторений работает и без него.

## 5. Что не делаем в итерации 2

- **Кросс-курсовые повторы** — повторение уроков из разных курсов
  в один «урок-повтор». Каждый урок в SM-2 независим.
- **Настройка интервалов пользователем** — стартовый `easiness`,
  множители и т. п.
- **Экспорт в Anki** / импорт сторонних колод.
- **FSRS** — см. §3.2.
- **Повторы на уровне шага** — см. §3.3.
- **A/B-тесты на параметрах** — `easiness_init`, пороги
  маппинга `score → quality`. Подбираем вручную, меряем drop-off
  руками.

## 6. Что делать после принятия ADR

1. **L-21** (backend): Prisma-миграция с таблицей `lesson_reviews`,
   `LessonReviewService` (расчёт SM-2, выборка «сегодня»),
   интеграция в `ProgressService.completeLesson` (создание/обновление
   записи при `score ≥ 80`), cron `@Cron('0 3 * * *')` с distributed
   lock через Redis, установка `@nestjs/schedule`.
2. **L-22** (frontend): раздел «К повторению сегодня» на
   `LessonsPage`, API `GET /lessons/due`, прохождение урока в
   режиме повтора (пометка, что это повтор, запись в
   `LessonReview`), порог `≥ 80%` для успешного повтора.
3. Обновить `lessons-module.md` §2.1 и §2.3 ссылкой на эту ADR
   и добавить упоминание `LessonReview` (делается в L-21).

Изменения алгоритма SM-2 после принятия ADR — через новый ADR
или отдельным комментарием в этом файле с привязкой к тикету.

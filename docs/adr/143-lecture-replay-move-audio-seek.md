# ADR-143: Переход к моменту обсуждения хода в записи лекции (клик по ходу → перемотка аудио)

**Статус:** Черновик на ревью координатором
**Дата:** 2026-06-25
**Задача:** KS-4638
**Связанные ADR:** [ADR-115](./115-lecture-audio-recording.md), [ADR-116](./116-lecture-audio-p2p.md), [ADR-119 §3.2/S5](./119-lecture-ui-coach-student.md), [ADR-142](./142-lecture-multi-analysis-switching.md)

> **Установка для этой работы.** Пользователь явно попросил усиленное внимание контрактам клиент-сервер: «синхронизация клиентской и серверной части должна быть идеальной». В §3-§5 контракт зафиксирован однозначно (единый источник истины в shared-типах, детерминированный алгоритм построения, тесты на синтетических фикстурах). При любом расхождении между разделами этого ADR — пометьте противоречие явно и согласуйте до реализации; не «дотолковывайте» по умолчанию.

## 1. Контекст

### 1.1 Что есть сейчас

После ADR-115/116 у каждой записанной лекции есть два параллельных потока:

1. **Доска и ходы.** `LectureRecording.events[]` — упорядоченный массив `RecordedEvent` с метками `t` (мс от `Lecture.startedAt`). Типы события зафиксированы в `packages/shared/src/types/live-analysis.ts`:
   - `RecordedMoveEvent` — `{t, type:'move', payload:{uci, ply}}`.
   - `RecordedStatePatchEvent` — `{t, type:'state-patch', payload:{tree (JSON-строка), currentGlobalIndex?, orientation}}`. **`tree`** — `{history: ChessMove[], headers?, initialFen?}` с проставленными `globalIndex` у каждого узла (KS-3780); **`currentGlobalIndex`** — индекс узла, на котором стоит тренер.
   - `RecordedResetEvent` — `{t, type:'reset', payload:{fen, orientation}}`.
   - `RecordedAnalysisSwitchEvent` — `{t, type:'analysis-switch', payload:{analysisId, title}}` (ADR-142).
   - `RecordedClosedEvent` — `{t, type:'closed', payload:{reason}}`.

2. **Аудио тренера.** `LectureAudio` со `storageKey` (S3-объект Opus/Ogg), `durationMs`, `offsetMs`. Связь со временем хода: `audio.currentTime = (event.t − offsetMs) / 1000` (ADR-115 §2.4, ADR-116 §2.4).

`LectureReplayPage` уже воспроизводит запись: одна шкала времени, доска и аудио ведутся синхронно. Клик по ходу в Moves panel сейчас **переключает позицию на доске**, но **аудио не перематывается**.

### 1.2 Чего хочет пользователь

> Студент кликает по ходу в Moves panel — аудиодорожка перематывается на момент, когда тренер говорил про этот ход.
>
> У некоторых ходов будет несколько таймштампов (тренер возвращался к этому ходу несколько раз) — студенту предлагается выбор.

### 1.3 Что нужно от ADR

1. Однозначный канонический идентификатор хода-в-записи (как ключ, по которому Moves panel находит таймштампы).
2. Формат и алгоритм построения индекса «ход → список упоминаний» (детерминированный).
3. Контракт клиент-сервер с явной точкой ответственности (кто что вычисляет, где источник истины).
4. UI клика и выбора между несколькими таймштампами.
5. Граничные случаи: переключение окон анализа (ADR-142), reset, ход, на котором тренер не стоял, удалённый Analysis.

### 1.4 Ограничения

- ADR-142 принцип: backend хранит только указатели; содержимое (`tree`) живёт в БД (Analysis) либо в `LectureRecording.events` (state-patch). Никакого дублирующего парсинга на backend.
- Один разработчик, минимум миграций.
- Объём `LectureRecording.events` — десятки KB на типичную лекцию, до 50 MB hard cap (ADR-113); полная итерация на клиенте — миллисекунды.

### 1.5 Что НЕ в скоупе

- Транскрипция аудио и поиск по словам тренера.
- Привязка таймштампа к моменту, когда тренер «впервые произнёс название хода» (нужна транскрипция; не делаем).
- Изменение формата записи лекции.
- Сервер-сайд предвычисление индекса (рассмотрено и отвергнуто в §9.2).
- Прокрутка таймлайна с маркерами всех упоминаний (Phase 2 — chip-overlays на progress bar плеера).
- UI редактирования / удаления упоминания тренером (запись иммутабельна).

## 2. Решение — обзор

**Один источник истины — `LectureRecording.events`.** Backend отдаёт его как сейчас, без изменений. Клиент `LectureReplayPage` при загрузке записи один раз пробегает `events[]` и строит **индекс упоминаний** — Map `moveKey → MoveVisit[]`. Клик по ходу в Moves panel ищет в Map; перематывает `<audio>`.

**Контракт фиксируется в shared-типах** (`packages/shared/src/types/lecture-replay.ts`) — две сущности:
1. `MoveKey` — канонический идентификатор хода-в-записи (см. §3).
2. `MoveVisit` — одно «посещение» узла тренером, с временными границами (см. §4).

Плюс — функция-builder с **детерминированным** алгоритмом (§5), реализованная единожды в `packages/shared` и используемая клиентом. Тесты на синтетических фикстурах гарантируют, что у двух любых клиентов на одних и тех же `events` получится байт-в-байт идентичный индекс.

**Никакого нового REST/WS.** Никакого backend-кода. Никаких миграций.

## 3. Канонический идентификатор хода-в-записи (`MoveKey`)

### 3.1 Проблема

`globalIndex` ChessMove — стабильный сквозной индекс внутри **одного** дерева (KS-3780). Но в одной лекции дерево может пересоздаваться несколько раз:
- На каждый `reset` (легковесный сброс FEN, дерево очищается).
- На каждый `analysis-switch` (тренер сменил окно — ADR-142). После switch'а тренер начинает заливать дерево нового окна, `globalIndex` нумеруется с нуля заново.

Значит, `globalIndex=5` в одном сегменте записи и `globalIndex=5` в другом — **разные** узлы. Прямой `globalIndex` как ключ не подходит.

### 3.2 Решение: сегмент + globalIndex

**Сегмент** — отрезок записи между двумя «жирными» событиями (`reset` или `analysis-switch`). Сегменты нумеруются с нуля по порядку появления. Сегмент 0 начинается с `t=0`.

```ts
/**
 * KS-4638 / ADR-143 §3. Канонический идентификатор хода в записи
 * лекции. Уникален в пределах одного `LectureRecording`. Backend этот
 * тип не использует — он живёт только на клиенте и в shared-типах,
 * как контракт между builder'ом индекса и Moves panel'ью.
 *
 * `segment` — порядковый номер сегмента записи. Сегмент 0 начинается
 * с t=0. Инкрементируется на каждом `reset` или `analysis-switch`
 * событии. Подробнее — §5.2.
 *
 * `globalIndex` — стандартный сквозной индекс узла дерева в пределах
 * сегмента. Источник — `ChessMove.globalIndex` (KS-3780).
 *
 * Сериализуется в Map-ключ как строка `"<segment>:<globalIndex>"`
 * (см. §4.2). Это единственный канонический формат — клиенты не
 * вычисляют свои варианты, не парсят и не нормализуют по-другому.
 */
export type MoveKey = {
  segment: number;       // целое, ≥ 0
  globalIndex: number;   // целое, ≥ 0
};
```

**Почему именно (segment, globalIndex), а не UCI-путь от корня.**
- `globalIndex` уже зашит в каждый узел (KS-3780). Никакой пересчёт не нужен.
- UCI-путь стал бы лишней операцией на каждый клик: «найти все ходы от корня до этого узла, собрать массив, сериализовать».
- В Moves panel рендерится дерево из state-patch'а — узел `ChessMove` уже имеет `globalIndex`. Клик отдаёт его как есть, плюс текущий сегмент (известен по проигрываемому моменту).

**Стабильность.** Внутри одного сегмента `globalIndex` гарантируется стабильным контрактом state-patch'а (KS-3780). Между сегментами — ключ изолирован полем `segment`. Коллизий не возникает.

### 3.3 Что считать сегментом

Сегмент инкрементируется (на 1) при обработке любого из:
- `RecordedResetEvent` (тип `'reset'`);
- `RecordedAnalysisSwitchEvent` (тип `'analysis-switch'`);

в порядке появления в `events[]`. **Никакие другие события сегмент не сдвигают** (включая `move`, `state-patch`, `closed`).

Финализатор инжектит синтетический `analysis-switch` на `t=0` если первое событие — не switch (ADR-142 §6.5 / KS-A05). Это значит:
- Если лекция стартовала с пустого `LiveAnalysis` без привязки к Analysis — сегмент 0 продолжается до первого reset/switch.
- Если стартовала с привязкой — синтетический switch на `t=0` уже инкрементирует сегмент **до** старта основной записи. Конвенция: синтетический switch на `t=0` оставляет `segment=0` (не сдвигает с −1 на 0, потому что начальное значение и так 0). См. формальный алгоритм §5.2.

## 4. Формат индекса упоминаний

### 4.1 `MoveVisit` — одно посещение узла

```ts
/**
 * KS-4638 / ADR-143 §4. Одно посещение узла тренером — отрезок времени,
 * в течение которого `currentGlobalIndex` указывал на этот узел.
 *
 * `enteredAtMs` — момент входа на узел (мс от `Lecture.startedAt`).
 * Это `t` события, на котором `currentGlobalIndex` стал равен
 * `MoveKey.globalIndex` (см. §5.4). Используется для seek'а аудио:
 *   audio.currentTime = (enteredAtMs − audio.offsetMs) / 1000
 * (формула из ADR-115 §2.4 / ADR-116 §2.4).
 *
 * `durationMs` — сколько мс тренер пробыл на узле до следующей смены
 * `currentGlobalIndex` (или до конца сегмента, если узел был активен
 * на момент reset/analysis-switch/closed). UI использует для подписи
 * «(пробыл 12 сек)» и для сортировки «самое содержательное
 * упоминание» (Phase 2).
 *
 * `endedAtMs` — производное `enteredAtMs + durationMs`; вынесено
 * отдельным полем, чтобы клиенты не считали его по-разному (один —
 * inclusive границу, другой — exclusive). Это формально дублирующее
 * поле; builder обязан проставлять оба и гарантировать
 * `endedAtMs == enteredAtMs + durationMs` (см. §5.5).
 */
export type MoveVisit = {
  enteredAtMs: number;   // целое, ≥ 0
  endedAtMs: number;     // целое, ≥ enteredAtMs
  durationMs: number;    // целое, = endedAtMs − enteredAtMs, ≥ 0
};
```

### 4.2 `MoveTimestampIndex` — карта посещений

```ts
/**
 * KS-4638 / ADR-143 §4. Полный индекс упоминаний всех узлов записи.
 *
 * Ключ — сериализованный `MoveKey` в формате `"<segment>:<globalIndex>"`.
 * Десятичные числа, без ведущих нулей, без пробелов. Единственный
 * канонический формат сериализации (см. функцию `serializeMoveKey`
 * в §5.7); все клиенты обязаны использовать её.
 *
 * Значение — массив `MoveVisit[]`, упорядоченный по `enteredAtMs`
 * возрастанию. Пустой массив `[]` в индексе НЕ хранится — отсутствие
 * ключа означает «ноль упоминаний» (см. §6.3).
 *
 * `segmentBoundaries` — для Moves panel'и: сопоставление номер сегмента
 * → метаинформация. Нужен, чтобы UI знал «как назвать сегмент в выбор-
 * popover'е» (например, «Окно: Каро-Канн» из `analysis-switch.title`)
 * и чтобы алгоритм поиска «активного сегмента в момент времени t»
 * работал O(log N).
 */
export type SegmentBoundary = {
  segment: number;                      // совпадает с индексом в массиве
  startedAtMs: number;                  // включительно; для сегмента 0 = 0
  endedAtMs: number | null;             // exclusive; null = до конца записи
  /** Метка для UI:
   *   - для сегмента, начатого `analysis-switch` — payload.title;
   *   - для сегмента, начатого `reset` — null (UI рисует как «—» или «после сброса»);
   *   - для нулевого сегмента, не начатого со switch — null. */
  title: string | null;
};

export type MoveTimestampIndex = {
  /** Map<serializeMoveKey(MoveKey), MoveVisit[]> с инвариантом
   *  «массив непуст и отсортирован по enteredAtMs». */
  visits: ReadonlyMap<string, ReadonlyArray<MoveVisit>>;
  /** Хронологический список сегментов записи. Индекс массива =
   *  `segment`. Используется UI для подписей и для поиска
   *  segment-of-time. */
  segmentBoundaries: ReadonlyArray<SegmentBoundary>;
  /** Полная длительность записи (мс) — нужна для расчёта `endedAtMs`
   *  у последнего активного посещения и последнего сегмента. Берётся
   *  из `LectureRecording.durationMs`. */
  totalDurationMs: number;
};
```

### 4.3 Что НЕ хранится в индексе

- Полное дерево (оно в `events[]`).
- Текст, FEN, UCI узла (Moves panel и так умеет вывести любую информацию о ходе через `ChessMove`).
- Audio offset (это атрибут `LectureAudio`, индекс времени-независим от него; конвертация — на стороне плеера).

## 5. Алгоритм построения индекса

### 5.1 Где живёт алгоритм

Чистая функция в `packages/shared/src/utils/lecture-replay/buildMoveTimestampIndex.ts`:

```ts
function buildMoveTimestampIndex(
  events: ReadonlyArray<RecordedEvent>,
  totalDurationMs: number,
): MoveTimestampIndex;
```

Без зависимостей от React, DOM, fetch. Покрыта unit-тестами на синтетических фикстурах из §10. Используется `LectureReplayPage` один раз при загрузке записи; результат держится в `useMemo`.

### 5.2 Состояние builder'а

Перед циклом:
```
state = {
  segment: 0,                          // текущий сегмент
  currentGlobalIndex: null,            // на каком узле «стоит» тренер
  visitStartedAtMs: null,              // когда зашёл в текущий узел
  visits: Map<string, MoveVisit[]>(),
  segmentBoundaries: [{                // нулевая запись для segment 0
    segment: 0, startedAtMs: 0,
    endedAtMs: null, title: null
  }],
}
```

### 5.3 Закрытие сегмента / посещения

Хелпер `closeVisit(state, atMs)`: если `currentGlobalIndex != null` и `visitStartedAtMs != null` —
- сериализовать ключ `serializeMoveKey({segment: state.segment, globalIndex: state.currentGlobalIndex})`;
- сформировать `MoveVisit { enteredAtMs: state.visitStartedAtMs, endedAtMs: atMs, durationMs: atMs − state.visitStartedAtMs }`;
- push в `state.visits.get(key) ?? new Array()`;
- `state.currentGlobalIndex = null`, `state.visitStartedAtMs = null`.

Хелпер `closeSegment(state, atMs, openNextWithTitle)`:
- `closeVisit(state, atMs)`;
- `state.segmentBoundaries[state.segment].endedAtMs = atMs`;
- `state.segment += 1`;
- `state.segmentBoundaries.push({segment, startedAtMs: atMs, endedAtMs: null, title: openNextWithTitle})`.

### 5.4 Обработка каждого события (по `event.type`)

| `event.type` | Действие |
| --- | --- |
| `'analysis-switch'` | Если `event.t === 0 && state.segment === 0 && state.currentGlobalIndex === null && state.visits.size === 0`: «нулевой синтетический switch» — **не закрывает сегмент**, только обновляет `segmentBoundaries[0].title = event.payload.title`. Иначе: `closeSegment(state, event.t, event.payload.title)`. |
| `'reset'` | `closeSegment(state, event.t, null)`. Title нового сегмента — `null` (сброс без явного заголовка). |
| `'state-patch'` | Если `event.payload.currentGlobalIndex === undefined` — событие игнорируется для индекса (тренер обновил дерево, но не сменил указатель). Иначе: если `event.payload.currentGlobalIndex !== state.currentGlobalIndex`: `closeVisit(state, event.t)`; `state.currentGlobalIndex = event.payload.currentGlobalIndex`; `state.visitStartedAtMs = event.t`. |
| `'move'` | **Не меняет** ни сегмент, ни текущий узел в индексе. Move-событие добавляет ход в дерево; реально на новый узел тренер встанет следующим `state-patch`'ем (с обновлённым `currentGlobalIndex`). См. §5.6. |
| `'closed'` | Закрывает сегмент: `closeSegment(state, event.t, null)`. (Открытый «после» сегмент не создаётся, потому что записи больше нет; нюанс — последний boundary с `endedAtMs = event.t` и `startedAtMs = event.t` не создаётся либо удаляется. Builder обязан очистить последний пустой boundary.) |

После итерации — финализация:
- Если `state.currentGlobalIndex != null` — `closeVisit(state, totalDurationMs)`.
- Последний `segmentBoundaries[*].endedAtMs` — `totalDurationMs`, если не закрыт.
- Если последний boundary в `segmentBoundaries` оказался пустым (`startedAtMs === endedAtMs`), удалить его (артефакт `'closed'`-обработки).
- Сортировка `visits[k]` по `enteredAtMs` — уже гарантирована порядком обхода (события в `events[]` отсортированы по `t` через RPUSH).

### 5.5 Инвариант `durationMs == endedAtMs − enteredAtMs`

В коде builder'а обязательно явное вычисление обоих полей через одну формулу. Тесты §10.x.5 проверяют для каждого выданного `MoveVisit` равенство — иначе сборка считается некорректной.

### 5.6 Почему `move` не создаёт посещение

`RecordedMoveEvent` несёт только `{uci, ply}` — без `currentGlobalIndex`. После move-события состояние дерева у тренера: «новый узел добавлен, courseur стоит на нём». Но в журнал индекс узла попадает только через следующий `state-patch` (KS-3780: state-patch присылается сразу после move-серии с обновлённым деревом и индексом). Соответственно «момент посещения» нового узла = `t` ближайшего `state-patch'а` с этим `currentGlobalIndex`, а не `t` самого move'а.

Это **корректно для UX**: разница между `t(move)` и `t(state-patch)` — миллисекунды (один тик rate-limiter'а тренера). Аудио тренера всё это время идёт; перематывать на `t(move)` или на `t(state-patch)` для слушателя неотличимо.

Если в редком случае move без последующего state-patch'а («тренер сделал ход и тут же закрыл лекцию») — узел не получит посещения и его не будет в индексе. UI покажет «упоминания не найдены» (см. §6.3).

### 5.7 Сериализация ключа

```ts
function serializeMoveKey(k: MoveKey): string {
  return `${k.segment}:${k.globalIndex}`;
}
function parseMoveKey(s: string): MoveKey {
  const [seg, idx] = s.split(':');
  return { segment: Number(seg), globalIndex: Number(idx) };
}
```

Никаких leading-zero / padding / hex / разделителей кроме `:`. Эти две функции — **единственный** канонический путь; в shared-пакете лежат рядом с типами, и builder, и Moves panel, и тесты импортируют их оттуда. Запрещено в местах использования собирать строку вручную.

## 6. Контракт клиент-сервер

### 6.1 Что отдаёт сервер

**Без изменений.** Существующие endpoint'ы:
- `GET /lectures/:id` — возвращает `LectureSummary` с полями `audio?: LectureAudioInfo` и `recordingId?` (как сейчас, ADR-115/116).
- `GET /lectures/:id/recording` — возвращает `LectureRecording` с `events`, `durationMs`, `startingFen`, `orientation`, `truncated`.

Никаких новых endpoint'ов, никаких новых полей. **Backend об индексе ничего не знает.**

### 6.2 Что вычисляет клиент

`LectureReplayPage` при загрузке:
1. Получает `recording.events` и `recording.durationMs`.
2. `const index = buildMoveTimestampIndex(events, durationMs)` — единственная точка вызова, в `useMemo([events, durationMs])`.
3. Прокидывает `index` пропом в `MovesPanel` и в `LectureReplayPlayer`.

Зрители одной и той же лекции на разных устройствах построят **байт-в-байт идентичный** индекс из идентичных `events[]` — алгоритм детерминирован (§5).

### 6.3 Где смотреть на ход в индексе

Moves panel рендерит дерево из текущего активного `state-patch` (или из `Analysis.tree` если активен `analysis-switch` без последующих state-patch'ей). Каждый узел `ChessMove` имеет `globalIndex`. Текущий сегмент известен из таймера плеера (вычисляется через `segmentBoundaries`: бинарный поиск по `startedAtMs <= currentTimeMs`).

При клике на узел:
```ts
const key = serializeMoveKey({ segment: currentSegment, globalIndex: node.globalIndex });
const visits = index.visits.get(key) ?? [];
```

- `visits.length === 0` → попап «Этот ход не обсуждался в эфире» + кнопка «Открыть позицию без перемотки звука» (доска переключается, аудио продолжает играть). См. §7.4.
- `visits.length === 1` → атомарно: `seekTo(visits[0].enteredAtMs)` + переключить доску на узел. См. §7.2.
- `visits.length > 1` → popover-выбор (§7.3).

### 6.4 Что фиксируется в shared types (одно место истины)

В `packages/shared/src/types/lecture-replay.ts`:
- `MoveKey`, `MoveVisit`, `SegmentBoundary`, `MoveTimestampIndex` (§3, §4).
- `serializeMoveKey`, `parseMoveKey` (§5.7).
- Сигнатура `buildMoveTimestampIndex` (см. §5.1, реализация в `packages/shared/src/utils/lecture-replay/`).

В `packages/shared/src/utils/lecture-replay/buildMoveTimestampIndex.spec.ts` — фикстуры из §10. Эти тесты — формальная спецификация. Любой их прогон должен проходить; рассинхрон builder'а и тестов — критическая регрессия.

### 6.5 Что НЕ в shared types

- React-компоненты (`MovesPanel`, popover-выбор) — во фронте.
- Контроллеры аудио (`<audio>`-ref, `seekTo`) — во фронте.
- Стилизация — в проекте слоя layout.

### 6.6 Версионирование контракта

Поля типов `MoveKey/MoveVisit/MoveTimestampIndex` фиксированы с момента согласования этого ADR. Любое добавление поля — minor-расширение (опциональные поля); удаление/переименование — breaking, потребует ADR-обновления + переходного периода. Поскольку индекс не сериализуется в сеть / БД (живёт только в памяти клиента), breaking-изменение требует только одновременного обновления builder'а и потребителей. Backend остаётся вне контракта.

## 7. UI

### 7.1 Где появляется поведение

`MovesPanel` в `LectureReplayPage` — каждый узел дерева получает обработчик клика (или контекст-меню). Триггер — клик левой кнопкой по узлу (как сейчас «перейти к позиции»), плюс модифицированное поведение: одновременно с переключением позиции — seek аудио.

### 7.2 Один таймштамп — сразу seek

```
[узел e4] ── клик ──┐
                    ├─► board.goto(node)
                    └─► audio.currentTime = (visit.enteredAtMs − offsetMs) / 1000
                        + если audio.paused: audio.play()  (опционально, см. §7.5)
```

Текущий момент в плеере отображается на progress bar'е, при seek'е переходит на новую отметку. Никаких confirm'ов, никаких всплывающих окон.

### 7.3 Несколько таймштампов — popover-выбор

Popover (или sliding sheet на mobile) рядом с узлом:

```
┌─ Тренер возвращался к этому ходу ────────────┐
│   ⊙ 02:14   (пробыл 12 сек)                  │
│   ⊙ 08:31   (пробыл 04 сек)                  │
│   ⊙ 21:07   (пробыл 47 сек)  ← самое долгое  │
├──────────────────────────────────────────────┤
│  [Перейти к позиции без перемотки звука]      │
└──────────────────────────────────────────────┘
```

- Строки отсортированы хронологически (по `enteredAtMs` возрастанию).
- Метка «самое долгое» — у строки с максимальным `durationMs` (если >1 строки — у одной, выбранной стабильной сортировкой по `enteredAtMs`). Подсказка для студента, какое упоминание содержательнее.
- Клик по строке — `audio.currentTime = (visit.enteredAtMs − offsetMs) / 1000` + переключение позиции на доске.
- Кнопка снизу — переход к позиции без seek'а аудио (полезно, если студент сейчас слушает другую часть).

Hover на узел в Moves panel показывает кол-во упоминаний бейджем `× N` рядом с ходом (если N > 1).

### 7.4 Ноль таймштампов — деградация

UI-варианты:
- (a) **Узел кликабелен** — переключает доску на позицию, но toast «Тренер не останавливался на этом ходе в эфире». Aудио не трогаем.
- (b) Узел кликабелен, но bytype-меньше. Без toast'а — просто doska меняется, как сейчас (поведение до KS-4638). Это самое тихое поведение.

**Решение:** вариант (b). Студент не должен получать «ошибки» — он просто получает текущее поведение Moves panel'и. Toast возникнет только если он сделал что-то особенное (например, открыл попап через контекст-меню).

Узлы с `visits.length === 0` помечаются в Moves panel неярким значком `·` (без бейджа), чтобы информированный студент видел разницу. Это опционально и относится к слою layout.

### 7.5 Авто-play при seek'е

При seek'е аудио — оставаться в текущем состоянии play/pause. **Не запускать автоматически**, если аудио на паузе: студент мог сознательно поставить на паузу. Запуск воспроизведения — отдельное действие play-кнопкой.

Исключение: если плеер ещё не начинал играть в этой сессии (т.е. `audio.played.length === 0`), seek + автозапуск допустимы — стандартная UX логика media-плееров. Реализация на стороне `LectureReplayPlayer`.

### 7.6 Доступность

- Узел Moves panel'и должен принимать `Enter` / `Space` (как кнопка); при `Shift+Enter` — открыть popover-выбор даже если упоминание одно (для clavier-навигации).
- Popover закрывается по `Esc`.
- Aria-label на узле: `«ход e4, упоминаний 3, открыть варианты»`.

### 7.7 Mobile

Popover вместо центрированного — sliding sheet снизу (по конвенции ADR-119 §6.6). Тач-цели — минимум 44×44 px по правилам мобильного UI-кита проекта.

## 8. Граничные случаи

### 8.1 Переключение окон анализа (ADR-142)

Сценарий: тренер за лекцию переключился A1 → A2 → A1 (обратно).
- Сегмент 0: окно A1.
- На `analysis-switch (A2)`: closeSegment → сегмент 1 (title=«A2»).
- На `analysis-switch (A1)`: closeSegment → сегмент 2 (title=«A1»).

В индексе ключи `0:5` (e4 в первом посещении A1) и `2:5` (e4 во втором посещении A1) — **разные**, даже если узел в дереве «тот же». UI Moves panel'и отображает дерево **текущего сегмента**; клик по e4 в момент replay'я внутри сегмента 2 даст ключ `2:5` → возвращаются только посещения внутри сегмента 2.

**Это сознательное поведение.** Если студент хочет услышать e4 из первого захода — он должен сначала перемотать плеер в сегмент 0 (UI: переключатель сегментов в timeline'е, §11 Phase 2), потом кликнуть e4. Альтернатива (объединять глобально по «семантически тому же ходу») — отвергнута: «семантически тот же» требует сравнения дерева Analysis (а оно может быть удалено), и противоречит изоляции сегментов из §3.

### 8.2 `Reset` (легковесный сброс FEN)

`Reset` инкрементирует сегмент так же, как `analysis-switch`, но `title=null`. UI Moves panel'и в сегменте после reset'а рендерит дерево с тем `startingFen`, что пришёл в reset'е (и последующими state-patch'ами). Никаких отличий от switch'а в логике индекса.

### 8.3 Узел в дереве, на котором тренер не стоял

Тренер ввёл вариацию `1.e4 e5 2.Nf3 Nc6 3.Bc4` и сразу пошёл дальше; на 3.Bc4 не остановился, тут же убрал ход (state-patch уточнил `currentGlobalIndex` на другой узел).
- `visits.get("0:7")` для узла Bc4 вернёт `undefined` → длина 0.
- Клик по нему — поведение §7.4 (b).

### 8.4 Тренер «застрял» на узле до конца лекции

Последний `state-patch` указывает `currentGlobalIndex=42`, после него только `closed`. Тогда `closeSegment` на `closed` закроет последнее посещение с `endedAtMs = event.t` (`closed`-события). Если `closed`-нет (лекция оборвалась) — finalization в §5.4 закрывает через `totalDurationMs`. UI показывает корректную длительность.

### 8.5 Несколько одинаковых `currentGlobalIndex` в state-patch'ах подряд

`state-patch 1: currentGlobalIndex=5` → текущий узел 5, visitStartedAt=t1.
`state-patch 2: currentGlobalIndex=5` (например, тренер просто обновил аннотации) → **не закрывает посещение**, visit продолжается (§5.4 условие `!==`).

### 8.6 Длительность посещения = 0

Если два `state-patch'а` пришли в одну мс (теоретический edge): visit с `durationMs=0` валиден (инвариант §5.5 разрешает `≥ 0`). UI отображает «(0 сек)» либо скрывает duration. Это допустимое поведение, не ошибка.

### 8.7 Удалённый Analysis (ADR-142 §6.5)

Если `analysis-switch.payload.analysisId` указывает на удалённый Analysis — `GET /analyses/:id` вернёт 404. Moves panel в этом сегменте пуста / показывает «окно удалено». **Индекс это никак не задевает**: builder работает только по `events`, не по содержимому Analysis. Сегмент существует, его `title` — из `payload.title` (надгробная подпись). Клики просто некуда применить — узлов в UI нет.

### 8.8 Усечённая запись (`recording.truncated === true`)

Запись обрезана по 50 MB cap'у (ADR-113). `events[]` — префикс реальной ленты. Builder работает на префиксе как обычно; финализация добивает последнее посещение через `totalDurationMs` (это длительность префикса, не «всей» лекции — устарелое значение поправит финализатор). UI помечает запись «truncated» (как сейчас, не нужно нового).

### 8.9 Сегмент без `state-patch`

Тренер открыл новое окно (`analysis-switch`), сделал move через `move`, но `state-patch` ещё не пришёл, и тут `closed`. В индексе посещений для этого сегмента — **ноль ключей**. Сегмент в `segmentBoundaries` всё равно есть. UI с этим работает корректно (нет узлов с упоминанием — нечего перематывать).

### 8.10 Расхождение `events[]` и аудио

`offsetMs` берётся из `LectureAudio` (ADR-115/116). Это серверный параметр; индекс на него не смотрит. Если `offsetMs` некорректен (например, аудио стартовало позже лекции на 2 мин и `offsetMs` это отражает) — все таймштампы плеер сдвинет одинаково. Индекс остаётся канонически точным относительно `Lecture.startedAt`. Корректность offset'а — отдельная гарантия audio-конвейера (ADR-116 риск 3).

### 8.11 Лекция без аудио (`recording.audio === null`)

Случай, когда тренер записал ходы, но не дал микрофон или Egress упал. Индекс строится как обычно; UI Moves panel'и **не показывает** кнопку seek (нет аудио). Hover-бейдж `× N` всё равно показывается, чтобы студент видел структуру лекции; popover при множественных таймштампах открывается, но кнопки seek в нём заменены на «перейти к позиции» (тот же эффект, что в §7.4).

## 9. Альтернативы и почему отвергнуты

### 9.1 UCI-путь от корня как идентификатор хода

См. §3.2. Минусы: дополнительная вычислительная работа на каждый клик; путь чувствителен к структуре дерева (вариации могут перенумеровываться). `globalIndex` уже стабилен (KS-3780). Отвергнуто.

### 9.2 Сервер предвычисляет индекс и кладёт в БД (`LectureRecording.moveTimestampIndex`)

Pro: один запрос — один индекс, никаких пробегов на клиенте.

Contra:
- Миграция БД (новая колонка / отдельная таблица).
- Дублирование данных, которые тривиально вычислимы из `events`.
- Расхождение версий: при изменении алгоритма (§5) у старых лекций индекс окажется по старой версии, нужны бэкфилы. Источник правды размывается.
- Объём индекса для длинных лекций ≈ тот же, что `events` — экономия по сети 0.
- Противоречит принципу ADR-142 (БД — источник содержимого, всё производное — клиент).

Отвергнуто. Клиент справится за миллисекунды.

### 9.3 Сервер на лету (`GET /lectures/:id/move-timestamps`)

Pro: единая точка вычисления, нельзя ошибиться в алгоритме на клиенте.

Contra:
- Backend заводит логику парсинга `tree` (JSON-строки) и обхода — противоречит KS-3780 (backend хранит дерево как строку, не парсит).
- Лишний REST-вызов на каждую загрузку записи.
- Расхождение версии алгоритма «backend vs frontend» при follow-up'ах — типичная ловушка ADR-142.

Отвергнуто. Алгоритм лежит в shared, builder — один.

### 9.4 «Семантический» ключ (FEN после хода)

Использовать FEN после хода как ключ — тогда повторение одной и той же позиции в разных окнах/вариациях даст один ключ.

Pro: «вот эта позиция обсуждалась N раз во всей лекции».

Contra:
- Студент кликает по конкретному ходу в конкретной ветке — он ожидает упоминаний именно в **этом** контексте, не «где-то в лекции эта позиция встречалась».
- FEN-коллизии: одна и та же позиция доступна разными путями (транспозиции). Это вводит ложные срабатывания.

Отвергнуто.

### 9.5 Транскрипция аудио и индекс по словам

Pro: реальная привязка «тренер сказал e4».

Contra:
- Требует Whisper API или аналог; стоимость инфры, точность для шахматной терминологии.
- Не покрывает случай «тренер показал ход молча» (демонстрационно).

Не в скоупе KS-4638. Возможный отдельный ADR.

### 9.6 Маркеры на progress-bar плеера вместо клика по узлу

Pro: студент видит «горячие моменты» сразу.

Contra:
- Не отменяет необходимости в клике по узлу (это естественный UX).
- Может перегрузить progress-bar (десятки маркеров).

Не альтернатива — комплементарно. Phase 2.

## 10. Тестовые фикстуры (обязательная часть контракта)

Шесть синтетических фикстур, на которых `buildMoveTimestampIndex` обязан выдавать точно описанный результат. Размещаются в `packages/shared/src/utils/lecture-replay/__fixtures__/`. Покрытие — Эпик A KS-A02.

### F1. Прямая партия без вариаций

Events:
- `t=0,   move {uci:'e2e4', ply:1}`
- `t=200, state-patch {currentGlobalIndex:0}`
- `t=5000, move {uci:'e7e5', ply:2}`
- `t=5100, state-patch {currentGlobalIndex:1}`
- `t=12000, closed`

Ожидание: `totalDurationMs=12000`, segments=[{0, 0, 12000, null}], visits=`{"0:0":[{200,5100,4900}], "0:1":[{5100,12000,6900}]}`.

### F2. Возврат к узлу

Events: `state-patch {0}` t=100; `state-patch {1}` t=2000; `state-patch {0}` t=5000; `state-patch {2}` t=9000; `closed` t=15000.

Ожидание: `"0:0"` → 2 visits `[{100,2000,1900},{5000,9000,4000}]`; `"0:1"` → 1 visit; `"0:2"` → 1 visit до 15000.

### F3. Reset в середине

Events: `state-patch {0}` t=100; `reset {fen}` t=3000; `state-patch {0}` t=4000; `closed` t=10000.

Ожидание: segments=[{0, 0, 3000, null}, {1, 3000, 10000, null}]; `"0:0"` → 1 visit `{100,3000,2900}`; `"1:0"` → 1 visit `{4000,10000,6000}`.

### F4. Analysis-switch на t=0 (синтетический)

Events: `analysis-switch {analysisId, title:'A1'}` t=0; `state-patch {0}` t=500; `analysis-switch {A2, 'A2'}` t=10000; `state-patch {0}` t=11000; `closed` t=20000.

Ожидание: segments=[{0, 0, 10000, 'A1'}, {1, 10000, 20000, 'A2'}] (синтетический не сдвинул, только проставил title); `"0:0"` → 1 visit; `"1:0"` → 1 visit.

### F5. State-patch без `currentGlobalIndex`

Events: `state-patch {0}` t=100; `state-patch {undefined currentGlobalIndex, новый tree}` t=2000; `state-patch {1}` t=5000; `closed` t=10000.

Ожидание: `"0:0"` → 1 visit `{100,5000,4900}` (промежуточный без currentGlobalIndex не закрывает); `"0:1"` → 1 visit `{5000,10000,5000}`.

### F6. Move без последующего state-patch'а

Events: `state-patch {3}` t=1000; `move e2e4 ply 5` t=8000; `closed` t=10000.

Ожидание: `"0:3"` → 1 visit `{1000,10000,9000}` (move'а нет, переход не состоялся). Никаких других ключей.

### F7. Узел никогда не был активен

Events: `state-patch {0}` t=100; `closed` t=5000.

Ожидание: `"0:0"` → 1 visit `{100,5000,4900}`. Все остальные ключи отсутствуют (узлы 1, 2, … введены, но не посещены). Клик по ним в UI → §7.4 (b).

### F8. `Closed` без предшествующего активного узла

Events: `closed` t=3000.

Ожидание: `visits.size === 0`; `segmentBoundaries = [{0, 0, 3000, null}]`; `totalDurationMs=3000`.

## 12. Риски и подводные камни

1. **Алгоритм builder'а в shared разойдётся с фактическим форматом events.** Контр-меры: фикстуры §10 — формальная спецификация; unit-тесты в shared падают, если builder отклоняется. CI блокирует merge при падении.

2. **Объём `events[]` у длинных лекций.** 50 MB hard cap (ADR-113) — это 100k+ событий. Линейный пробег за O(N) — десятки мс на современном железе. `useMemo` спасает от повторных пересчётов. Если в проде увидим тормоза — Phase 2: кэширование `index` в IndexedDB по `recording.id`.

3. **Согласованность ключа.** Где-то на фронте кто-то соберёт строку `"0:0"` вручную, а не через `serializeMoveKey`. Контр-меры: ESLint-правило `no-restricted-syntax` на инлайн-строки `\d+:\d+` (опц.); код-ревью; импорт-only из shared.

4. **Студент кликает по ходу, но плеер ещё не дошёл до этого сегмента.** Например, плеер в сегменте 0, студент уже видит дерево сегмента 1 (потому что Moves panel пере-рендерил при `state-patch`). `currentSegment` будет 0, ключ соберётся `"0:N"`, который, скорее всего, отсутствует → визуально «упоминаний нет». **Решение:** `MovesPanel` рендерит дерево **активного сегмента в момент `currentTimeMs`**, не «последнего из events». То есть Moves panel слушает не «весь поток state-patch'ей», а только тот, что относится к текущему `currentSegment`. Это поведение уже частично реализовано (rebuild дерева при `analysis-switch` событии в replay) — нужно убедиться, что и при `reset` Moves panel пере-рендерится из дерева сегмента.

5. **Auto-play после seek'а.** На некоторых браузерах (Safari iOS) после программного `audio.currentTime = X` без user-gesture браузер ставит на паузу. UX-нюанс, не блокер. Решение: первый клик на узел = user-gesture, дальше всё работает.

6. **Длительный pause на одном узле сильно искажает «самое долгое».** Тренер мог отойти на 5 минут, currentGlobalIndex не менялся. Это выглядит как «самое содержательное упоминание». Реальной проблемы нет — студент кликнет, увидит «(пробыл 5 мин)» и сам решит. Метка «самое долгое» — подсказка, не категоричный ярлык.

7. **Алгоритм неустойчив к нарушению порядка events.** Builder исходит из того, что `events[]` отсортирован по `t`. Это гарантировано Redis RPUSH (ADR-142 §6.10). На случай поломки — добавить assertion в builder'е: `if (event.t < prevT) throw new Error('events out of order')`. Подстрахуем регресс.

8. **`currentGlobalIndex` ссылается на узел, отсутствующий в дереве.** Теоретический edge: рассинхрон state-patch'ей. Builder этого не различает (ему нужен только индекс как ключ); UI Moves panel'и не найдёт узел и не сможет визуально отметить упоминание. Реальной проблемы нет: упоминание есть в индексе, но «безымянное»; popover показывает только мс — этого достаточно.

9. **Тренер быстро кликает Moves panel в эфире.** Это создаёт серию `state-patch` событий с разными `currentGlobalIndex`. Каждый клик — потенциальное «посещение» с `durationMs ≈ 100мс`. Индекс распухает, popover'ы шумят. Митигация: фильтр в UI «показывать только visits с `durationMs >= 500мс`» (опц., Phase 2). Backend ничего не фильтрует — индекс остаётся полный.

10. **Изменение алгоритма (§5) в будущем.** Если builder обновится, у студентов с открытыми вкладками будет старый индекс до перезагрузки страницы. Это приемлемо (не критическое расхождение). Долгоживущий кеш в IndexedDB (Phase 2) — версионировать ключ через `algorithmVersion` в shared.

## 13. Связь с соседними ADR

- **ADR-115/116** — аудио-конвейер не задет. Используем существующий `audio.currentTime` и `LectureAudio.offsetMs`.
- **ADR-119** — `LectureReplayPage` уже есть; добавляется логика и компонент popover'а. Маршрут не меняется.
- **ADR-142** — `analysis-switch` корректно учитывается через `segment` в `MoveKey` (§3.3, §8.1). Если Analysis удалён — индекс работает, UI деградирует штатно (§8.7).
- **ADR-113** — `LectureRecording.events` остаётся форматом без изменений.
- **ADR-117/118** — доступ и инструменты не задеты.

## 14. Резюме для координатора

- **Принцип:** `LectureRecording.events` — источник истины; клиент один раз строит детерминированный индекс «ход → визиты»; никаких новых REST/WS/миграций.
- **Контракт:** в shared-пакете — четыре типа (`MoveKey`, `MoveVisit`, `SegmentBoundary`, `MoveTimestampIndex`), два хелпера (`serializeMoveKey`, `parseMoveKey`), одна функция `buildMoveTimestampIndex`. Поведение зафиксировано фикстурами §10 (восемь штук) — формальная спецификация.
- **Идентификатор хода:** `(segment, globalIndex)`. Сегмент инкрементируется на `reset` и `analysis-switch`. `globalIndex` — стабильный сквозной индекс узла (KS-3780).
- **UI:** 0 visits → как сейчас; 1 visit → атомарный seek+goto; >1 visits → popover с выбором по mm:ss и duration.
- **Объём работ:** ≈ 1 день shared + 2 дня frontend + 1 день layout + 1 день QA. Один эпик KS-4638, 5-6 задач.
- **Главные риски:** (а) единственная точка истины для алгоритма — shared-builder; CI-падение на фикстурах = блок merge'а; (б) Moves panel в replay должна рендерить дерево **активного сегмента**, а не «последнего» (риск §12.4).

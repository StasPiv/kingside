# ADR-016: Archive — синхронизация PLY-лимитов между деревом дебютов и списком партий

**Дата:** 2026-04-21
**Статус:** Предложено
**Задача:** KS-1631
**Связанные:** ADR-013 (базовый архив), ADR-014 (games-by-position), ADR-015 (classical-only)

---

## Контекст

### Наблюдаемый баг (прод)

Пользователь открывает AnalysisPage с позицией после 15.Ne2 в партии испанской серии:

```
FEN: r1b1qrk1/4b1pp/p1pp1n2/1p2p1B1/4P3/1P1Q1N1P/1PP1NPP1/R2R2K1 b - - 5 15
```

- Панель `ArchiveTreePanel` (bucket=Masters) показывает «Ruy Lopez, по 1 партиям», ход `h6`, avgElo 2461.
- Клик «Смотреть 1 партий →» ведёт на `/archive/games?fen=…&sort=topElo`.
- Страница `ArchiveGamesByPositionPage` показывает бейдж `≈1 партий` (тот же `totalApprox`), **но список пуст** — «В этой позиции партий не найдено».

### Root cause

Два источника данных под одним UX покрывают **разные диапазоны ply**:

| Источник | Код | Лимит | Используется |
| --- | --- | --- | --- |
| `position_stats` | `apps/archive-importer/src/position-indexer.ts:22` | `PLY_LIMIT = 40` | `ArchiveTreePanel` (агрегаты ходов), `totalApprox` в бейдже списка |
| `archive_game_positions` | `apps/archive-importer/src/position-row-builder.ts:17` | `POSITION_PLY_LIMIT = 24` | `ArchiveGamesByPositionPage` (перечень партий) |

Позиция после 15.Ne2 попадает на ply = 29. `position_stats` её индексирует (29 ≤ 40) — дерево видит партию и считает `totalApprox = 1`. `archive_game_positions` её не индексирует (29 > 24) — список партий пуст.

### Почему лимиты разошлись

ADR-014 §1.3 вводил `POSITION_PLY_LIMIT = 24` с обоснованием:

> «ply ≤ 24 … покрывает 98% запросов дерева: после 20 ply позиции в 95% случаев уникальны (1 партия на позицию), а в панели `ArchiveTreePanel` пользователь видит "total < 5" и в список не переходит.»

Обоснование построено на гипотезе, что пользователь **не переходит** в список партий из миттельшпильных позиций. Наблюдаемый баг опровергает эту гипотезу:

1. Пользователь, анализирующий реальную дебютную серию, естественно доходит до 12–18 полных ходов (ply 24..36).
2. Дерево продолжает показывать данные — значит, продолжает приглашать к клику («Смотреть N партий»).
3. Даже единичная партия на миттельшпильной позиции — ценная информация (найти, как играли мастера дальше), не менее ценная, чем агрегат исходов.

Открытый вопрос §4 ADR-014 («если `archive_games_list_position_not_indexed_total` > 0.1% — поднимаем до 30») уже предвидел эту ситуацию, но метрика не была внедрена и триггер не сработал заранее — проблему поймали по пользовательскому отчёту.

## Инвариант (контракт tree ↔ list)

**Invariant #1 — tree/list consistency:**
Для любой пары `(position_key, bucket)` и любого набора пользовательских фильтров `F`:

> Если `ArchiveTreePanel` показал `totalApprox(position, bucket) = N ≥ 1` — клик «Смотреть N партий» приводит на страницу, где список **либо содержит ≥ 1 партии**, **либо честно сообщает «позиция за пределами индекса»** (без бейджа `≈N партий`).

Тривиальное следствие: нельзя одновременно показывать `totalApprox ≥ 1` и текст «партий не найдено» без явного пояснения причины.

**Invariant #2 — ply-lock:**

> `POSITION_PLY_LIMIT(archive_game_positions) == PLY_LIMIT(position_stats)`.

Оба лимита связаны единой константой (экспортируется из одного модуля). Любое изменение — в обоих местах, с обязательным backfill до деплоя UI-изменений.

**Invariant #3 — honest badge:**

> Бейдж `≈N партий` на странице `/archive/games` показывается **только если сервер уверен**, что ≥ 1 партию он может выдать. Если `totalApprox > 0` но `archive_game_positions` пуст для позиции — сервер возвращает `totalApprox: null` и UI показывает fallback-сообщение.

Для проверки инварианта — новая метрика `archive_tree_list_mismatch_total{bucket}`: инкремент на каждый ответ `games/by-position` с `items.length === 0 && totalApprox > 0`. Алёрт: любое значение > 0 за 5 минут.

## Рассмотренные варианты

### (A) Поднять `POSITION_PLY_LIMIT` до 40

**Pro:**
- Полная симметрия лимитов — инвариант `ply-lock` выполняется конструктивно.
- Никаких on-demand вычислений, никаких дополнительных путей в коде.
- UX одинаков от дебюта до ранних миттельшпилей — пользовательских «чёрных дыр» нет.
- Консистентен с архитектурной ставкой ADR-014 §1.4: при Phase B включаются hash-партиции, которые одинаково хорошо работают на любом PLY-лимите.

**Contra:**
- `archive_game_positions` вырастает в ~1.67× (см. §«Оценка объёма»).
- Backfill для существующих TWIC-партий (~250k сегодня, план — до 5M) нужно прогнать до включения ссылки «Смотреть N партий» в UI.

### (B) Опустить `PLY_LIMIT` в `position_stats` до 24

**Pro:**
- Уменьшает объём `position_stats` (~40% экономии строк).
- Backfill не нужен (сужение домена).

**Contra:**
- Дерево обрезается после 12-го полного хода — весь миттельшпиль пропадает.
- В большинстве дебютных систем (испанская, сицилианская Найдорф, французская) теоретические ветки идут до 15–20 полных ходов. Потеря данных в этом диапазоне ломает главный UX-сценарий дебютной подготовки.
- Противоречит планам ADR-013 §10 — там архив растёт и углубляется.
- Пользователь, открывший позицию после 14.h3 в испанской (ply=27), вообще не увидит дерева. Это регресс, а не исправление.

**Отвергнуто** по причине несоразмерного ухудшения UX.

### (C) UI-скрытие ссылки «Смотреть N партий» на ply > 24

**Pro:**
- Самое дешёвое решение — только фронт.
- Никаких миграций.

**Contra:**
- Симптоматическое: оставляет пользователя без возможности увидеть партии в миттельшпиле, хотя данные технически доступны для индексации.
- Инвариант #1 **не** восстановлен — бейдж `totalApprox=1` в дереве остаётся обещанием, на которое теперь нельзя ответить. Пользователь видит «1 партия» без способа её посмотреть — это хуже, чем сейчас.
- Не совместим с будущими задачами маркетинга (SEO-страницы `/archive/games?fen=…` для миттельшпильных позиций мастеров).

**Отвергнуто** как лечение симптома, а не причины.

### (D) Fallback на сканирование `archive_games` (PGN)

**Идея:** при `archive_game_positions` пустом — сканируем `archive_games`, парсим `pgn`/`moves` каждой партии, ищем совпадение позиции.

**Contra:**
- Нет дешёвого способа сузить кандидатов. `archive_games` не индексирован по позициям (если бы был — это и был бы `archive_game_positions`).
- Полный скан на 250k партий с PGN-парсингом: ~20–40 секунд (замер по существующему парсеру `parseGame` в `archive-importer`). На Phase B (5M) — десятки минут. Неприемлемо для online-запроса.
- Попытка сузить через «партии, которые индексированы до ply 24» тоже бесполезна: чтобы узнать, какие game_id были на ply 24, снова нужен обратный индекс.
- Кэширование не спасает — пользовательские позиции в миттельшпиле уникальны, кэш-хит будет близок к нулю.

**Отвергнуто** по стоимости.

### (E) Гибрид: БД c PL=24, lazy-indexing по требованию

**Идея:** хранить в БД PL=24, при запросе ply > 24 — on-demand построить строки для недостающих ply, закэшировать в `archive_game_positions`.

**Pro:**
- Экономит объём до момента первого запроса на «глубокую» позицию.

**Contra:**
- Проблема та же, что у (D): чтобы lazy-индексировать — нужно знать, какие партии-кандидаты есть. Без полного скана или сохранённого обратного индекса это не работает.
- Первый запрос на миттельшпильную позицию становится медленным (секунды вместо миллисекунд) — UX ухудшается именно там, где мы пытаемся улучшить.
- Добавляет вторую семантику записи в `archive_game_positions` (асинхронный воркер при импорте + синхронная ленивая запись на чтении). Конкуренция, race-conditions на уникальных ключах.
- Долгоживущий технический долг: lazy-путь нужно тестировать отдельно, метрики, quota.

**Отвергнуто** как оптимизация, цена которой (сложность) превышает выгоду (объём).

## Решение: **вариант (A) — поднять `POSITION_PLY_LIMIT` до 40**

Обоснование:

1. Это единственный вариант, конструктивно обеспечивающий инвариант `ply-lock`. Все остальные варианты либо нарушают его, либо обходят — с расплатой в UX или сложности.
2. Стоимость — линейный рост одной таблицы в 1.67× — укладывается в пределы, предусмотренные ADR-014 §1.3 для Phase A/B. До Phase C (>10M партий, переход в ClickHouse) выбранный лимит не создаёт операционных проблем.
3. Обоснование §1.3 ADR-014 «список нужен только для дебютов» признаётся устаревшим: UX показывает обратное (пользователи уходят в миттельшпиль, панель Database показывает данные на ply 28–35).
4. Backfill уже реализован инфраструктурно (`apps/archive-importer/src/backfill.ts`, KS-1611) — нужна лишь модификация режима, чтобы он дополнял уже существующие партии недостающими ply 25..40 (см. §«План миграции»).

### Уточнения

- **Единая константа.** Чтобы инвариант `ply-lock` не разошёлся повторно — выносим лимит в `packages/shared/src/constants/archive.ts`:

  ```ts
  /** Максимальный ply, индексируемый в position_stats и archive_game_positions. */
  export const ARCHIVE_PLY_LIMIT = 40;
  ```

  И `position-indexer.ts`, и `position-row-builder.ts` импортируют одну константу. Тесты проверяют: `PLY_LIMIT === POSITION_PLY_LIMIT === ARCHIVE_PLY_LIMIT`.

- **Fail-closed UX-guard.** На API-уровне в `GET /api/archive/games/by-position`, если `items.length === 0 && totalApprox > 0` — логируем warn, инкрементируем `archive_tree_list_mismatch_total`, и возвращаем `totalApprox: null`. Это защита от возможных рассинхронов во время миграции и в будущем.

- **Не трогаем верхнюю границу.** Рассматривался вариант PL=60/80 (покрыть весь миттельшпиль). Отвергнут: это ×3..×3.5 объёма без ясной UX-выгоды — после 20 полных ходов позиции почти всегда уникальны (1 партия), и ценность списка для таких позиций сомнительна (хотя и не нулевая). PL=40 — компромисс, совпадающий с уже выбранным `position_stats.PLY_LIMIT`.

- **Будущее уточнение.** Если метрика `archive_tree_list_mismatch_total` после стабилизации всё равно будет > 0 на ply ≈ 40 (хит по границе) — рассматриваем PL=60 в следующем ADR с соответствующей оценкой объёма.

## Оценка объёма

### Базовая модель (из ADR-014 §1.3)

Средняя TWIC-партия после фильтра classical-only (ADR-015) — ~80 полуходов. Из них индексируется:
- При PL=24: `min(24, plyCount) ≈ 24` уникальных строк на партию (транспозиции редки, <5%).
- При PL=40: `min(40, plyCount) ≈ 40` уникальных строк на партию; короткие партии (< 40 ply) индексируются полностью.

Коэффициент роста при переходе PL=24 → PL=40: **~1.67×** (верхняя оценка; реальный рост чуть ниже из-за партий < 40 ply).

Размер одной строки `archive_game_positions` (по §1.2 ADR-014, heap + оба B-tree индекса, включая tuple header и fillfactor):
- **tuple heap** ≈ 80 байт (16 positionKey + 8 bucket + 16 gameId + 2 ply + 8 moveUci + 1 side + 8 playedAt + 2 avgElo + 1 result + служебные)
- **оба индекса** ≈ 60 байт дополнительно (без payload duplication)
- **итого ≈ 140 байт/строка** округлённо (~170 МБ на 1M строк с overhead)

### Таблица объёмов

| Сценарий | Партии (classical) | Rows PL=24 | Rows PL=40 | Size PL=40 (table+2idx) |
| --- | --- | --- | --- | --- |
| MVP TWIC (сейчас) | 250k | ~6M | ~10M | ~1.4 GB |
| Year 3 TWIC | 750k | ~18M | ~30M | ~4.2 GB |
| Phase B | 5M | ~120M | ~200M | ~28 GB |
| Phase C | 10M | ~240M | ~400M | ~56 GB (PG) / ~8 GB (CH) |
| Phase D | 50M | ~1.2B | ~2B | ~280 GB (PG) / ~40 GB (CH) |

**Диспропорция с ADR-014 §1.3:** в ADR-014 размер оценивался в 85 байт/строку (без учёта indexes tuple-pointer'ов и WAL/bloat overhead). Здесь пересчитано реалистичнее (~140 байт/строка, включая два вторичных индекса и bloat 20%). Это уточнение применимо и к PL=24 — фактический размер `archive_game_positions` на Phase B при PL=24 — **~17 GB** (не 10 GB, как в ADR-014), при PL=40 — **~28 GB**.

### Операционные порог и

- **До Phase B (≤1M партий, ~8 GB):** без партиционирования, один B-tree hot-part в buffer cache (~4 GB RAM для PG) — всё работает.
- **Phase B (5M, ~28 GB):** включаем `PARTITION BY HASH (position_key)` на 32 партиции (как в ADR-014 §1.4). Partition pruning на запросе → работает с одной партицией ~900 MB.
- **Phase C (10M, ~56 GB):** переход в ClickHouse (ADR-014 §1.4). При PL=40 размер ~8 GB — комфортно.
- **Phase D (50M):** ClickHouse обязателен. PG становится не target-БД для этого пути.

**Вывод:** PL=40 укладывается во все фазы без изменения архитектурной стратегии ADR-013/014. Точки перехода между фазами сдвигаются незначительно (Phase B наступит на ~30% меньшем объёме партий, чем прогнозировалось в ADR-014). Это не критично — триггер перехода по ADR-013 §10 основан на метрике `archive_query_duration_p95`, а не на номинальном количестве строк.

### Критерий инварианта #2 применительно к объёму

> Выбранный PL=40 даёт Phase A/B размер ≤ 30 GB — зона комфорта PG (buffer cache 4–8 GB RAM, single-box). Триггер Phase C — переход в ClickHouse — остаётся по метрике latency, а не по раздуванию таблицы.

## План миграции

### Предварительное состояние

- Production БД: `archive_game_positions` содержит строки для ply 0..24, ~6M строк (MVP TWIC).
- `position_stats` содержит агрегаты для ply 0..40 — остаётся без изменений.
- Воркер `apps/archive-importer` пишет ply 0..24 в `archive_game_positions` при импорте новых TWIC-issue.
- Backfill-скрипт `apps/archive-importer/src/backfill.ts` существует (KS-1611), но в текущем виде **пропускает партии, уже присутствующие в `archive_game_positions`** (§«backfill.ts: SELECT DISTINCT … WHERE game_id = ANY(…)»).

### Этапы

**Этап 1. Код.**
  - Вынести константу `ARCHIVE_PLY_LIMIT = 40` в `packages/shared/src/constants/archive.ts`.
  - `apps/archive-importer/src/position-indexer.ts`: заменить локальный `PLY_LIMIT` на импорт `ARCHIVE_PLY_LIMIT` (значение не меняется — 40).
  - `apps/archive-importer/src/position-row-builder.ts`: заменить `POSITION_PLY_LIMIT = 24` на импорт `ARCHIVE_PLY_LIMIT` (значение меняется на 40).
  - Обновить тесты `position-row-builder.test.ts` (ожидаемое `ply ≤ 40`).
  - Удалить дублирующее значение лимита в других местах (grep `24|40` по `apps/archive-importer`, `apps/api/src/archive`).

  Деплой шага 1 без backfill: воркер начинает писать ply 0..40 для **новых** TWIC-issue. Существующие партии в БД остаются с ply 0..24 до backfill.

**Этап 2. Backfill-режим «extend».**
  - Добавить в `apps/archive-importer/src/backfill.ts` режим `--mode=extend` (либо новый скрипт `extend-ply.ts`), который:
    1. Читает `archive_games` keyset'ом по `id ASC` батчами по 2000.
    2. Для каждой партии вызывает `buildPositionRowsForGame` (уже обновлён, вернёт ply 0..40).
    3. Записывает через `ArchivePositionWriter` (COPY → ON CONFLICT DO NOTHING). Существующие ply 0..24 будут no-op по PK `(position_key, bucket, game_id)`, новые ply 25..40 — добавятся.
    4. Прогресс каждую итерацию, возможность resume.
  - **Не вызывать существующий backfill** в режиме KS-1611 — его логика фильтрует уже-существующих `game_id`, поэтому он пропустит все партии и ничего не добавит.

  Альтернатива: добавить параметр `--ignore-existing-game-ids` в текущий `backfill.ts` вместо нового режима. Решение — за backend-агентом, ADR фиксирует лишь требование.

**Этап 3. Запуск backfill на проде.**
  - В tmux-сессии/systemd-unit: `npm run archive:backfill -- --mode=extend` на production API-хосте.
  - Оценка времени (PL=40, добавляются только ply 25..40):
    - MVP (250k партий): ~40–60 минут.
    - Year 3 (750k): ~2–3 часа.
    - Phase B (5M, если к тому моменту не мигрировали): ~15–20 часов.
  - Нагрузка: воркер COPY'ит батчами по ~30k rows, PG выдерживает без заметного влияния на latency API (подтверждено по KS-1611 на первичной заливке).
  - Проверка прогресса: метрика `archive_games_list_position_not_indexed_total` должна стремиться к 0.

**Этап 4. Проверка консистентности.**
  После завершения backfill — запустить sanity-query:

  ```sql
  -- Позиции в position_stats без записей в archive_game_positions.
  -- Ожидание: 0 после backfill. До backfill — число позиций с ply 25..40.
  SELECT COUNT(DISTINCT ps.position_key)
  FROM position_stats ps
  WHERE ps.total > 0
    AND NOT EXISTS (
      SELECT 1 FROM archive_game_positions agp
      WHERE agp.position_key = ps.position_key
        AND agp.bucket = ps.bucket
    );
  ```

  И второй — спот-проверка на known-bad позиции из задачи:

  ```sql
  SELECT COUNT(*) FROM archive_game_positions
  WHERE position_key = '<hex из FEN r1b1qrk1/…>'::bytea
    AND bucket = 'master';
  -- ожидание: >= 1
  ```

**Этап 5. Снятие feature-flag / фронт.**
  До завершения этапа 4 — ничего на UI менять не нужно: страница `/archive/games` уже показывает «не найдено» там, где индекс пуст. Это baseline-поведение, оно не ухудшается backfill'ом.
  После успешной проверки §4:
    - Убрать условные guards в UI (если были от варианта C).
    - Добавить fail-closed guard на API (см. §«Уточнения»).
    - Включить метрику-алёрт `archive_tree_list_mismatch_total > 0`.

**Этап 6. Мониторинг после релиза.**
  - Проверить на проде через день: `archive_tree_list_mismatch_total` == 0, `archive_games_list_position_not_indexed_total` == 0.
  - Проверить размер таблицы `archive_game_positions` — не больше прогноза (±20%).

### Rollback

- Если backfill по каким-то причинам падает или даёт неконсистентные данные — его можно прервать и повторить. ON CONFLICT DO NOTHING обеспечивает идемпотентность.
- Если решение в целом признаётся неверным (гипотетически) — константу можно откатить обратно на 24, но уже записанные ply 25..40 придётся чистить отдельным скриптом:
  ```sql
  DELETE FROM archive_game_positions WHERE ply > 24;
  ```
  После этого — VACUUM FULL на таблицу.

### Downtime

**Нет.** Все этапы — online. Импортёр и API работают параллельно с backfill.

## Задачи для координатора

По итогам этого ADR координатор создаёт (ownership — по CLAUDE.md):

1. **backend (shared):** вынести `ARCHIVE_PLY_LIMIT = 40` в `packages/shared/src/constants/archive.ts`; обновить `position-indexer.ts` и `position-row-builder.ts` на единую константу; обновить тесты.
2. **backend (archive-importer):** добавить режим `--mode=extend` (или аналог) в `backfill.ts` — без фильтра `уже существующие game_id`.
3. **backend (api):** fail-closed guard в `archive.service.ts` (ответ `games/by-position`: если `items=[]` и `totalApprox>0` → лог warn + `totalApprox: null`); метрика `archive_tree_list_mismatch_total{bucket}`.
4. **devops:** алёрт на `archive_tree_list_mismatch_total > 0` за 5 минут; дашборд с размером `archive_game_positions`.
5. **backend (ops):** запуск backfill на проде после мерджа шагов 1–2 (manual run, логирование через journalctl).
6. **qa:** проверка инвариантов на known-bad позиции из задачи (FEN после 15.Ne2); spot-check на 5–10 миттельшпильных позициях на ply ∈ [25..40]; регресс-тест `ArchiveTreePanel` + `ArchiveGamesByPositionPage`.

Нумерацию и зависимости расставит координатор.

## Подводные камни (и честное признание неопределённостей)

1. **Оценка объёма 140 байт/строку — приблизительная.** Реальный размер зависит от `fillfactor` индексов, bloat, WAL. На проде может оказаться ±30%. Если после backfill размер сильно выпадет из прогноза — пересчитать, при необходимости включить партиционирование раньше планового Phase B.

2. **Коэффициент роста 1.67× — верхняя оценка.** Реальный рост может быть 1.4–1.6×, если в корпусе много коротких партий (рапид, сдача до 30 ходов). Для classical после ADR-015 — скорее ближе к верхней границе.

3. **Backfill на проде — фоновая операция**, но при PG под нагрузкой (импорт нового TWIC, пользовательские запросы) может затянуться. Стоит запускать в часы минимальной нагрузки или через `pg_bulkload` / `statement_timeout` на уровне воркера.

4. **Проблема может повториться** — если в будущем `PLY_LIMIT` в `position_stats` будет поднят (например, до 60 для покрытия миттельшпиля при обновлении ADR-013), всё повторится. Защита — инвариант #2 (единая константа) и тест, проверяющий идентичность значений.

5. **Metric `archive_tree_list_mismatch_total` — ловит только уже-возникшие рассинхроны**, не предотвращает их. Если в будущем появится новый источник `totalApprox` (например, ClickHouse-репликация с другим лимитом) — нужно будет расширить инвариант на все источники.

6. **Не рассматривали влияние на `ArchiveTreePanel` кэш (Redis).** При smena `PLY_LIMIT` логика дерева не меняется (PL там уже 40), поэтому кэш не требует инвалидации. Но если в будущем какие-то ключи кэшируются с учётом `POSITION_PLY_LIMIT` — потребуется flush.

## Открытые вопросы

1. **Должен ли фронт показывать «позиция за пределами индекса» объяснительно?** Сейчас — просто «партий не найдено». После backfill эта ситуация (для ply ≤ 40) станет невозможной; для ply > 40 — останется. Решение — фронт в отдельной задаче, ADR фиксирует инвариант #3 (honest badge) как обязательное требование API.

2. **Нужен ли периодический audit-скрипт?** Cron раз в сутки, проверяющий инвариант консистентности (§«Этап 4»). Операционно полезен, но можно отложить до первого инцидента. Решение — devops-задача.

3. **Кэш дерева в Redis (ARCHIVE_TREE_CACHE_CHANNEL).** При тех же `position_stats` кэш не нужно инвалидировать. Проверить, что ключи кэша `arch:tree:*` не включают `POSITION_PLY_LIMIT` как параметр.

4. **Расширение до PL=60 в будущем.** Если метрика `archive_tree_list_mismatch_total` начнёт хитить на границе 40, или пользовательские отчёты появятся для ply > 40 — следующий ADR. Это не сейчас.

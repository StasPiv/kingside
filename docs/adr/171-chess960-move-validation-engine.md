# ADR 171: Движок валидации ходов для Chess960 — выбор и стоимость перехода

- **Статус:** Proposed (требует прототипа backend для подтверждения)
- **Дата:** 2026-07-31
- **Задача:** KS-5017
- **Контекст-фича:** поддержка Chess960 / Fischer Random (оценка масштаба — /tmp/chess960-scope.md)

## Контекст

Текущий движок валидации ходов — **chess.js ^1.4.0** (последняя в npm, публикация ~год назад).
Он не поддерживает Chess960:
- не грузит произвольную стартовую расстановку с корректными правами рокировки в Shredder/X-FEN
  (буквы вертикалей вместо `KQkq`);
- не умеет рокировку king-takes-rook (единственная нотация рокировки в 960);
- README/публичного `Chess960`/`variant` режима нет.

chess.js используется в проекте **очень широко**: 9 воркспейсов имеют его в зависимостях, конструкция
`new Chess(` встречается в **135 файлах**:

| Воркспейс | Файлов с `new Chess(` |
|---|---|
| apps/web | 84 |
| apps/api | 29 |
| apps/tactic-worker | 8 |
| packages/shared | 6 |
| apps/archive-service | 5 |
| apps/game-service | 1 |
| packages/maia-core | 1 |
| packages/pdf-to-lesson-yaml | 1 |

Вывод: **глобальная замена chess.js исключена** — это затронет анализ, паззлы, архив, трансляции, PDF,
maia и потянет тотальный регресс всего продукта. Рассматриваем добавление движка 960 **точечно** в
игровой путь (валидация live-партий), а не замену везде.

## Требования к движку 960

1. Загрузка произвольной стартовой позиции из FEN с рокировкой в Shredder/X-FEN.
2. Рокировка king-takes-rook (включая крайние случаи: король ходит на 1 клетку, ладья «перепрыгивает»).
3. Генерация и валидация легальных ходов, определение мата/пата/ничьей.
4. UCI на входе/выходе (проект хранит и передаёт ходы в UCI: `e2e4`).
5. TypeScript-типы.
6. Совместимая лицензия для проприетарного продукта.

## Кандидаты

### A. chessops (niklasf, экосистема lichess)
- **960:** полная. Есть `chess960` режим генерации рокировки, исправленная king-takes-rook,
  чтение FEN/UCI/SAN, вариантные правила. Реально работает в проде lichess. Актуальная версия ~0.15.x.
- **TS:** написан на TypeScript, типы первоклассные.
- **API:** функциональный/immutable (`Setup`, `Position`, `parseFen`, `makeUci`). **Сильно отличается**
  от императивного chess.js (`new Chess()`, `.move()`, `.fen()`). Требует адаптер-обёртку.
- **Лицензия:** **GPL-3.0-or-later** — сильный копилефт. 🔴 Риск: линковка в проприетарный
  backend/frontend-бандл создаёт производную работу под GPL. Юридически спорно для закрытого продукта.
- **Размер:** модульный (можно импортировать только нужное), но требует замера (bundlephobia/прототип).

### B. kokopu (yo35)
- **960:** поддерживается (документированный туториал Chess960), плюс Antichess/Horde. FEN/UCI/SAN/PGN.
  Актуальная версия 4.13.x, поддерживается активно (TypeScript ~6.x в сборке).
- **TS:** есть типы, сборка на TypeScript.
- **API:** классовый (`Position`), стиль **ближе к chess.js**, чем chessops — легче обернуть.
- **Лицензия:** **LGPL-3.0-or-later** — слабый копилефт. 🟡 Использование как библиотеки без модификации
  допустимо в закрытом продукте, но при статической сборке в бандл фронта LGPL требует обеспечить
  возможность замены библиотеки (условие выполнимо, но требует внимания). Мягче GPL.
- **Размер:** крупнее (включает полноценный PGN-парсер) — замерить, для фронта важно.

### C. Своя обработка поверх chess.js
- Патчить/форкать chess.js под 960: он внутренне завязан на стандартную расстановку и нотацию `KQkq`,
  собственная обработка рокировки king-takes-rook = переписывание ядра генерации ходов.
- **Оценка:** высокий риск ошибок в редких 960-позициях, дорогая поддержка форка, нет гарантий на
  крайние случаи рокировки. 🔴 Не рекомендуется.

### D. @jackstenglein/chess (форк chess.js)
- Форк chess.js (v2.2.x, обновляется). Даёт PGN/варианты. **Поддержка именно 960-рокировки не
  подтверждена** — по публичным данным неясно. Требует отдельной проверки, если рассматривать.

## Рекомендация

1. **Не заменять chess.js глобально.** Оставить его для всего не-960 (анализ, паззлы, архив, трансляции,
   PDF, maia) — 135 мест не трогаем, регресс не провоцируем.
2. **Ввести отдельный движок только для валидации 960-партий** в игровом пути:
   `apps/api/game.service`, `apps/game-service/game.service`, live-игра на `apps/web`. Изолировать за
   тонким адаптером с интерфейсом, похожим на используемый кусок chess.js (`move`, `fen`, `moves`,
   `isGameOver`, история), чтобы игровой код ветвился по `variant`, а не переписывался.
3. **Предпочтительный кандидат — kokopu** (LGPL мягче GPL; классовый API ближе к chess.js → дешевле
   адаптер). **chessops** технически сильнее и проверен на проде lichess, но **GPL-3.0 — блокер по
   лицензии** для закрытого продукта; использовать только если юрист подтвердит допустимость либо если
   решим открыть код.
4. **Обязателен прототип на backend** (отдельная задача, не эта): подтвердить на живых 960-позициях —
   king-takes-rook во всех крайних случаях, корректный UCI in/out, отсутствие расхождений с chess.js на
   стандартных партиях, замер размера бандла для фронта. Выбор kokopu vs chessops финализировать по
   результатам прототипа + решения по лицензии.

## Оценка стоимости перехода

- **Затрагиваемые места (только 960-путь):** ~3 модуля валидации (api, game-service, web-live) + адаптер
  в shared. НЕ 135 файлов — стандартный путь остаётся на chess.js.
- **Риск регрессии обычных партий:** низкий при изолированном адаптере (chess.js не трогаем), но требует
  регресс-QA игрового пути после введения ветки по `variant`.
- **Объём:** сам переход-адаптер — **M**. Полная фича 960 (генерация позиции, миграция БД, matchmaking,
  UI, Stockfish UCI_Chess960) — **L**, разбита в /tmp/chess960-scope.md.
- **Нужен ли прототип backend:** **да, обязательно** — до планирования остальных задач 960, т.к. выбор
  движка определяет объём адаптера и лицензионное решение.

## Дополнение (KS-5018): доработка самого chess.js под 960 — форк vs патч

Контекст: kokopu (LGPL) и chessops (GPL) отвергнуты по лицензии. Оценён вариант остаться на chess.js
(лицензия **BSD-2-Clause** — разрешительная) и доработать его под Chess960. Разбор по исходнику
установленной версии (`node_modules/chess.js/dist/esm/chess.js`, v1.4.0, 3368 строк).

### Что в chess.js захардкожено под стандартную рокировку

Рокировка вшита в **ядро движка** в ~10 связанных местах, включая внутреннее представление:

| Место (стр.) | Что захардкожено | Нужно для 960 |
|---|---|---|
| `DEFAULT_POSITION` 1294 | стандартный старт | не проблема (FEN передаётся в конструктор) |
| FEN-парсер рокировки 1866–1878 | принимает только `K/Q/k/q` | парсить Shredder-/X-FEN (буквы вертикалей ладей) |
| FEN-генератор 1913–1927 | выводит только `KQkq` | выводить X-FEN |
| `ROOKS` 1565–1573 | ладьи жёстко на a1/h1/a8/h8 | произвольные вертикали ладей |
| внутр. `_castling` (2 бита/цвет) | KSIDE/QSIDE-биты, вертикаль ладьи НЕ хранится | расширить: помнить исходные вертикали ладей |
| `_castlingKey`/Zobrist 2000–2002 | индекс из 2 бит | пересобрать hash под новое представление |
| генерация рокировки 2447–2468 | `castlingTo = king ± 2`, фикс. проверки пустоты и атак на ±1/±2/±3 | король идёт на фикс. c/g-вертикаль (дистанция любая, вплоть до 1 клетки); проверять весь путь короля И ладьи, исключая их самих |
| `_makeMove` 2600–2609 | ладья ставится на `to∓1` относительно клетки короля | телепорт ладьи на d/f, король на c/g при произвольных стартах |
| undo рокировки 2730+, 2998+ | те же фикс. смещения | симметрично |
| `_updateCastlingRights` 2122–2148 | король ищется на e1/e8, ладьи на a1/h1/a8/h8 | на нестандартной позиции эта функция **сбросит права рокировки**; вызывается каждый ход |

Отдельный нюанс — **UCI**: проект хранит/прогоняет ходы как `from+to` (`e1g1`). chess.js генерит рокировку
как ход короля на g/c. В 960 общепринятая нотация — **king-takes-rook** (`to` = вертикаль ладьи);
на позициях, где король уже на g/соседней или ладья перекрывает целевую клетку, king-to-нотация даёт
коллизию/неоднозначность. Нужно решить формат UCI рокировки и согласовать парсинг обратно.

### Форк vs патч поверх (monkey-patch/обёртка)

- **Monkey-patch/обёртка — нежизнеспособен.** Всё нужное приватно: поля `_castling`, `_board`, `_kings`,
  методы `_moves`/`_makeMove`/`_updateCastlingRights` не экспортируются (TS-`private`, `_`-конвенция,
  минификация в бандле). Патчить прототип и лезть в приватные поля — крайне хрупко, ломается на любом
  апдейте. Плюс представление рокировки (2 бита) физически не вмещает вертикаль ладьи — обёрткой не
  расширить.
- **Форк — реалистичен** (BSD-2 разрешает), но это **правка ядра**: новое представление рокировочных
  прав тянет за собой FEN in/out, генерацию ходов, make/undo, обновление прав и Zobrist-hash. Это не
  «дописать функцию», а хирургия по общему коду. Сопровождение: свой форк, ручной перенос правок при
  обновлениях upstream — риск на практике низкий (chess.js без релизов ~год, ядро заморожено). Плюс:
  у chess.js есть perft-тесты — форк можно валидировать регрессией.

### Риск регрессии обычных партий

**Высокий.** Правятся функции, общие для стандарта и 960 (генерация рокировки, `_updateCastlingRights`,
`_makeMove`/undo, FEN, hash). Ошибка затронет и обычные партии — а chess.js в проекте в **135 файлах**
(анализ, паззлы, архив, трансляции). Обязателен полный прогон perft/регресса стандартных партий на форке.

### Объём и сравнение с «вторым движком за адаптером»

| Критерий | Форк chess.js (этот путь) | Второй движок за адаптером (осн. ADR) |
|---|---|---|
| Лицензия | ✅ BSD-2 чистая | 🔴 kokopu LGPL / chessops GPL — оба отвергнуты |
| Объём разработки | **L** (правка ядра + regression-suite) | адаптер M, но приемлемого кандидата по лицензии нет |
| Риск регрессии стандарта | высокий (общий код) | низкий (chess.js не трогаем) |
| Кол-во движков | один (консистентность в 135 файлах) | два |
| Сопровождение | свой форк, ребейз (риск низкий — upstream заморожен) | обновления сторонней библиотеки |
| Прототип backend | **обязателен** | обязателен |

### Вывод и рекомендация (KS-5018)

Доработка chess.js под 960 **реалистична только как форк** (monkey-patch отпадает), объём — **L**,
риск регрессии стандартных партий — высокий, но управляем perft-регрессией chess.js.

**Поскольку kokopu и chessops отвергнуты по лицензии, форк chess.js остаётся единственным лицензионно
чистым путём** — рекомендую его. Обязателен прототип на backend ДО планирования: подтвердить
king-takes-rook во всех крайних 960-позициях, формат UCI рокировки, и прогнать perft-регрессию
стандартных партий на форке. Если прототип выявит неприемлемую сложность/нестабильность — вернуться к
вопросу лицензии (пересмотр LGPL kokopu) как запасному варианту.

## Открытые вопросы (для координатора/пользователя)

- Лицензия: приемлема ли LGPL-3.0 (kokopu) в продукте? GPL-3.0 (chessops) — почти наверняка нет для
  закрытого кода. При вето на обе — путь только форк chess.js. Нужно решение до финализации.
- Хранить стартовую позицию как индекс 0–959 или полный FEN (влияет на миграцию Game).
- 960 только в casual/бот на старте или сразу в matchmaking/турнирах (сужает объём).

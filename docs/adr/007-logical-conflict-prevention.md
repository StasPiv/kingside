# ADR-007: Предотвращение логических конфликтов при параллельной работе агентов

## Статус

Принято (2026-03-08)

## Контекст

ADR-006 и KS-199 зафиксировали, что git worktrees предотвращают файловые конфликты, а Jira-статусы — дублирование работы. Но логические конфликты (два агента несовместимо меняют API-контракт, схему БД или бизнес-логику) не покрываются ни одним из этих механизмов. Merge проходит без ошибок, но приложение ломается в runtime.

## Решение

### 1. Contract-first подход

Все изменения API начинаются с `packages/shared/src/types/api-contracts.ts`. Контракт фиксируется в main до начала работы потребителей (backend, frontend). Параллельная работа потребителей допустима только после фиксации контракта.

### 2. Зоны риска и ownership

Файлы классифицируются по уровню риска конфликтов:

- **Высокий** — `packages/shared/`, `prisma/schema.prisma`, `prisma/migrations/`: только один агент в один момент
- **Средний** — DTO, API-хуки, gateways: меняются только после обновления shared-контракта в main
- **Низкий** — изолированные компоненты/сервисы: параллельная работа безопасна

### 3. TypeScript как валидатор совместимости

`tsc --noEmit` (через `turbo run typecheck`) запускается перед каждым merge в main. Ловит: удаление полей, изменение типов, добавление обязательных полей без обновления потребителей.

### 4. Последовательность миграций

Prisma-миграции создаются строго последовательно. Параллельное создание миграций запрещено. Задачи с миграциями помечаются в Jira.

### 5. Версионирование при ломающих изменениях

При ломающем изменении API — переходный период с поддержкой обоих вариантов (V1 + текущая версия), чтобы backend и frontend мигрировали независимо.

## Последствия

### Положительные

- Логические конфликты обнаруживаются на этапе компиляции (TypeScript), а не в runtime
- Contract-first устраняет корневую причину — рассинхронизацию ожиданий между агентами
- Ownership снижает вероятность пересечений

### Отрицательные

- Дополнительная последовательность замедляет работу (контракт → потребители, а не параллельно)
- Семантические конфликты (изменение бизнес-логики) не обнаруживаются — только e2e-тесты
- Enforcement остаётся на уровне промптов и процессов, нет технических блокировок

### Компромисс

При текущем масштабе (один разработчик, 5 агентов, один сервер) процессные правила с TypeScript-валидацией — достаточный уровень защиты. Технические блокировки (CI gates, branch protection rules) можно добавить при росте команды.

# ADR-109. «Полный разбор партии»: per-move-эндпоинт с парными снимками before/after в формате position-comment

Статус: принят (KS-3713).
Дата: 2026-06-05.
Связано:
- KS-3710 (диагностика — источник решения).
- KS-3711 (backend — новый эндпоинт `POST /analyses/review/move-comment`).
- KS-3712 (frontend — миграция, расширение «интересных» ходов, починка трассировки Stockfish-WASM).
- ADR-108 (UX-эпик «Оценка позиции от AI», `position-comment` контракт).
- ADR-108b (overlay стрелки/подсветки от модели).
- ADR-107 (`positional_subterms` через ответвление SF 16 trace).
- ADR-102, ADR-103 (LLM-комментарии MVP-1, MVP-2 — родители режима «Полного разбора»).
- KS-3700, KS-3702 (иерархия достоверности и нормализация — переиспользуются).
- KS-3706 (введение условного комментирования сыгранного хода — здесь дальнейшее развитие).

## 1. Контекст

Режим «Полный разбор партии» (ADR-102/103) построен вокруг пакетного эндпоинта `POST /analyses/review/comments`. Фронт собирает по партии массив `MoveFactsDto[]`, отдаёт его одним запросом, модель комментирует сразу все «интересные» ходы. «Интересные» отбираются на стороне фронта фильтром `nag.length === 0` — комментируем только ходы с NAG-меткой (ошибки/неточности).

В KS-3710 пользователь прислал PGN короткой партии и две жалобы:

1. **Идентичные комментарии в дебюте.** На 2.f4, 3...e4, 4.Qh5 модель выдала слово в слово один и тот же текст. На разных позициях `MoveFactsDto` имеет близкий набор полей (нет дискриминирующего сигнала), модель опирается на шаблон.
2. **Пустые комментарии на значимых ходах.** 6.dxe6 (взятие фигуры), 7.exf7+ (взятие с шахом), 8.Bc4+ (шах), 9.Qg5# (мат) — комментариев нет вообще. Эти ходы не имеют NAG-метки (они сильные/лучшие в позиции), фронтовый фильтр их отрезает.

Диагностика бэкенд-агентом и обсуждение с пользователем (в роли архитектора) показали:

- `MoveFactsDto` структурно слабее, чем входной контракт `position-comment`. У него нет полного набора подкомпонент `positional_subterms` (Stockfish 16 trace), нет `sf18_eval`, нет `sf18_pv` (первая линия), нет `terminal_value_*` (статика на конечной позиции PV). То есть базис достоверности, который в режиме одиночной позиции (ADR-108, §8.2 / KS-3700) считается основным, в режиме полного разбора отсутствует.
- На стороне фронта четыре дополнительных пробела диагностики:
  - `move.mate = 0` вместо реальной дистанции до мата;
  - `mateBefore` / `mateAfter` стабильно `null` (не пробрасываются из движка);
  - `positional_subterms` стабильно `[]` (поломка трассировки Stockfish-WASM: `skipTraceForThisRun` ставится в `true` после первой ошибки и не сбрасывается);
  - `findHangingPiece` пропускает случай «защитники есть, но SEE > 0 (выгодное взятие)».
- Точечная правка `buildSystemPrompt` (как изначально планировалось в KS-3710) корень не лечит. Модели просто нечего сравнить — нет ни статической карты «до», ни «после», ни разницы между ними. На сильных ходах нет даже самого факта вызова.

Итог: режим «Полного разбора» опирается на структурно более бедный входной контракт, чем уже работающий режим одиночной оценки. Усиление промпта без замены контракта смысла не имеет.

## 2. Рассмотренные варианты

### Вариант A. Усиление текущего пакетного эндпоинта

Доработать `MoveFactsDto`: добавить `sf18_eval`, `sf18_pv`, `positional_subterms` на каждую позицию, исправить `move.mate`, `mateBefore`, `mateAfter`. Расширить промпт `buildSystemPrompt` фразой про иерархию достоверности. Расширить фронтовый фильтр «интересных» ходов.

**Минусы:**
- Размер payload растёт квадратично: 10–30 ходов × (FEN-before + FEN-after + factors-before + factors-after) — десятки килобайт на один запрос. Webhook отдаёт ответ за один шаг, время ответа растёт пропорционально количеству ходов.
- Один запрос — один таймаут. Сбой одного хода в середине партии приводит к потере всего разбора, повторять придётся целиком.
- Параллелизация на стороне сервера не получается естественно (webhook принимает один запрос, отдаёт один ответ). На фронте — тоже не получается (один пакетный вызов).
- Контракт расходится с `position-comment`: придётся либо синхронизировать руками два набора факторов, либо вводить общий тип и обходить его двумя путями. И то и другое — долговое.
- `parseModelOutput` `position-comment` (overlay highlights/arrows из ADR-108b) переиспользуется через копипасту.

### Вариант B. Per-move-эндпоинт с парными снимками before/after в формате position-comment (выбран)

Новый эндпоинт `POST /analyses/review/move-comment`. Один запрос — один ход. Тело содержит парные снимки `before`/`after` — те же `factors[]`, что в `position-comment` (с `sf18_eval`, `sf18_pv`, `positional_subterms`). Контракт ответа совпадает с `position-comment` (`comment`, `highlights`, `arrows`).

**Плюсы:**
- Базис достоверности тот же, что в режиме одиночной оценки. Промпт переиспользует уже отлаженную в KS-3700/KS-3702 иерархию: `sf18_eval` → `sf18_pv` → статика, акцент на разнице `before` vs `after`.
- Контракт ответа совпадает с `position-comment` — `parseModelOutput`, словарь расшифровок `subterm-labels`, валидация overlay (ADR-108b §3) переиспользуются без копий.
- Параллелизация естественная: фронт отправляет N запросов с контролируемой степенью параллелизма; rate-limit на бэке защищает от взрыва.
- Сбой одного хода локален: остальные ходы партии получат комментарий.
- «Интересные» ходы отбираются фронтом по расширенному критерию (взятия, шахи, маты, превращения, рокировки, заметное `material_change` или `positional_shifts`, а также классические ошибки/неточности по `classification`). Сильные ходы со значимым изменением позиции больше не отрезаются.
- Точка эволюции: позже можно перенести сбор `before`/`after`-снимков на сервер (фронт даёт только `fen` и `move`, сервер сам зовёт Stockfish и собирает факторы) — см. §5.

**Минусы:**
- Текущие лимиты per-user (10/мин, 30/день) рассчитаны на одиночные запросы и не выдержат партию из 20–30 интересных ходов. Нужны отдельные ключи `review-move:rate:*` с увеличенными лимитами.
- Объём трафика на партию вырастает (множество мелких запросов вместо одного крупного). Это нормально — каждый запрос отвечает быстрее, общий wall-clock не хуже за счёт параллелизма.
- Период миграции: старый эндпоинт нужно держать рабочим, пока фронт не переехал; временно — два кодовых пути.

### Вариант C. Без эндпоинта на бэке: фронт сам шлёт в существующий `position-comment` дважды на ход

Фронт на каждый интересный ход вызывает `POST /analyses/position/comment` дважды (FEN-before и FEN-after) и сшивает оба ответа в один комментарий руками.

**Минусы:**
- Дважды дёргается LLM-webhook на каждый ход — вдвое дороже по квоте.
- Сшивка двух разрозненных комментариев в один связный текст на фронте — без LLM это получится конкатенация, что хуже одного цельного ответа модели «вот ход, вот до, вот после».
- Никакого выигрыша по контракту: всё равно тащим парные снимки, но без общего вызова.

### Решение

Выбран **вариант B**. Корень — структурный разрыв базиса достоверности между режимами одиночной оценки и полного разбора. Закрывается переходом на тот же входной контракт, а не латанием бедного DTO.

## 3. Выбранное решение

### 3.1. Новый эндпоинт

`POST /analyses/review/move-comment`. Один запрос — один комментарий на один ход.

Тело запроса:

```ts
type MoveCommentRequest = {
  move: {
    san: string;
    uci: string;
    capture: string | null;        // тип взятой фигуры, null если не взятие
    check: boolean;
    mate: number | null;           // реальная дистанция до мата в полуходах
    castling: 'O-O' | 'O-O-O' | null;
    promotion: string | null;
    classification: 'best' | 'good' | 'inaccuracy' | 'mistake' | 'blunder';
  };
  before: { fen: string; factors: PositionFactor[]; eval?: EvalSnapshot };
  after:  { fen: string; factors: PositionFactor[]; eval?: EvalSnapshot };
  language: 'ru' | 'en';
};
```

`factors[]` — тот же массив подкомпонент, что в `position-comment` (`sf18_eval`, `sf18_pv`, `positional_subterms` со всеми `value_*` / `terminal_value_*`, `tactical_motifs`, `hanging_piece`, `threats_*`).

Ответ:

```ts
type MoveCommentResponse = {
  comment: string;
  highlights?: Array<{ square: string; color: AiOverlayColor }>;  // 0..4
  arrows?:     Array<{ from: string; to: string; color: AiOverlayColor }>;  // 0..2
};
```

Контракт ответа поэлементно совпадает с `PositionCommentResponse` (ADR-108b §3.1).

### 3.2. Промпт (RU + EN)

`buildSystemPrompt` нового эндпоинта инструктирует модель:

- «вот сыгранный ход, вот оценка ДО, вот оценка ПОСЛЕ; посмотри, какие факторы изменились, как изменилась оценка, и объективно прокомментируй сделанный ход»;
- иерархия достоверности `sf18_eval` → `sf18_pv` → статика; вердикт о стороне с перевесом следует за `sf18_eval`, статика и `positional_subterms` объясняют «как именно» (формулировка из KS-3700);
- акцент на разнице `before` vs `after` — не пересказывать обе позиции, описывать сдвиг;
- запрет шаблонных зачинов («По форме», «На доске типичная» — из acceptance KS-3710);
- если `classification` = `mistake`/`blunder`/`inaccuracy` ИЛИ есть hanging-фигура у только что ходившего ИЛИ `eval_after` резко хуже для ходящего — комментарий открывается констатацией ошибки и приводит смысл лучшего хода (по `sf_best` / `threats_missed`), без буквального пересказа `sf_best.line` (антипаттерн KS-3706);
- та же палитра подсветок/стрелок и семантика цветов, что в ADR-108b §4 (`red` слабость/угроза, `green` план/лучший ход, `yellow` ключевая идея, `blue` зарезервирован за пользователем).

EN-версия синхронна.

### 3.3. Переиспользования

- Парсер ответа модели `parseModelOutput` из `position-comment` (один контракт ответа — одна реализация).
- Словарь расшифровок подкомпонент `subterm-labels`.
- Иерархия достоверности (KS-3700).
- Нормализация и сбор `factors[]` (KS-3702) — на фронте прогоняется дважды, на `fen-before` и `fen-after`.
- Валидация overlay из ADR-108b §3 (длина массивов, координаты `[a-h][1-8]`, маппинг цветов через `toAnnotationColor`).

### 3.4. Лимиты

Текущие ключи `position-comment:rate:*` (20/мин, 200/день на пользователя — ADR-108 §6.1) рассчитаны на manual-режим одиночных кликов и не подходят.

Заводятся отдельные ключи `review-move:rate:*`. Конкретные цифры согласуются при реализации KS-3711; ориентир — поддержка партии из 30 интересных ходов в течение нескольких минут, плюс запас на параллельные сессии. Global daily limit на сервис сохраняется и пересматривается отдельно по фактическому потреблению.

### 3.5. Отбор «интересных» ходов на фронте

Старый фильтр `nag.length === 0` снимается. Новый критерий:

- ошибки/неточности (`classification` ≠ `best` / `good`);
- взятия (`move.capture !== null`);
- шахи (`move.check`);
- маты (`move.mate !== null`);
- превращения, рокировки;
- ходы с заметным `material_change` или `positional_shifts` (порог уточняется при реализации).

Тихие ходы без сигналов не комментируются — экономия запросов.

### 3.6. Параллельность и оркестрация на фронте

Фронт оркестрирует очередь запросов. Степень параллелизма выбирается так, чтобы не упираться в `review-move:rate:per-min`. Один таймаут — на один ход; сбой локален и отображается в UI отдельной плашкой «комментарий не удалось получить» именно у этого хода, без потери остальных.

### 3.7. Миграция

- Старый `POST /analyses/review/comments` остаётся рабочим до полной выкладки фронта (KS-3712).
- После полной миграции фронта старый эндпоинт снимается. До этого момента — два кодовых пути на бэке.
- `MoveFactsDto` устаревает вместе со старым эндпоинтом.

### 3.8. Четыре пробела диагностики на фронте (закрываются в KS-3712)

Без них новый эндпоинт смысла не имеет — `factors[]` в `before`/`after` будут такими же пустыми, как сейчас:

1. Снять фильтр `nag.length === 0` в `useGameReview.ts` (закрывает кейс с 6/7/8/9 ходами repro KS-3710).
2. `move.mate = 0` → реальная дистанция до мата (полуходы из движка).
3. `mateBefore` / `mateAfter` → вытащить из движка и пробросить в `before.eval` / `after.eval`.
4. `findHangingPiece` → расширить, чтобы кейс «защитники есть, но SEE > 0» классифицировался как hanging-фигура (зевок слона из 5...Be6 в repro KS-3710).

### 3.9. Починка трассировки Stockfish-WASM (закрывается в KS-3712)

`positional_subterms` стабильно `[]`, потому что `skipTraceForThisRun` ставится в `true` после первой ошибки и не сбрасывается. Без починки `factors[]` в `before`/`after` будут пустыми, и весь смысл перехода теряется. Лечится найти и сбросить флаг (или корректно восстанавливать трассировку после ошибки), покрыть тестом.

## 4. Последствия

### Положительные

- Базис достоверности на ход тот же, что в режиме одиночной оценки. Жалоба KS-3710 №1 (шаблон в дебюте) лечится самим набором данных, не косметической правкой промпта.
- Сильные ходы со значимыми событиями (взятия / шахи / маты / превращения) получают комментарий. Жалоба KS-3710 №2 закрывается расширением критерия отбора.
- Один контракт ответа на оба режима (одиночная оценка и полный разбор) — общий парсер, общий словарь расшифровок, общая валидация overlay, общая палитра цветов. Будущие правки промпта или формата overlay идут в одно место.
- Локальный сбой одного хода не убивает разбор партии целиком.
- Точка эволюции — серверный сбор `before`/`after`-снимков (см. §5).

### Отрицательные / стоимость

- На партию из 30 интересных ходов идёт 30 LLM-вызовов вместо одного. Квота на пользователя расходуется быстрее; нужны отдельные более щедрые ключи `review-move:rate:*`.
- Период миграции: на бэке временно два кодовых пути (старый пакетный и новый per-move). Сразу после полной выкладки фронта старый снимается — это явный коммит, а не опциональная уборка.
- Wall-clock одного полного разбора зависит от выбранной степени параллелизма. При последовательной отправке партия из 30 ходов разбирается заметно дольше, чем сейчас одним пакетным запросом; при параллельной — упор в rate-limit.
- Объём трафика клиент↔сервер растёт: 30 запросов с парными снимками тяжелее одного пакетного, но за счёт мелких пакетов RTT компенсируется.

### Что устаревает

- `MoveFactsDto` — после миграции фронта.
- `POST /analyses/review/comments` (старый пакетный) — после миграции фронта.
- Логика фильтра «интересных» по `nag.length === 0` на фронте.
- Лимиты `position-comment:rate:*` остаются за режимом одиночной оценки; для полного разбора — отдельный набор `review-move:rate:*`.

## 5. Открытые вопросы

1. **Серверный сбор `before`/`after`-снимков.** Альтернатива: фронт передаёт только `fen` + `move`, сервер сам зовёт Stockfish (узел в инфраструктуре, где он уже есть) и собирает `factors[]`. Плюсы — уносим тяжёлый WASM-трафик с клиента, унифицируем источник `factors[]` с `position-comment` (там сбор тоже можно унести на сервер позже). Минусы — latency растёт (один запрос вместо параллельных WASM-вызовов в браузере), нагрузка на сервер существенно выше. Решение откладывается до набора метрик по фактическому wall-clock полного разбора при параллельной отправке с фронта. Не блокер MVP, фиксируется как направление развития.
2. **Конкретные значения лимитов `review-move:rate:*`.** Согласуются при реализации KS-3711 по факту замера; начальный ориентир — 60/мин и 600/день на пользователя при degree-of-parallelism 4 на фронте.
3. **Степень параллелизма на фронте.** Точное значение зависит от итоговых лимитов и UX-ожиданий по wall-clock. Решение принимается при реализации KS-3712 после согласования цифр §5.2.
4. **Сохранение overlay (`highlights` / `arrows`) в PGN.** В ADR-108b §2 это явно вне границ для режима одиночной оценки. Для полного разбора пока тоже не сохраняем (только текст комментария пишется в `move.comment` через существующий пайплайн). Серверная персистентность overlay по `(analysisId, ply)` — отдельный follow-up после фидбэка.
5. **Видимость лейбла «Из полного разбора» в `AiPositionCommentPanel`** (ADR-108 §7). Поведение не меняется: лейбл показывается на любом непустом `move.comment` независимо от того, каким именно эндпоинтом он был получен. Маркер источника (старый/новый) в `move.comment` не вшиваем.
6. **Адаптация под уровень игрока** (ADR-108 §10.1). Параметр `user_elo` в промпт нового эндпоинта на старте не передаётся. Если по фидбэку выяснится, что требуется — добавляется параметром в DTO без изменения контракта `factors[]`.

## 6. Резюме

Режим «Полного разбора партии» переводится с пакетного `POST /analyses/review/comments` на per-move `POST /analyses/review/move-comment`. Один запрос — один ход. Тело содержит парные снимки `before`/`after` в том же формате `factors[]`, что и `position-comment`. Контракт ответа совпадает с `position-comment` (`comment` + опциональные `highlights` / `arrows`). Иерархия достоверности и палитра overlay — из KS-3700 и ADR-108b. «Интересные» ходы отбирает фронт по расширенному критерию (NAG ИЛИ взятие ИЛИ шах ИЛИ мат ИЛИ превращение/рокировка ИЛИ заметный сдвиг материала/позиции). Лимиты per-user — отдельные ключи `review-move:rate:*`, конкретные цифры — при реализации. Старый эндпоинт держится рабочим до полной миграции фронта и снимается сразу после.

Реализация: KS-3711 (backend) и KS-3712 (frontend, миграция + четыре пробела диагностики + починка трассировки Stockfish-WASM) идут параллельно.

## 1. Контекст

Запрос пользователя (Telegram, 2026-05-11): «надо сделать ревизию
разделов и логику отображения пунктов меню в левой панели на десктопе
и в нижней панели на мобильном». На скриншоте `/tmp/telegram/
326129694_0.jpg` видна вертикальная колонка с 11+ иконками подряд:
🏠 ♟ 🏆 🧩 ⚡ 🧠 🎯 🎓 🔬 📚 📺, ниже divider и ещё 📋 ✨ 👥 ⚙ (+ 🛡
для админа, 📝 кнопка feedback'а в футере). Иерархии нет, всё в
один уровень.

Параллельно по KS-2793 решено: пункт «Уроки» переименовывается в
«Обучение», каталог Studies становится табом внутри `/lessons`. То есть
в этом ADR — не появляется нового пункта Studies; пункт «Обучение»
заменяет «Уроки».

Цель документа: предложить структуру меню (топ-уровневые ≈5 пунктов
на desktop + динамический 3+1 на mobile), сгруппировав вторичные
пункты, и составить список frontend-задач под реализацию.

### 2.2 Mobile Bottom Bar (`apps/web/src/components/MobileBottomBar.tsx`)

Логика (KS-2373): 3 кнопки top-3 + кнопка «Ещё». Top-3 динамически
подтягивается из `GET /user/nav-stats/top?limit=3` (backend учитывает
переходы пользователя). Default до получения ответа: `['play',
'tournaments', 'workshop']`.

Whitelist (`useNavStats.ts` → `NAV_ROUTES`): play, tournaments,
workshop, lessons, drills, broadcasts, archive, profile, puzzles,
precision (10 routes). «Ещё» открывает выпадающий список из остатков
whitelist'а + features, friends, feedback, settings, admin.

Состояние: top-3 — частотные сценарии (полезно), но whitelist
не покрывает все категории (например, у активного «тактика» в top-3
могут оказаться puzzles+drills+precision — фактически три тренировочные
кнопки, и потеряется быстрый доступ к Play/Workshop). Внутри «Ещё»
нет группировки — плоский список 6–8 ссылок.

### 2.3 Оценка частоты использования (без аналитики, экспертная)

Точной аналитики переходов на руках у архитектора нет — `nav-stats`
есть у backend (`POST /user/nav-stats/increment`), но дамп её в ADR не
выгружен. Ниже — экспертная оценка приоритета сценариев на основе
архитектуры продукта:

| Категория | Сценарии | Частота (экспертно) |
|-----------|---------|---------------------|
| Play | играть быстрые/блиц/классика; турниры | **очень высокая** (ежедневная) |
| Train | задачи, rush, drills, precision | **высокая** (несколько раз/нед., но эпизодически) |
| Learn | уроки, курсы | **средняя** (для новичков — высокая, для опытных — низкая) |
| Analyze | workshop, архив | **средняя** (после каждой партии у мотивированных) |
| Watch | трансляции | **низкая для большинства**, **высокая для турнирной аудитории во время событий** |
| Social | друзья, профиль, чат | **средняя** |
| Utility | настройки, feedback, features, admin | **редко** (1 раз за сессию или реже) |

Эта оценка — гипотеза; перед реализацией предлагаю экспортнуть
агрегированный `nav-stats` (есть на backend, ADR-в-курсе) и подкрепить
расстановку реальными числами (см. §6.1 в декомпозиции).

## 3. Информационная архитектура — группировка

Из аудита выделяются 4 «обучающие/тренировочные» пункта подряд (🧩 🧩
⚡ 🧠 🎯) и 2 «аналитических» (🔬 📚). Эти группы — кандидаты на
сворачивание.

### 3.1 Концептуальные группы

| Группа | Что входит сейчас | i18n-ключ группы |
|--------|---------------------|---------|
| **Играть** (Play) | Играть, Турниры | `nav.play` (расширить) |
| **Тренировка** (Train) | Задачи, Puzzle Rush, Тренажёры, Точность | `nav.train` (новый) |
| **Обучение** (Learn) | Уроки (+ Студии-таб по KS-2793) | `nav.learn` (переименовать `nav.lessons`) |
| **Анализ** (Analyze) | Лаборатория, Архив | `nav.analyze` (новый) |
| **Трансляции** (Watch) | TV | `nav.tv` |
| **Социальное / Утилитарное** | Друзья, Настройки, Feedback, Features, Admin | в footer / drawer |

Если каждая группа на desktop — один топ-уровневый пункт, то получаем
**5 «контентных» + 1 ссылка `🏠 Главная`** = **6 пунктов**. Это укладывается
в лимит «5–7» из ТЗ.

### 3.2 Что делать с «утилитарным»

В sidebar выносится фиксированный «footer-блок» (как сейчас) с
4 иконками:

| Иконка | Куда |
|--------|------|
| 👤 / 🟢 | Профиль / статус пользователя (ссылка `/profile`) |
| ⚙ | Настройки (`/settings`) |
| 📝 | Feedback (модалка, как сейчас) |
| 🛡 | Admin (только админ) |

Друзья (👥) и Features (✨) — переезжают в «Профиль» как сабменю
(`/profile/friends`, `/profile/features` или как табы). Сценариев заходить
в «Друзей» или «Возможности» из любого места приложения мало — это
профильный workflow.

Альтернатива: оставить «Друзья» как самостоятельный пункт sidebar,
если будет social-эпик в roadmap'е. Решает координатор. По умолчанию
в этом ADR — спрятать.

### 3.3 Submenu vs single-page vs drawer

Три варианта раскрытия группы при клике на топ-пункт:

**A. Single-page** (рекомендуемый для большинства): клик на «Тренировка»
открывает `/train` — лобби, где карточками выложены 4 подраздела с
описаниями. Это естественно для новичка («что такое drills?» — увидит
карточку с описанием). Используется уже для Lessons (DiscoverCoursesPage)
и Archive.

**B. Submenu (раскрывающийся ряд иконок)**: при наведении/клике
открывается ряд из 4 иконок прямо в sidebar. Минусы: занимает место,
плохо работает на узких экранах, нет места под подписи. Уместно
только для desktop, и только если у группы 2–3 пункта.

**C. Drawer (выезжающая панель)**: вторичный sidebar справа от
основного, скрытый по умолчанию. На наш текущий лэйаут (sidebar 64px
шириной + контент) — много усилий, мало пользы.

Решение: **single-page лобби** для каждой группы (`/train`, `/analyze`).
Submenu — только как hover-фичу (tooltip с тремя ссылками) — это
nice-to-have, не блокирует MVP.

### 3.4 Mobile-стратегия

Mobile bottom bar — **сохраняем динамический 3+1**: 3 топ-кнопки из
`GET /user/nav-stats/top?limit=3` (KS-2373) + кнопка «Ещё». Решение
пользователя (KS-2794, §9.4): «динамически нужно оставить на мобильном
нижнюю панель, три пункта должны быть видны которые часто посещаются».

Что меняется относительно текущего состояния:

1. **Whitelist `NAV_ROUTES` пересмотрен под группы.** Сейчас в whitelist
   10 маршрутов: `play`, `tournaments`, `workshop`, `lessons`, `drills`,
   `broadcasts`, `archive`, `profile`, `puzzles`, `precision`. После
   ревизии sidebar 4 из них (`puzzles`, `drills`, `precision`,
   плюс отдельный `puzzle-rush`-маршрут который не в whitelist'е)
   логически принадлежат группе «Тренировка», 2 (`workshop`, `archive`)
   — «Анализ». Чтобы динамика top-3 не давала «три тренировочные
   кнопки подряд», в whitelist остаются **только групповые маршруты**:
   `play`, `train`, `learn`, `analyze`, `broadcasts`, `profile`.
   Подсчёт частоты по бэкенду — на уровне группы.
2. **`/tournaments`** — снимается из whitelist (по §9.1 пользователь
   решил не выделять Турниры; раздел пока без контента). Переходы
   на `/tournaments` теперь учитываются как заходы в группу `play`
   (resolveNavRoute → `play`).
3. **«Ещё» (drawer)** — переделывается из плоского списка ссылок в
   сгруппированный sheet (см. §5.2 ниже): Социум / Аккаунт / Помощь /
   Админ.
4. **`useNavStats` миграция счётчиков**: при старте новой версии в БД
   останутся старые счётчики (`puzzles`, `drills`, `precision`,
   `workshop`, `archive`, `tournaments`, `lessons`). Backend-агрегатор
   должен **сводить их к новым группам** на чтении (`puzzles`+`drills`+
   `precision` → `train`; `workshop`+`archive` → `analyze`;
   `tournaments` → `play`; `lessons` → `learn`). Это разовая правка
   `GET /user/nav-stats/top` без миграций — стары записи не теряются.

## 4. Предложение новой структуры — Desktop

### 4.1 Топ-уровневые пункты (sidebar)

```
┌──── sidebar (≈64px) ────┐
│                          │
│  ♟    Играть             │  nav.play → /play
│  🧠   Тренировка         │  nav.train → /train (Задачи, Rush, Drills, Precision)
│  🎓   Уроки              │  nav.lessons → /lessons (+ таб Студии, KS-2793)
│  🔬   Анализ             │  nav.analyze → /workshop (+ таб Архив)
│  📺   Трансляции         │  nav.tv → /broadcasts
│                          │
│  ──── divider ────       │
│                          │
│  👤   Профиль            │  /profile
│  👥   Друзья             │  /friends
│  ⚙   Настройки          │  /settings
│  📝   Feedback (модал)   │
│  🛡   Админка            │  adminOnly
└──────────────────────────┘
```

**5 контентных** пунктов сверху + **3–4 утилитарных** в нижнем блоке
(Профиль, Друзья, Настройки, Feedback-модалка, опц. Админка).
Сейчас на скриншоте — 11 контентных подряд. Сокращение более чем
в 2 раза.

Что **убрано** относительно предыдущей итерации этого ADR (Proposed):

- 🏠 **Главная** — снято по решению пользователя (§9.2 ниже). На
  корне `/` для авторизованных делаем редирект на `/play`, для
  гостей — лендинг. Логотип Kingside в шапке остаётся ссылкой на
  главную для тех, кому понадобится.
- 🏆 **Турниры** — снято по §9.1. Раздел сейчас пустой; до появления
  контента пункт не нужен. Маршрут `/tournaments` сохраняется
  (внутренний доступ, прямые ссылки), переходы туда учитываются как
  заходы в группу `play` для nav-stats.
- ✨ **Возможности** (`/features`) — переносится в drawer «Ещё» на
  mobile и в **отдельный пункт футера sidebar не выводится**. Доступ
  через `/profile` (как ссылка) или прямой URL. См. §6 декомпозицию.

«Друзья» по решению §9.3 — **в футере sidebar** (рядом с Профилем,
Настройками, Feedback'ом), а не вложены в `/profile`.

### 4.2 Что происходит при клике

| Топ-пункт | Behaviour |
|-----------|-----------|
| ♟ Играть | `/play` — основной экран. Маршрут `/tournaments` остаётся доступен по прямой ссылке, но в sidebar отдельно не выводится |
| 🧠 Тренировка | `/train` — лобби с 4 карточками: Задачи / Rush / Drills / Точность. Каждая карточка ведёт на свой существующий маршрут |
| 🎓 Уроки | `/lessons` — внутри табы «Курсы / Мои» (+ «Студии» когда KS-2793 MVP завершится). Ребрендинг `nav.lessons` → `nav.learn` отложен до KS-2793 (§9.5) |
| 🔬 Анализ | `/analyze` — лобби с карточками: Лаборатория (`/workshop`/`/analysis`), Архив (`/archive`). Опционально — «Партии по позиции» |
| 📺 Трансляции | `/broadcasts` — без изменений |

Если feature-flag выключает подраздел (например, `drillsEnabled=false`),
карточка в `/train` скрывается, либо рендерится в «coming soon»
состоянии (продуктовое решение). Если **все** подразделы группы
выключены — топ-пункт sidebar тоже скрыт (логика gating переезжает с
индивидуальных пунктов на групповые).

### 4.3 Поведение «активная подсветка»

Подсветка топ-пункта — если pathname **попадает в любой из
вложенных маршрутов**, не только в точный URL пункта. То есть:

- `/play*`, `/tournaments*` → подсветка `♟ Играть`.
- `/train*`, `/puzzles*`, `/puzzle-rush*`, `/drills*`, `/precision*` → подсветка `🧠 Тренировка`.
- `/lessons*` (включая будущие `/lessons?tab=studies` и
  `/analysis/study/<chapter>` из KS-2793) → `🎓 Уроки`.
- `/analyze*`, `/workshop*`, `/analysis*`, `/archive*` → `🔬 Анализ`.
- `/broadcasts*` → `📺 Трансляции`.

Реализация — расширить `NavItem.match` массивом всех вложенных
префиксов, как уже сделано для `workshop` (`['/workshop','/analysis']`).
Регрессионный тест активной подсветки — обязательный (паттерн из
KS-2790).

### 4.4 Корневой роут `/`

Решение (§9.2): на `/` стоит редирект.

- **Авторизованный пользователь** → редирект `/play` (основной use-case
  — играть).
- **Гость** → лендинг (страница приглашения войти / зарегистрироваться).
  Лендинг — отдельная задача от ревизии sidebar (продуктовый дизайн),
  здесь фиксируем только сам редирект.

`/lobby` как маршрут **сохраняется** (есть прямые ссылки, маркетинговые
кампании, dashboards). В sidebar пункт `🏠 Главная` снят; ссылка на
`/lobby` остаётся доступна через логотип шапки.

## 5. Предложение новой структуры — Mobile

### 5.1 Bottom bar (динамический 3+1, как сейчас по KS-2373)

По решению пользователя (§9.4): mobile bar остаётся **динамическим
3+1**. Три кнопки top-frequency из `GET /user/nav-stats/top?limit=3` +
кнопка «Ещё» (drawer). KS-2373 не переписываем.

```
┌──────────────────────────────────────────────────────────┐
│                                                           │
│                 содержимое страницы                       │
│                                                           │
├──────────────────────────────────────────────────────────┤
│   <top-1>      <top-2>      <top-3>           ⋯           │
│  (динамически по nav-stats)              Ещё              │
└──────────────────────────────────────────────────────────┘
```

Где `<top-N>` — один из групповых маршрутов: `play`, `train`,
`learn`, `analyze`, `broadcasts`, `profile`. До сбора статистики
у нового пользователя — дефолт `['play', 'train', 'learn']`
(прежний дефолт `['play', 'tournaments', 'workshop']` устарел с
ревизией групп).

**Что меняется в `useNavStats.ts` относительно текущей реализации:**

1. `NavRoute` whitelist сужается с 10 маршрутов до **6 групповых**:
   `play`, `train`, `learn`, `analyze`, `broadcasts`, `profile`.
2. `resolveNavRoute(pathname)` маппит вложенные маршруты в группы:
   - `/play*`, `/tournaments*` → `play`
   - `/train*`, `/puzzles*`, `/puzzle-rush*`, `/drills*`, `/precision*` → `train`
   - `/lessons*` → `learn`
   - `/analyze*`, `/workshop*`, `/analysis*`, `/archive*` → `analyze`
   - `/broadcasts*` → `broadcasts`
   - `/profile*`, `/player/*` → `profile`
3. `useTopNavStats` фильтрует ответ backend под новый whitelist; если
   backend отдаёт старые ключи (`puzzles`, `drills`, `tournaments` …)
   — маппит их в новые группы на чтении (см. §5.3 «миграция счётчиков»).
4. `useTrackNavStats` пишет инкремент с новым ключом (группой), не с
   индивидуальным маршрутом.
5. `DEFAULT_TOP` обновляется до `['play', 'train', 'learn']` (вместо
   `['play', 'tournaments', 'workshop']`).

### 5.2 Drawer «Ещё»

При тапе на `⋯` выезжает sheet снизу с **сгруппированным** списком
(сейчас — плоский). Группировка:

```
┌──────────────────────────────────────────┐
│ Ещё                                  ╳   │
│                                          │
│ ▸ Социум                                 │
│   📺 Трансляции        /broadcasts       │
│   👥 Друзья            /friends          │
│                                          │
│ ▸ Аккаунт                                │
│   👤 Профиль           /profile          │
│   ⚙ Настройки         /settings         │
│                                          │
│ ▸ Помощь                                 │
│   ✨ Возможности       /features         │
│   📝 Обратная связь    (модалка)         │
│                                          │
│ ▸ Админ (видна только админу)            │
│   🛡 Флаги             /admin            │
└──────────────────────────────────────────┘
```

В drawer'е могут параллельно появиться **те групповые маршруты, что
не попали в top-3** (`analyze`, `broadcasts` и т. п. — если у
пользователя в этот период активны другие группы). Это базовое
поведение текущего `MobileBottomBar` — сохраняем.

«Главная» (`/lobby`) и «Турниры» (`/tournaments`) из drawer удаляются:
лобби живёт в логотипе шапки, турниры — недоступны как пункт
навигации до появления контента (прямые ссылки работают).

### 5.3 Миграция nav-stats счётчиков

В таблице `user_nav_stats` лежат накопленные счётчики по старому
whitelist'у (`puzzles`, `drills`, `precision`, `puzzle-rush`,
`tournaments`, `workshop`, `archive`, `lessons`, ...). При переходе
на групповой whitelist данные **не теряются** — backend `GET
/user/nav-stats/top` агрегирует на чтении:

```
SUM(puzzles + drills + precision + puzzle-rush)         → train
SUM(workshop + archive)                                  → analyze
SUM(tournaments + play)                                  → play
lessons                                                  → learn
broadcasts                                               → broadcasts
profile                                                  → profile
```

Это маленькая backend-правка (один JOIN/CASE в SQL агрегатора), без
миграций. Старые счётчики продолжают писаться какое-то время (если
старые сборки приложения остаются у части пользователей) — это
безболезненно: агрегатор схлопнет их на чтении.

Альтернатива (truncate + старт с нуля) — отвергнута, потому что
пользователи потеряют свой персонализированный top-3 на N дней до
накопления новых данных.

## 8. Риски

1. **Регрессия в активной подсветке** (KS-2790 уже чинили похожее).
   Митигация: ADR058-T6 явно требует тестов; берём паттерн из
   текущего `match`-массива `workshop`.
2. **Старые ссылки в i18n** на `/puzzles` и т. п. — продолжают работать
   (маршруты не удаляются, удаляются только пункты sidebar). Закладки и
   обмен ссылками не ломаются.
3. **«Где же Drills?»** — пользователь, привыкший к старому sidebar'у,
   не найдёт раздел. Митигация: ADR058-T17 changelog + при первом
   рендере новой структуры в течение N дней — onboarding-tooltip
   («Тренажёры теперь в разделе Тренировка»).
4. **Лимит feature-flag gating: «все 4 train-подраздела выключены»**.
   В текущем sidebar — пункт просто скрыт. В новом — если все 4
   выключены, скрываем `Train` целиком; если выключены частично —
   `TrainLobbyPage` показывает только включённые карточки. Логика
   gating переезжает с пунктов на карточки лобби.
5. **KS-2793 ещё не реализован**: таб «Студии» в `/lessons` зависит от
   KS-2793 MVP. Этот ADR не блокируется — структура sidebar
   реализуема прямо сейчас, таб «Студии» добавляется отдельно в KS-2793.
6. **nav-stats после релиза**: первые часы после релиза `useTrackNavStats`
   пишет уже новые групповые ключи, но старые сборки приложения у
   части пользователей продолжают писать старые. Митигация: backend
   T12 принимает оба whitelist'а и схлопывает на чтении (см. §5.3).
7. **Поведение `/lobby`**: маршрут остаётся работающим, но из меню
   исчез. Кому действительно нужно — попадает через логотип шапки.
   Митигация: ничего не меняем в маршрутизации, только в навигации.

## 11. Доводка: Desktop submenu вместо лобби-страниц (KS-2839)

**Дата:** 2026-05-12
**Триггер:** обратная связь пользователя после деплоя KS-2794 пакета:
> «мне не очень нравится лобби на каждый раздел выглядит как пустая
> страница с несколькими ссылками и у нас эти обе повторяются — лучше
> было бы сделать меню двойной вложенности. На десктопе меню двойной
> вложенности было бы идеально. А вот лобби можно оставить на мобильном».

### 11.1 Решение

На **desktop** убираем лобби-страницы как UX-паттерн и заменяем их
двухуровневым меню в sidebar. На **mobile** лобби-страницы (`/train`,
`/analyze`) — остаются как есть (KS-2796 / KS-2797).

Структура desktop sidebar после доводки:

```
┌──── sidebar (≈64px collapsed / 220px expanded popover) ────┐
│                                                             │
│  ♟    Играть              → /play                           │
│  🧠   Тренировка    ›     → раскрывает submenu              │
│         ├─ 🧩 Задачи              → /puzzles                │
│         ├─ ⚡ Puzzle Rush         → /puzzle-rush            │
│         ├─ 🧠 Тренажёры           → /drills                 │
│         └─ 🎯 Точность            → /precision              │
│  🎓   Уроки               → /lessons                        │
│  📺   Трансляции          → /broadcasts                     │
│  🔬   Анализ        ›     → раскрывает submenu              │
│         ├─ 🔬 Мастерская          → /workshop               │
│         └─ 📚 Архив               → /archive                │
│                                                             │
│  ──── divider ────                                          │
│                                                             │
│  👤   Профиль                                               │
│  👥   Друзья                                                │
│  ⚙   Настройки                                             │
│  📝   Feedback (модалка)                                    │
│  🛡   Админка (admin only)                                  │
└─────────────────────────────────────────────────────────────┘
```

Стрелочка-маркер «›» рендерится **только** на пунктах с подменю
(`🧠 Тренировка`, `🔬 Анализ`). Прямые пункты (`♟ Играть`, `🎓 Уроки`,
`📺 Трансляции`) — без неё. Это визуально отличает «лиф» от
«родителя».

### 11.2 UX-паттерн подменю — анализ вариантов

| Вариант | Плюсы | Минусы |
|--------|-------|--------|
| **A. Hover-поповер** (как Lichess Tools/Learn): курсор на пункте → справа от sidebar появляется панель с подпунктами | Не отнимает вертикаль sidebar'а; быстро для мыши; sticky-футер не прыгает | На тачскрине (Surface, гибридный ноут) hover не работает — нужен click-fallback; требует обработки «уехал курсором — но не сразу схлопывать» (≈100 ms delay) |
| **B. Inline-аккордеон**: клик по пункту раздвигает sidebar вниз, подпункты внутри той же колонки | Простой keyboard/tab; работает на любом устройстве; нет hover-сложностей | Sticky-футер «прыгает» при раскрытии; визуально съедает вертикаль; на узких высотах <600px подпункты могут не помещаться |
| **C. Слайд-out панель** из левого края (Discord/Slack-стиль) | Большое пространство для подпунктов с описанием | Перегруз: чтобы вернуться, нужно закрыть; ломает «один клик — одна цель»; чуждо нашему лэйауту (узкий sidebar) |
| **D. Hover-поповер + click-toggle на тач**: hover открывает на desktop, click открывает/закрывает на тач — гибрид A с защитой от тач-устройств | Покрывает все юзкейсы; UI остаётся компактным; sticky-футер не прыгает | Больше JS-логики (нужен `pointer: fine` detection); тестов больше |

**Выбор — вариант D (hover-поповер + click-toggle).**

Обоснование:

1. **Самый знакомый паттерн** для шахматной аудитории — Lichess
   использует именно его для своих «Tools» / «Learn» dropdown'ов.
   Пользователи Kingside часто параллельно сидят на Lichess; mental
   model уже сформирована.
2. **Без съедания вертикали** sidebar'а. Текущая высота с 5 контентными
   пунктами + 4 утилитарных = ~9 строк. Аккордеон при раскрытии
   `🧠 Тренировка` (+4 подпункта) и `🔬 Анализ` (+2 подпункта) добавит
   до 6 строк в неудачном случае — sidebar становится 15 строк, на
   разрешении 768×1024 это уже близко к высоте viewport'а.
3. **Sticky-футер не прыгает.** Поповер рендерится в overlay-слое
   (`position: fixed`), не влияет на flex-layout sidebar'а.
4. **Тач-устройства покрываются.** Через `matchMedia('(pointer: fine)')`
   определяем тип указателя: `coarse` (touch) → клик на пункте
   открывает/закрывает поповер (как dropdown), `fine` (мышь) →
   hover + 100 ms закрытия после `mouseleave`. На desktop с
   touch-экраном (Surface) предпочитаем `pointer:fine` (PointerEvents
   приоритизирует мышь, если она подключена).
5. **Keyboard полная поддержка** (см. §11.4).

### 11.3 Active-highlight для подменю

Подсветка работает на двух уровнях:

- **Групповой пункт** (Тренировка / Анализ) подсвечен, если pathname
  попадает в любой из вложенных маршрутов:
  - `/train`, `/puzzles*`, `/puzzle-rush*`, `/drills*`, `/precision*` → `🧠 Тренировка`
  - `/analyze`, `/workshop*`, `/analysis*`, `/archive*` → `🔬 Анализ`
  Реализация — уже есть в `NavItem.match` (KS-2803, KS-2790 паттерн).
- **Подпункт** в поповере подсвечен, если pathname матчит его
  конкретный маршрут:
  - `/puzzles*` → подсвечен «Задачи»
  - `/drills*` → «Тренажёры»
  - и т. д.

Если поповер не открыт, подсветка подпункта не видна (поповер
схлопнут). При открытии поповера активный подпункт подсвечивается
сразу (визуальная подсказка, где пользователь сейчас).

«Двойная подсветка» (родитель + ребёнок) — то, как ведёт себя
Lichess. Пользователь сразу понимает иерархию.

### 11.4 A11y / клавиатура / ARIA

ARIA-роли:

- Sidebar = `<nav role="navigation" aria-label="Main">`.
- Каждый пункт с подменю — `<button aria-haspopup="menu"
  aria-expanded="true|false" aria-controls="<popover-id>">`.
- Popover — `<div role="menu" id="<popover-id>"
  aria-labelledby="<parent-button-id>">`, внутри `<a role="menuitem">`
  для подпунктов.
- Пункт без подменю — обычный `<a>`, не `<button>`.

Клавиатура:

| Клавиша | Поведение |
|---------|-----------|
| `Tab` / `Shift+Tab` | Перемещение фокуса между пунктами sidebar'а |
| `Enter` / `Space` на groupItem | Открыть поповер; фокус — на первом подпункте |
| `Esc` в поповере | Закрыть, фокус возвращается на parent-button |
| `↓` / `↑` в поповере | Переключение между подпунктами |
| `Enter` на подпункте | Переход по ссылке |
| `Tab` в поповере | Закрыть поповер и перейти к следующему элементу sidebar'а |

Hover-таймер: 100 ms после `mouseleave` до закрытия поповера —
страховка от случайного `mouseleave` при движении на подпункт.

### 11.5 Решение по лобби-страницам

Маршруты `/train` и `/analyze` **остаются** в роутинге. Поведение —
зависит от устройства:

- **Desktop** (`useIsMobile() === false`): при прямом заходе на `/train`
  → редирект на `/puzzles` (первый разрешённый подраздел; если все
  выключены — на `/lobby`). При прямом заходе на `/analyze` → редирект
  на `/workshop`. Это страхует старые ссылки/закладки.
- **Mobile** (`useIsMobile() === true`): рендерит лобби-страницу как
  есть (KS-2796 / KS-2797). Никаких изменений.

Решение «оставить fallback с редиректом» — проще, чем удалять роуты:
не ломает закладки пользователей, маркетинговые ссылки, поисковую
индексацию.

Внутри `TrainLobbyPage` / `AnalyzeLobbyPage`:

```tsx
const isMobile = useIsMobile();
if (!isMobile) {
  return <Navigate to={firstEnabledSubpath} replace />;
}
// ... рендер лобби карточек ...
```

top-3 + «Ещё». Эта структура не меняется в KS-2839. Подменю на mobile
не делаем (там пользователь идёт через лобби).

### 11.7 Реализация — детали

**Sidebar компонент** (`apps/web/src/components/Sidebar.tsx`):

- В `NavItem` расширяется поле `children?: NavItem[]` — массив
  подпунктов. Если `children` задан, при клике/hover открывается
  поповер; иначе обычная `<Link>`.
- Новый компонент `SidebarSubmenu` инкапсулирует hover/click-toggle
  логику + поповер + ARIA. State `openId: string | null` — какой
  пункт открыт (один за раз).
- Хук `usePointerType()` для детекции mouse vs touch (через
  `matchMedia('(pointer: fine)')` + listener). Hover активен при
  `fine`, click — всегда.

Поповер позиционируется через `position: fixed`, `left:
<sidebar-width>` (60–64px), `top: <parent-button-top>`. Расчёт `top`
— через `useRef` на parent-button + `getBoundingClientRect()`.

**Лобби-страницы** — добавить `useIsMobile()` + redirect-логику.

**Тесты:**

- Sidebar.test.tsx — рендер двух поповеров, hover/click, keyboard,
  ARIA-атрибуты, активная подсветка group + подпункта.
- TrainLobbyPage / AnalyzeLobbyPage — на desktop редирект, на mobile
  рендер.
- E2E (Playwright) — клик на `🧠 Тренировка` → поповер виден; клик
  по «Задачи» → переход на `/puzzles` + group + child highlighted.

### 11.11 Риски

1. **Hover-поповер не закрывается при движении курсора по диагонали**
   (классический dropdown bug). Митигация: 100 ms grace-period после
   `mouseleave` + проверка `isHovered` у поповера и parent-button.
2. **Click-toggle на тач конфликтует с hover на гибридных устройствах**
   (Surface). Митигация: `usePointerType()` динамически переключает
   стратегию; preferred — `fine` (мышь подключена), `coarse` —
   click-only.
3. **Закладка на `/train` у активных пользователей** → редирект на
   `/puzzles` может удивить. Митигация: changelog + tooltip-onboarding
   первые N дней (T27).
4. **Регрессия в активной подсветке** (KS-2790 уже был случай).
   Митигация: T22 + полноценный test-coverage (T26).
5. **Накладные расходы на дополнительные событий-листенеры** (`pointer`,
   `mouseleave`, `keydown`). Митигация: один глобальный listener на
   document для `Escape` + локальные на pointer-events компонента;
   профилирование не требуется (объём — миллисекунды).

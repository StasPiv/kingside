# ADR-006: Координация агентов — запрет параллельных конфликтующих экземпляров

## Статус

Принято (2026-03-08)

## Контекст

В задачах KS-176 и KS-177 выявлена системная проблема: один и тот же агент (frontend, backend, QA) запускался многократно параллельно на одну задачу. Это приводило к:

1. **Конфликтующим изменениям** — параллельные экземпляры frontend-агента вносили разные исправления в одни и те же файлы (один менял max-width, другой — width, третий добавлял ResizeObserver).
2. **Противоречащим отчётам** — один экземпляр QA сообщал "баг исправлен", другой одновременно — "баг НЕ исправлен".
3. **Потере контекста** — агенты не видели изменений других экземпляров и работали с устаревшим кодом.
4. **Бесконечным циклам** — каждый новый экземпляр "исправлял" уже исправленное или ломал чужие исправления.

Примеры: frontend сделал 6 коммитов с разными подходами к одной проблеме (KS-176), backend дважды добавил excludeId в разных коммитах (KS-177).

## Решение

### Правило 1: Одна задача — один экземпляр агента

Координатор ЗАПРЕЩАЕТ запускать второй экземпляр агента на задачу, если первый ещё не завершил работу. Статус задачи в Jira — единственный источник правды:

- **В работе (In Progress)** — агент активно работает. Запуск второго экземпляра ЗАПРЕЩЁН.
- **In Review** — работа завершена, ожидает проверки. Можно запускать QA.
- **К выполнению (To Do)** — задача свободна, можно назначать агента.

### Правило 2: Строгая последовательность для связанных задач

Если задача требует работы нескольких ролей (например, backend + frontend + QA), они выполняются ПОСЛЕДОВАТЕЛЬНО, а не параллельно:

```
backend → In Review → QA проверяет → frontend → In Review → QA проверяет → Done
```

Параллельный запуск backend и frontend на одну фичу допускается ТОЛЬКО если они работают в разных файлах/модулях и это явно указано координатором.

### Правило 3: Координатор проверяет статус перед запуском

Перед тем как дать задачу агенту, координатор обязан:

1. Проверить статус задачи в Jira
2. Убедиться, что нет активного агента на этой задаче
3. Проверить комментарии — нет ли незавершённой работы

### Правило 4: Агент фиксирует начало и конец работы

Каждый агент при получении задачи:

1. Переводит задачу в "В работе" (если ещё не переведена)
2. Оставляет комментарий `AGENT_ROLE: начал работу`
3. По завершении — комментарий `AGENT_ROLE: работа завершена` + коммит
4. Переводит в "In Review" или "Done"

### Правило 5: QA работает только с финальным состоянием

QA-агент запускается ПОСЛЕ того, как разработчик (frontend/backend) завершил работу и перевёл задачу в "In Review". QA не запускается параллельно с разработкой.

## Последствия

### Положительные
- Устраняются конфликтующие изменения
- Устраняются противоречащие отчёты QA
- Каждый агент работает с актуальным состоянием кода
- Прекращаются бесконечные циклы исправлений

### Отрицательные
- Последовательное выполнение медленнее параллельного
- Требует дисциплины от координатора

### Компромисс
Скорость приносится в жертву корректности. Для проекта с одним разработчиком это приемлемо — параллельность создаёт больше проблем, чем решает.

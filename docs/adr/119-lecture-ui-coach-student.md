# ADR-119: Пользовательский интерфейс лекций — единый жизненный цикл для тренера и ученика

**Статус:** Принято к реализации (после ревью координатором)
**Дата:** 2026-06-08
**Задача:** KS-3928
**Связанные ADR:** [ADR-110](./110-live-analysis-broadcast.md), [ADR-113](./113-coach-page.md), [ADR-115](./115-lecture-audio-recording.md), [ADR-116](./116-lecture-audio-p2p.md), [ADR-117](./117-lecture-student-tools-policy.md), [ADR-118](./118-lecture-access-control.md)

## 1. Контекст

### 1.1 Что есть сейчас

Интерфейс работы с лекциями сложился органически вокруг отдельных задач:

- **Создание** — `CreateLectureModal`
  (`apps/web/src/components/analysis/CreateLectureModal.tsx`, KS-3911 / ADR-117 B01):
  модалка, открывается из `AnalysisActionsMenu` на странице анализа. Тренер вводит
  название, выбирает чекбоксами доступные инструменты, отправляет `POST /lectures`.
  После успеха — переход на `/live/:slug` (live-view зрителя, тренер видит ту же
  страницу с publisher-controls).
- **Публичный профиль тренера** — `/coach/:username` (ADR-113): список public-лекций,
  расписание, ссылки на отдельные карточки. Список рендерится через
  `GET /coaches/:username/lectures` (только `public`).
- **Live-view зрителя** — `LiveAnalysisViewerPage` на маршруте `/live/:slug`,
  оборачивает `AnalysisPage` в режиме `liveSession={mode:'viewer'}`.
- **Воспроизведение записи** — `LectureReplayPage` на маршруте `/lectures/:id`
  (KS-3794, ADR-113 §4): `GET /lectures/:id` + `GET /lectures/:id/recording`,
  передача `replay.currentTimeMs` в `AnalysisPage`. Управление: play/pause, seek,
  скорость ×1/×1.5/×2.
- **Настройки инструментов** — `LectureToolsSettingsModal`
  (`apps/web/src/components/lecture/LectureToolsSettingsModal.tsx`, KS-3912 / ADR-117 B02):
  открывается из `AnalysisActionsMenu` для владельца, чекбоксы «разрешено», PATCH.
- **Publisher controls** — `LecturePublisherControls`: виджет управления live для
  тренера (start/stop запись, аудио-канал из ADR-116).

### 1.2 Что не сложено в систему

- **Нет страницы «мои лекции».** Тренер не видит свои лекции в одном месте — только
  через свой публичный профиль `/coach/:username` (где только `public` и без
  служебных статусов: scheduled, cancelled).
- **Нет страницы для ученика «доступные мне лекции».** Ученик попадает на лекцию
  только по прямой ссылке от тренера.
- **`/lectures/:id` сегодня = воспроизведение записи**, а должен быть универсальной
  «карточкой лекции» (landing): описание, статус, CTA (смотреть live / запись /
  ждать начала / записаться). Жёсткое перенаправление в replay делает мёртвыми
  ссылки на `scheduled` и `live`-лекции.
- **Управление доступом** (ADR-118) пока никуда не встроено в UI — нет места, где
  тренер видит allowlist и редактирует его.
- **Поток создания через модалку анализа** — нестандартный для большинства SaaS:
  пользователь ожидает «создать лекцию» из меню кабинета лекций, а не из меню
  страницы анализа. Текущий поток рабочий, но затрудняет создание лекции «с
  нуля» (без открытой партии). Дать оба входа.
- **Разные модалки настроек** (инструменты — ADR-117, доступ — ADR-118) — без
  единой точки управления лекцией. Тренер должен из одного места видеть и менять
  все её атрибуты.

### 1.3 Что нужно

ADR описывает целевой пользовательский интерфейс лекций — единое представление
жизненного цикла для тренера (создать → провести → завершить → поправить → удалить)
и ученика (найти → открыть → смотреть → вернуться). С опорой на:

- модель доступа из ADR-118 (`public | unlisted | restricted` + allowlist);
- настройки инструментов из ADR-117 (`disabledTools`);
- существующие сущности `Lecture`, `LiveAnalysis`, `LectureRecording`, `LectureAudio`.

### 1.4 Принципы

1. **Минимум кликов до основного действия.** Открыть лекцию для просмотра — один
   клик из кабинета. Создать — один клик из меню. Начать live — один клик с карточки
   `scheduled`-лекции.
2. **Семантическая чистота.** Одна сущность — одно название. «Лекция», не «трансляция»
   / «эфир» / «вебинар». Статусы — единый набор `scheduled | live | recorded |
   cancelled`, без UI-синонимов.
3. **Универсальный URL.** `/lectures/:id` всегда работает: переадресует на нужный
   подвид по статусу, не «404» для scheduled, не «landing вместо replay».
4. **Симметрия ролей.** У тренера и ученика — одинаковая ментальная модель: и тот,
   и другой имеют «свой список лекций», страницу карточки лекции, страницу
   просмотра. Разница — наполнение и CTA.
5. **Mobile-first для просмотра.** Доска + видео/аудио — это `LiveAnalysisViewerPage`
   и `LectureReplayPage`, оптимизированы под мобильный. Управление (тренерское) —
   допускается desktop-приоритет, но базовый mobile-вид должен быть рабочим.

### 1.5 Ограничения

- Один разработчик, итеративная поставка.
- Не ломаем существующие маршруты `/coach/:username`, `/lectures/:id`, `/live/:slug`.
- Не вводим новых сервисов / больших миграций — этот ADR про UI, модель данных
  меняется через ADR-117 и ADR-118.
- Стиль и компоненты — существующие из проекта (UI-кит уже сложен, не вводим
  параллельный design system).

### 1.6 Что НЕ в скоупе

- Push / e-mail уведомления о live-лекции — отложено, отдельная задача.
- Закладки и заметки ученика к ключевым моментам записи — отложено.
- Аналитика посещаемости для тренера — отложено.
- Полноценный курс (`Course`) и enrollment — отложено (см. ADR-118 §1.2).
- Чат во время лекции — отложено (нет инфраструктуры).
- Любые платные / monetisation-аспекты.

## 2. Карта маршрутов

Текущие маршруты сохраняются, добавляются новые. `/lectures/:id` меняет роль:
вместо жёсткого replay становится «умной» страницей-роутером по статусу.

| Маршрут | Кому | Что внутри |
| --- | --- | --- |
| `/coach/:username` | Все (без auth) | Публичный профиль тренера. Список `public`-лекций (live + recorded + ближайшие scheduled). Расписание. **Сохранён.** |
| `/lectures` | Аутентифицированные | «Кабинет лекций» — единый список. Тренер видит свои (все статусы); ученик — те, к которым есть allowlist-доступ + `public` подписки тренеров (последний пункт — задел, см. §3.5). **Новый.** |
| `/lectures/:id` | Зависит от visibility/access | **Меняет поведение.** Landing-страница лекции: мета (название, описание, тренер, статус, scheduled-время, длительность), CTA по статусу. Старые прямые ссылки на recorded не ломаются — landing для recorded предлагает «Смотреть запись» сразу, далее `/lectures/:id/replay`. |
| `/lectures/:id/live` | Зависит от access | Live-просмотр. Если `status≠live` → 404 / редирект на `/lectures/:id`. Сегодня эту роль фактически играет `/live/:slug`; маршрут оставляем как параллельный для совместимости (см. §6.1). |
| `/lectures/:id/replay` | Зависит от access | Воспроизведение записи. Сегодня — это `/lectures/:id`; делаем оба URL рабочими, старые ссылки не ломаем (см. §6.1). |
| `/lectures/:id/edit` | Owner only | Не отдельный маршрут — модалка `LectureSettingsModal`, открывается с `/lectures/:id`. Можно поддержать deep-link `?modal=settings` для UX «поделился ссылкой на нужный раздел». |
| `/lectures/:id/unavailable` | Все | Страница «лекция больше не доступна» (ADR-118). Reason берётся из query `?reason=auth_required|revoked|not_found`. **Новый.** |
| `/live/:slug` | Все | Live-просмотр по slug LiveAnalysis. **Сохранён** для совместимости и для случаев «трансляция без лекции» (если такие есть). |

**Стратегия совместимости** для `/lectures/:id`:
- Запрос на `/lectures/:id` → fetch `LectureDetail` → роутинг в коде страницы:
  - `status='recorded'` и есть `recordingId` → автоматический redirect на
    `/lectures/:id/replay`, **либо** показать landing с большой кнопкой «Смотреть
    запись» (см. §3.2, решение — landing+CTA, чтобы тренер видел свои настройки,
    а ученик — описание).
  - `status='live'` → redirect на `/lectures/:id/live` (или show CTA «Подключиться»).
  - `status='scheduled'` → показать landing с «Лекция начнётся в HH:MM».
  - `status='cancelled'` → landing с «Лекция отменена».

Аккуратное поведение для старых deeplink'ов: тренер раздавал ссылки `/lectures/:id`
на запись — пользователь после ADR-119 кликает и автоматически попадает в replay
(после короткой landing-страницы или сразу — выбираем в реализации, см. §3.2).

## 3. User flows

### 3.1 Тренер — флоу

#### F1. Создать лекцию с нуля (из кабинета)

```
/lectures → кнопка «Создать лекцию» в правом верхнем углу
→ модалка CreateLectureModal (см. §4.1)
  → поля: название, описание (опционально), запланированная дата (опционально),
    видимость (public | unlisted | restricted),
    если restricted — кнопка «Добавить учеников» с поиском,
    чекбоксы доступа к инструментам
  → «Создать» → POST /lectures → редирект на /lectures/:id (новая, status=scheduled)
```

#### F2. Создать лекцию из открытой партии (текущий поток)

```
/analysis/:id → AnalysisActionsMenu → пункт «Создать лекцию»
→ та же модалка с предзаполненным `analysisId`
→ создание → редирект на /lectures/:id с привязанным analysisId
```

Сохранение текущего потока — важно, тренер может создавать лекцию «по поводу этой
позиции» в одно действие. Оба входа (F1 и F2) ведут к **одной** модалке.

#### F3. Открыть «свои лекции»

```
/lectures → таблица:
  фильтры: статус (scheduled / live / recorded / cancelled), видимость
  колонки: название, статус, аудитория (sm. §3.4), дата, действия (⋮)
  сортировка: по умолчанию — обновлённые сверху
  выделение текущего live: бейдж «В эфире» + цвет
```

#### F4. Запустить scheduled-лекцию (start live)

```
/lectures → строка scheduled → кнопка «Начать»
ИЛИ /lectures/:id (landing) → большая CTA «Начать лекцию»
→ POST /lectures/:id/start → редирект на /lectures/:id/live (тренерский режим)
  → AnalysisPage с liveSession.mode='owner' + LecturePublisherControls
```

#### F5. Управление доступом в эфире

```
В тренерском live-режиме (/lectures/:id/live) — кнопка «Доступ учеников»
  в правой панели управления (или в AnalysisActionsMenu, см. §4.3)
→ открывается LectureAccessPanel (модалка или sliding sheet, см. §4.2)
  - радио visibility, текущий allowlist в виде chip'ов
  - кнопка «+ Добавить» → инлайн-поиск пользователей
  - X на chip'е — мгновенный DELETE (с подтверждением, опционально)
→ изменения применяются сразу: revoke-события доходят до live-зрителей за ≤1 сек
```

#### F6. Завершить live

```
LecturePublisherControls → кнопка «Завершить»
→ подтверждение → POST /lectures/:id/force-end
→ status → recorded, редирект на /lectures/:id/replay (или landing, см. §3.2)
→ запись доступна сразу (events + audio уже сохранены)
```

#### F7. Поправить настройки уже recorded-лекции

```
/lectures → строка recorded → ⋮ → «Настройки»
ИЛИ /lectures/:id → кнопка «Настройки» (видна владельцу)
→ LectureSettingsModal — единая модалка с табами:
   • Основное: название, описание
   • Доступ: visibility + allowlist (как F5)
   • Инструменты: disabledTools (как ADR-117 §2.4)
→ изменения: для recorded видны при следующем открытии замены ученика
```

#### F8. Удалить лекцию

```
/lectures → строка → ⋮ → «Удалить»
→ модальное подтверждение «Удалить навсегда? Запись будет потеряна.»
→ DELETE /lectures/:id → исчезает из списка
```

#### F9. Поделиться ссылкой

```
/lectures/:id → кнопка «Поделиться»
→ popover: ссылка `/lectures/:id`, кнопка «Копировать»
→ опционально (для restricted) — «Добавить получателя в allowlist» инлайн
```

#### F10. Открыть свою публичную страницу

```
/lectures → ссылка «Мой публичный профиль» → /coach/:username (своя)
→ предпросмотр того, что видит ученик
```

### 3.2 Ученик — флоу

#### S1. Открыть «доступные мне лекции»

```
/lectures (ученик) → секции:
  • «Идут сейчас» — live, к которым есть доступ (allowlist или public)
  • «Запланированные» — scheduled от тренеров, к которым есть allowlist
  • «Записи» — recorded, к которым есть доступ
карточка лекции:
  название, тренер, статус, дата, превью доски (если есть)
клик по карточке → /lectures/:id
```

#### S2. Зайти по ссылке от тренера

```
Получил `/lectures/L1` в мессенджере → открыл
→ если auth и есть доступ → landing (см. F3 для тренера, тут для ученика)
→ если auth нет → /lectures/L1/unavailable?reason=auth_required
  → «Войдите, чтобы продолжить» + кнопка → /login?returnTo=/lectures/L1
→ если auth есть и доступа нет → /lectures/L1/unavailable?reason=revoked
  → «Лекция больше не доступна. Обратитесь к тренеру» + кнопка «На главную»
```

#### S3. Подключиться к live

```
/lectures/:id (status=live) → большая CTA «Подключиться»
→ /lectures/:id/live → AnalysisPage (mode=viewer) + LectureAudioListener
→ при revoke в эфире → overlay «Доступ отозван» + редирект unavailable
```

#### S4. Смотреть запись

```
/lectures/:id (status=recorded) → CTA «Смотреть запись» → /lectures/:id/replay
→ LectureReplayPage: play/pause, seek, speed
→ при попытке снова открыть после revoke → unavailable
```

#### S5. Вернуться к ключевому моменту

Заметки и закладки — follow-up, не в этом ADR. Базовое поведение: URL с
fragment `#t=120` → seek на 120-ю секунду при загрузке. Реализуется парсингом
`window.location.hash` в `LectureReplayPage`.

#### S6. Получить уведомление о live-лекции

Push/email — follow-up. На момент ADR-119 — никаких уведомлений (ученик сам
заходит в `/lectures` и видит «идёт сейчас»).

  кнопки «Сохранить». Toast «Сохранено» / «Ошибка».
- `[✕]` на ученике — `DELETE /lectures/:id/access/:userId`, мгновенно убирает chip.
  Если лекция live — revoke-event уходит зрителю.
- Поиск debounced 200 мс, минимум 2 символа.
- Если выбрана видимость `public` или `unlisted` — список allowlist'а отображается
  серым с пояснением «Действует только при «По списку». Сохранён на случай
  возврата».

## 6. Решения и обоснования

### 6.1 `/lectures/:id` — landing vs. немедленный replay

**Решение:** `/lectures/:id` — это landing. Для `recorded` лекции на landing'е
большая CTA «Смотреть запись», ведёт на `/lectures/:id/replay`. Старый замысел
«`/lectures/:id` сразу открывает запись» переезжает на `/replay`.

**Почему не редирект сразу:**
- Тренер хочет видеть свою лекцию: статус, доступ, кнопку «Настройки», «Поделиться»,
  «Удалить» — отдельно от плеера.
- Ученик хочет видеть описание лекции до начала просмотра — что внутри.
- Для `scheduled` и `live` — landing уже необходим, держим симметрию.

**Совместимость старых ссылок:** ссылки `/lectures/L1`, которые тренер раздавал
раньше для замечания записи, продолжат работать — пользователь видит карточку с
описанием и одним кликом «Смотреть запись» попадает в плеер. Поведение чуть
другое (один лишний клик), но не сломано.

**Альтернативный вариант** (отвергнут): «`/lectures/:id` для recorded автоматически
редиректит на `/replay`, для scheduled/live — landing». Несимметрично, требует
extra-логики в роутере. Если в ходе реализации UX-метрики покажут, что «один лишний
клик» — фрустрация, переключим на автоматический redirect через query-flag.

### 6.2 `/live/:slug` vs `/lectures/:id/live`

Сегодня live-просмотр привязан к slug `LiveAnalysis`, а не к ID лекции. Это
исторический артефакт ADR-110 (live-analysis жил до lecture-сущности из ADR-113).

**Решение:** оставить **оба** маршрута, рабочих параллельно:
- `/live/:slug` — для трансляций без лекции (если в будущем кто-то открывает live-сессию вне контекста лекции) и для совместимости.
- `/lectures/:id/live` — каноничный URL для live-лекции. Внутри страница берёт
  `lecture.liveAnalysisId.slug` и передаёт в `LiveAnalysisViewerPage`.

Со временем (отдельный refactor) можно унифицировать на `/lectures/:id/live`,
если live-сессии без лекции окажутся неактуальными.

### 6.3 Дефолт `visibility` для новых лекций

Сегодня — `public`. Менять дефолт сейчас — поломать ожидание тренеров, у которых
workflow «создал → лекция в публичном списке».

**Решение:** оставить `public` дефолтом. В `CreateLectureModal` явно показывать
выбранный уровень (радио сверху секции «Кто видит»), чтобы тренер видел и
переключал осознанно. Если по факту окажется, что большинство тренеров каждый раз
переключают на `restricted` — пересмотрим дефолт в отдельной задаче (или сделаем
«запомнить последний выбор пользователя»).

### 6.4 Единая модалка vs. отдельные

Раньше — две отдельные модалки (создание + инструменты). После ADR-119 — единая
`LectureSettingsModal` с тремя табами для post-creation редактирования; для
создания — отдельная `CreateLectureModal` (т.к. контекст совсем другой: «новая»
vs. «редактировать»).

Симметрия табов в edit-модалке (Основное / Доступ / Инструменты) и секций в
create-модалке (тоже основное → доступ → инструменты) — единый ментальный
шаблон.

### 6.5 Уведомления — НЕ в этом ADR

Push-уведомления, e-mail о live-лекции, напоминания за 10 минут до scheduled —
отдельный пласт (Service Worker, web-push, шаблоны писем, бэкенд-планировщик).
Не в скоупе ADR-119. Базовый replacement: ученик заходит в `/lectures`, видит
секцию «Идут сейчас». Этого достаточно для MVP.

### 6.6 Mobile-приоритет

Просмотровые страницы (`/lectures/:id/live`, `/lectures/:id/replay`) — главный
mobile-вход (ADR-117 §2.5 уже учёл mobile-вкладки сайдбара). Кабинет `/lectures`
и landing `/lectures/:id` — адаптируются по существующим breakpoint'ам:
- > 1024 px — таблица в кабинете, две колонки на landing'е.
- < 1024 px — карточный лейаут, один столбец, табы вместо колонок.

Модалки доступа и настроек на мобильном — sliding sheet (снизу), не центрированный
overlay (используем существующий пресет UI-кита).

  (для миниатюры доски на landing'е): для `live` — `LiveAnalysis.currentFen`,
  для `recorded` — стартовый FEN из `LectureRecording.events[0]`, для `scheduled` —
  null. Зашить в `GET /lectures/:id` и `GET /my/lectures`.
- **KS-F02 [backend]** — `LectureSummary.viewerCount?: number` для live (текущее
  число подключенных через `LiveAnalysisGateway`). Опционально, чтобы тренер
  видел «в эфире сейчас N учеников». Без этого MVP работает.

### Эпик G — QA (KS-3928-G)

- **KS-G01 [qa]** — Создать лекцию из `/lectures` (F1): попадает в кабинет с
  выбранными статусом и видимостью. Создать из `/analysis/:id` (F2): сохраняется
  привязка к analysisId.
- **KS-G02 [qa]** — Изменить доступ public → restricted из `/lectures/:id` →
  модалка «Настройки» → таб «Доступ» → добавить ученика → у ученика появляется
  в его `/lectures`.
- **KS-G03 [qa]** — Запустить scheduled-лекцию из кабинета → попадает в режим
  тренера-publisher'а; URL — `/lectures/:id/live`.
- **KS-G04 [qa]** — Зритель в эфире, тренер дёргает «удалить из allowlist'а» —
  у зрителя ≤1 сек overlay + редирект на unavailable.
- **KS-G05 [qa]** — Старая ссылка `/lectures/L1` на recorded-лекцию: открывается
  landing с большой кнопкой «Смотреть запись», клик → `/lectures/L1/replay`.
- **KS-G06 [qa]** — Mobile-сценарии: кабинет рендерится карточками; модалка
  настроек — sliding sheet; landing на узком экране.
- **KS-G07 [qa]** — Регрессия: существующие маршруты `/coach/:username`,
  `/live/:slug` работают как раньше.
- **KS-G08 [qa]** — Семантика статусов: статусы во всех местах названы одинаково;
  бейджи цветом совпадают между кабинетом и landing'ом.

### Карта зависимостей

```
ADR-118 (модель и API доступа) ──┐
                                  ├─→ C (UI доступа)
ADR-119 A (роутер) ──→ B (кабинет)│
                       │           ├─→ D (revoke handling)
                       └──→ C ─────┘
                                    │
              E (layout) — параллельно
              F (backend extras) — параллельно
              G (QA) — после A/B/C/D
```

Минимально-полная серия для первой выкатки: ADR-118 эпики A+B+C+D, ADR-119 эпики
A+B (без C — UI создания/редактирования доступа), показывает кабинет с фильтром
по статусу и landing-страницу. Затем — эпик C ADR-119 (управление доступом
тренера) и D (revoke handling).

## 9. Риски и подводные камни

1. **Старые внешние ссылки `/lectures/:id` на запись** — после изменения роли
   `/lectures/:id` на landing они продолжат работать, но потребуют один лишний
   клик. Альтернативно — автоматический redirect для `recorded`-статуса.
   Решение: следим за метриками, при росте «bounce» на landing — переключим
   на auto-redirect (см. §6.1).

2. **`/lectures` для ученика без allowlist'а** — пустой кабинет, неинформативный.
   Решение: пустое состояние с пояснением «Здесь появятся лекции, к которым
   тренер откроет вам доступ» и кнопкой «Найти тренеров» (ведёт на `/coaches` или
   главную). Если тренеров пока нет — пустое состояние без второй кнопки.

3. **Контекст «тренер vs ученик» в `/lectures`** — на момент ADR-119 в БД нет
   роли. Решение в KS-B04: показываем обе секции, тренерская по умолчанию пустая.
   Когда появится явная роль или флаг — упрощаем.

4. **Дублирование `LectureToolsSettingsModal` и таба «Инструменты»** в
   `LectureSettingsModal`. Совместимость: старая модалка остаётся как **внутренний
   рендер** (компонент тот же, обёртка разная). Никакого дубля кода — оба входа
   используют один `LectureToolsForm`.

5. **`/lectures/:id/live` vs `/live/:slug`** — две точки входа на один контент.
   SEO-конфликта нет (страницы non-indexable для restricted), но возможна
   путаница в analytics. Решение: внутренний нативный redirect с `/live/:slug`
   на `/lectures/:id/live` если slug привязан к лекции — оставляем follow-up,
   не блокирующий ADR.

6. **Mobile sliding-sheet — анимация и backdrop** — UI-кит должен это уметь.
   Если нет — fallback на центрированную модалку (хуже UX, но рабочий). Layout
   эпик E решает.

7. **Поиск пользователей `GET /users/search`** — privacy: любой авторизованный
   видит чужие профили. Это уже верно для существующих `/coach/:username`-ссылок.
   Дополнительный фильтр «только тех, кто разрешает приглашения» — отдельная
   задача (см. ADR-118 §6.9).

8. **Сценарий «два владельца одной лекции»** не предусмотрен. `Lecture.ownerId`
   — single FK. Co-coaching — отдельная задача, в данный момент UI исходит из
   «один тренер на лекцию».

9. **Большое количество allowlist-учеников** (>100): chip-список начинает плохо
   читаться. Решение: при `count > 10` — свернуть в «10 показаны + ещё N»,
   разворот по клику с виртуализацией. В первой итерации не делаем —
   реальный bottleneck при 100+ учениках, пока «хочу видеть лекцию у конкретных
   пятерых» — типовой сценарий.

10. **Live-страница тренера vs зрителя** на одном URL `/lectures/:id/live` —
    различаем по `lecture.ownerId === currentUser.id`. Если хочется
    «предпросмотр глазами ученика» (тренер открывает свою лекцию как зритель) —
    добавить query `?as=viewer` (follow-up).

## 10. Связь с соседними ADR

- **ADR-113** — основа: `Lecture` со статусами и видимостью. UI ADR-119 надстраивает
  кабинет и landing над этой моделью.
- **ADR-117** — настройки инструментов. Интегрируются как таб «Инструменты» в
  `LectureSettingsModal`; точка входа из `AnalysisActionsMenu` переключается.
- **ADR-118** — модель доступа. UI ADR-119 потребляет её API (`GET /my/lectures`,

  страницу `/lectures/:id/unavailable`.
- **ADR-116** — аудио. `LectureAudioListener`/`LectureAudioListenerCompact` уже
  встроены в `LiveAnalysisViewerPage` и `LectureReplayPage`, ADR-119 их не
  трогает.
- **ADR-110/111/112** — транспорт live, без UI-изменений.

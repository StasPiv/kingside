# ADR-083. Двухфазная генерация precision-puzzle — дешёвый отсев + глубокий анализ кандидатов

Статус: предложен (2026-05-28)
Связано: KS-3385 (этот ADR), ADR-068 (deltaW/deltaD), ADR-069
(objective convert/save), ADR-070 (унифицированный pipeline в
shared). Baseline-прогон `b22d154` (14.3 сек/позиция при 10M nodes).

## 1. Контекст

Текущий генератор (`packages/shared/src/utils/puzzle-gen-pipeline.ts`)
на КАЖДЫЙ ply делает до двух прогонов Stockfish по 10M nodes
(~14 сек каждый):

1. `pre = analyze(fenBefore, multiPV=2)` → PV1 (правильный ход) +
   `wdlBefore` POV зевнувшего.
2. `samePv1`-чек: если сыгранный = PV1 — не зевок, drop без post.
3. `post = analyze(fenAfter, multiPV=2)` → `wdlAfter` POV соперника.
4. `evaluateBlunder(wdlBefore, wdlAfter)` → accept/reject по
   deltaW/deltaD (ADR-068).

Стоимость: N ply × ~1.7 прогона × 14 сек. Для партии ~70 ply ≈
**28 минут**; полный проход по базе — ~22 часа (KS-3385).

Снижать nodes-лимит на ВСЕХ позициях нельзя — теряется точность
WDL-классификации зевка (пользователь это отверг). Но: **зевки
редки** (обычно ≤ 15% ply дают реальный delta-swing), а 10M тратится
на 100% позиций, из которых 85%+ — заведомо не зевки.

### Ключевое наблюдение

`fenAfter` ply=i == `fenBefore` ply=(i+1). Сейчас эта позиция
анализируется **дважды** (как post для i, как pre для i+1). При
последовательном проходе партии eval каждой уникальной позиции
можно посчитать **один раз**.

## 2. Решение — двухфазная схема

### Фаза 1 — cheap screen (по всем позициям, single-pass)

Дешёвый Stockfish (низкий nodes-лимит) проходит партию ОДИН раз,
строит eval-кривую (по одной оценке на уникальную позицию). По
кривой грубо оценивается delta WDL каждого хода. Позиции с явно
малым swing'ом — отбрасываются. Остальные → кандидаты фазы 2.

### Фаза 2 — deep confirm (только кандидаты)

На отобранных кандидатах — текущая `analyzePlyForBlunder` (pre+post
10M, samePv1, evaluateBlunder, buildPuzzlesFromCandidate). Без
изменений в логике классификации — точность сохраняется полностью.

## 3. Фаза 1 — cheap screen (детали)

### 3.1 Single-pass eval-кривая

```
positions = [startFen, fenAfterPly1, fenAfterPly2, ..., fenAfterPlyN]
evalCurve[k] = screenEngine.analyze(positions[k], multiPV=1, cheap)
              → wdl, нормализованный к POV white
```

Каждая уникальная позиция анализируется один раз. Это уже ~2×
экономия против текущего дублирования pre/post.

`screenEngine` — отдельная обёртка с низким лимитом
(`screenNodeLimit`, см. §5). multiPV=1 (нам не нужен PV2 для
screen — только грубый eval).

### 3.2 Грубая оценка swing'а хода

Для ply=i:
- `wBefore` = `evalCurve[i-1]` приведён к POV зевнувшего (side-to-move
  на fenBefore).
- `wAfter` = `evalCurve[i]` приведён к POV того же зевнувшего
  (инверсия, т.к. на fenAfter ходит соперник).
- `approxDeltaW = wBefore.w − wAfter.w` (падение вероятности выигрыша
  зевнувшего, в той же шкале что `evaluateBlunder.deltaW`).

### 3.3 Консервативный порог (главное)

Дешёвый анализ (200K nodes, depth ~14) менее точен — eval/WDL шумит
относительно 10M. Чтобы НЕ терять реальные зевки (false negatives),
порог фазы 1 берётся с **запасом** (margin):

```
кандидат фазы 2 ⟺ approxDeltaW ≥ (deltaWThreshold − screenDeltaMargin)
```

- `deltaWThreshold` — реальный порог зевка (фаза 2, текущая
  настройка ADR-068, например 0.25).
- `screenDeltaMargin` — запас, покрывающий максимальную ошибку
  дешёвого анализа (например 0.15 → пропускаем всё, где
  approxDeltaW ≥ 0.10).

`screenDeltaMargin` — **эмпирический параметр**, подбирается
калибровкой (§7) под целевой recall ≥ 99%.

Дополнительно — **не дропаем по samePv1 в фазе 1**: дешёвый движок
может ошибиться в лучшем ходе, samePv1-фильтр остаётся только в
фазе 2 (на 10M). Фаза 1 — чистый delta-screen.

### 3.4 Что НЕ делает фаза 1

- Не строит пазлы (только отбор кандидатов).
- Не определяет objective/themes/rating.
- Не пишет в БД.
- Не дропает по samePv1 / lowWplusDAfter (это фаза 2).
- Не использует multiPV=2.

## 4. Фаза 2 — deep confirm

На кандидатах из фазы 1 — текущий `analyzePlyForBlunder` БЕЗ
изменений: pre(fenBefore, 10M, mPV2) + post(fenAfter, 10M, mPV2) +
samePv1 + evaluateBlunder + buildPuzzlesFromCandidate.

Точность классификации = 100% от текущей (тот же deep-анализ на
тех же позициях). Двухфазность влияет ТОЛЬКО на то, какие позиции
доходят до deep-анализа, не на сам анализ.

## 5. Параметры

| Параметр | Назначение | Стартовое значение |
|---|---|---|
| `screenEnabled` | вкл/выкл фазы 1 (rollback-флаг) | true |
| `screenNodeLimit` | nodes для дешёвого прогона | 250_000 (калибровка) |
| `screenMultiPV` | multiPV фазы 1 | 1 |
| `screenDeltaMargin` | запас порога фазы 1 | 0.15 (калибровка) |
| `deepNodeLimit` | nodes фазы 2 (= текущий) | 10_000_000 |

`screenNodeLimit` и `screenDeltaMargin` — финализируются
калибровкой (§7). nodes (не depth) — для детерминизма и
воспроизводимости тестов между прогонами/железом.

## 6. Оценка выигрыша

Грубая модель (партия ~70 ply):

**Baseline:** 70 × 1.7 прогона × 14 сек ≈ **1666 сек** (~28 мин).

**Двухфазная:**
- Фаза 1: 70 уникальных позиций × (14 сек × 250K/10M) ≈ 70 × 0.35 ≈
  **~25 сек**.
- Фаза 2 при отсеве 85% → ~10 кандидатов × 2 × 14 = **280 сек**.
- Итого ≈ **305 сек** (~5 мин).

**Выигрыш ≈ 5.5×.** При отсеве 90% (~7 кандидатов) — фаза 2 = 196
сек, итого ~221 сек → **~7.5×**.

Точная цифра зависит от реального % отсева и `screenNodeLimit` —
финализируется калибровкой. Полный проход ~22 ч → **~3–4 ч**.

## 7. Калибровочный эксперимент (обязательная часть реализации)

Без этого нельзя выбрать `screenDeltaMargin` / `screenNodeLimit`.

1. Выборка ~50–100 партий (репрезентативная: разные Elo, фазы).
2. **Эталон:** текущий pipeline (10M на всех) → множество
   «истинных» зевков `B_true` с их deep-deltaW.
3. **Фаза 1:** дешёвый проход на тех же партиях →
   `approxDeltaW` каждого ply.
4. Для каждого зевка из `B_true` — его `approxDeltaW` в фазе 1.
5. Построить **recall(margin)**: при каком `screenDeltaMargin`
   процент истинных зевков с `approxDeltaW ≥ (threshold − margin)`
   достигает 99% (и 99.5%).
6. Выбрать `screenDeltaMargin` с recall ≥ 99% + небольшой запас.
7. При выбранном margin замерить **% отсева** (доля ply, НЕ
   попавших в кандидаты) → фактический выигрыш.
8. Повторить для `screenNodeLimit ∈ {100K, 250K, 500K}` — выбрать
   минимальный лимит, дающий recall ≥ 99% при разумном отсеве.

Артефакт: `docs/qa/two-phase-puzzle-gen-calibration-<date>.md` с
кривыми recall и финальными значениями параметров. Решение по
запуску на проде — после ревью этого артефакта.

**Целевой recall ≥ 99%** (пользователь не хочет терять реальные
зевки). Если калибровка покажет, что для 99% нужен margin,
оставляющий 50%+ позиций в фазе 2 (выигрыш < 2×) — двухфазность
не оправдана, эскалируем (см. §8 риск 1).

## 8. Риски

1. **Низкий recall.** Дешёвый screen пропускает реальные зевки.
   Митигация: калибровка (§7) + консервативный margin. Если для
   99% recall выигрыш < 2× — фича не оправдана, останавливаемся и
   эскалируем (возможно нужен другой подход — например depth-based
   screen или incremental deepening).
2. **`screenNodeLimit` слишком низкий → шум.** Eval скачет, margin
   приходится задирать → много кандидатов → нет выигрыша.
   Калибровка перебирает несколько лимитов.
3. **POV-нормализация eval-кривой.** Ошибка в инверсии WDL для
   black-to-move → неверный approxDeltaW. Юнит-тест на
   нормализацию обязателен (фикстуры с известными WDL).
4. **Терминальные позиции (мат/пат)** в eval-кривой — screen
   должен корректно их помечать (как сейчас `isGameOverAfter`),
   не считать swing'ом «мат → нет хода».
5. **Зевок на стыке окна (ply=startPly).** evalCurve[i-1] для
   первого кандидата = позиция до startPly. Нужно анализировать
   на 1 позицию раньше startPly (захватить fenBefore первого
   рассматриваемого ply). Учесть в replay.
6. **Двойной engine (cheap+deep) в обёртке.** tactic-worker
   должен поднять два лимита. Stockfish-пул один — фазы идут
   последовательно (сначала весь screen партии, потом deep
   кандидатов), параллелизм внутри фазы через пул.
7. **Регрессия точности.** Фаза 2 не меняется → классификация
   идентична. Гарантия: на калибровочной выборке множество пазлов,
   построенных двухфазно ⊆ множества эталона (никаких «новых»
   ложных зевков, только потенциально пропущенные — что и меряет
   recall).

## 9. Реализация — follow-up задачи

Зависимости: S1 → B1 (калибровка) → S2 (финал параметров) → B2
(интеграция). B1 — эксперимент, его результат определяет S2.

### KS-3386 (S1) — screen-функция и расширение pipeline-контракта

**Assignee:** backend (shared owner).
**Labels:** `puzzle`, `performance`.
**Описание:**
- В `packages/shared/src/utils/puzzle-gen-pipeline.ts`:
  - Расширить `PuzzleGenSettings`: `screenEnabled`,
    `screenNodeLimit`, `screenMultiPV`, `screenDeltaMargin`.
  - Изменить контракт engine: принимать `{ screenEngine,
    deepEngine }` (две обёртки с разными лимитами) ИЛИ добавить
    `ctx.nodeLimit` в `PuzzleGenEngine.analyze`. Рекомендация —
    две обёртки (чище).
  - Новая функция `screenGameForCandidates(steps, screenEngine,
    settings): { candidatePlys: Set<number>; evalCurve: ... }` —
    single-pass eval-кривая + грубый approxDeltaW + отбор
    кандидатов по `(deltaWThreshold − screenDeltaMargin)`.
  - POV-нормализация WDL к white + инверсия для black-to-move.
**Acceptance:**
- Юнит-тесты: eval-кривая single-pass (каждая позиция 1 раз);
  POV-нормализация (4 фикстуры w/b to move); отбор кандидата при
  approxDeltaW ≥ порога; терминальная позиция не даёт ложный
  swing.
- `screenEnabled=false` → поведение идентично текущему (фаза 1
  пропускается, deep на всех).

### KS-3387 (B1) — калибровочный эксперимент

**Assignee:** backend.
**Labels:** `puzzle`, `performance`.
**Зависит:** KS-3386.
**Описание:**
- CLI-скрипт в `apps/tactic-worker` (или `scripts/`):
  на выборке 50–100 партий прогнать эталон (10M на всех) и фазу 1
  (cheap), собрать `approxDeltaW` для каждого истинного зевка.
- Построить recall(margin) для `screenNodeLimit ∈ {100K, 250K,
  500K}`.
- Выбрать минимальный (`screenNodeLimit`, `screenDeltaMargin`) с
  recall ≥ 99%.
- Замерить % отсева и фактический выигрыш по времени.
**Acceptance:**
- Артефакт `docs/qa/two-phase-puzzle-gen-calibration-<date>.md`:
  кривые recall, выбранные параметры, % отсева, замер времени
  до/после.
- Решение: оправдана ли двухфазность (recall ≥ 99% при выигрыше
  ≥ 2×). Если нет — эскалация в комментарий с альтернативами.

### KS-3388 (S2) — финализация параметров в shared-дефолтах

**Assignee:** backend (shared owner).
**Labels:** `puzzle`, `performance`.

### KS-3389 (B2) — интеграция двухфазности в tactic-worker

**Assignee:** backend.
**Labels:** `puzzle`, `performance`.
**Зависит:** KS-3388.
**Описание:**
- В `apps/tactic-worker` обёртке: поднять `screenEngine` (cheap
  лимит) + `deepEngine` (10M). `processGameForPuzzles` сначала
  `screenGameForCandidates`, потом `analyzePlyForBlunder` только
  на `candidatePlys`.
- Телеметрия: лог `screened=N candidates=K dropRate=% phase1Sec=
  phase2Sec=` per game.
- `screenEnabled` за конфигом (rollback без redeploy если есть
  механизм; иначе env).
**Acceptance:**
- Прогон на тестовых партиях: выход двухфазного ⊆ эталона
  (нет ложных новых зевков); recall ≥ 99% (сверка с эталоном).
- Замер времени подтверждает выигрыш из калибровки (±20%).
- Телеметрия в логе.
- `screenEnabled=false` → старое поведение (safety).

## 10. Откат

- `screenEnabled=false` — фаза 1 пропускается, deep-анализ на всех
  позициях (текущее поведение). Полный rollback без миграций.
- Параметры в shared-дефолтах — изменение значения не ломает
  контракт.
- Фаза 2 (классификация) не трогается — нет риска для качества
  существующих/будущих пазлов.

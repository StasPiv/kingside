# ADR-169: Поиск похожих позиций по вектору («проверка глазами») — второй индекс над корпусом позиций

**Дата:** 2026-07-21
**Статус:** Предложено
**Задачи:** KS-4991 (ADR); вытекают backend (конвейер + индекс + запрос) и devops (pgvector)
**Связанные ADR:** 168 (представление позиции из скрытого слоя Lc0 — **подтверждён**, источник конфигурации), 028/033 (архив: хранение и интерфейс), by-position (`archive_position_stats` — точный FEN-поиск)

---

## 1. Контекст и цель

ADR-168 подтвердил: скрытый слой сильной трансформерной сети Lc0 даёт пригодное пространство похожести позиций (тест «зевок дальше тихого» ×4.25). Следующий шаг — **проверка глазами**: положить вектора в базу и по заданной позиции находить 5 наиболее близких.

Формулировка задачи (от пользователя): у нас есть база позиций, над ней уже построен один индекс — **точный по FEN** (`archive_position_stats`, поиск на равенство/транспозиции). Добавляем над тем же корпусом **второй индекс — по вектору** (поиск на расстояние, приближённые ближайшие соседи). База одна, индекса два. Это разные типы индексов; первый не расширяется во второй.

Границы: это **внутренняя проверка гипотезы**, не готовая пользовательская функция. Цель — увидеть качество соседей своими глазами, а не выкатить продукт.

## 2. Решения

### 2.1 Корпус (что индексируем)
Для «глазами» — **подмножество мастер-партий**, ~50–200k позиций (замер §3 показывает: это минуты работы). Отдельный набор сильных партий (PGN), НЕ полный прод-архив (~500k партий ≈ ~40 млн позиций).
Обоснование: для оценки качества нужна вариативность и сила партий, а не полный объём; отдельный набор не трогает прод-таблицы архива.
Полное индексирование прод-архива — **отдельное, более позднее решение** (после подтверждения качества глазами).

### 2.2 Хранение и индекс
- **pgvector** в Postgres. Новая таблица `position_embedding`: `id`, ключ позиции (FEN/хеш), ссылка на партию/источник, `vector vector(256)`.
- Метрика — **косинус** (как в PoC). Размерность — **256** (d_model сети t1-256x10, усреднение по клеткам).
- Индекс приближённых соседей pgvector (HNSW или IVFFlat) по косинусу — параметры подбираются на этапе реализации.

### 2.3 Кодировщик (где считать вектор)
Конфигурация — из ADR-168 §9: сильная трансформерная сеть Lc0, глубокий слой encoder, усреднение по клеткам, извлечение `leela2onnx → ONNX → onnxruntime`, CPU.

Два места вычисления:
- **Построение индекса (офлайн, разовое):** пакетный прогон корпуса. Переиспользуем PoC-инструмент `tools/poc-adr168-lc0-embedding/`.
- **Вектор запроса (на каждый запрос):** нужен один прямой проход ONNX. API сейчас ML-движок не держит.
  **Рекомендация для фазы «глазами»:** отдельный лёгкий **сервис-кодировщик** (или внутренний скрипт/утилита), а не встраивать onnxruntime в основной API. Если функция дорастёт до пользовательской — вернуться к вопросу (чистая форма для прод — сайдкар-сервис кодировщика).

### 2.4 Маршрут
Внутренний маршрут `GET /positions/similar?fen=…` → топ-5 (позиция + ссылка на партию/источник), рядом с `by-position`. На фазе «глазами» допустим внутренний/админский доступ, без публичного UI.

### 2.5 Инвариант согласованности
Нормализация перспективы «к ходу» и `HistoryFill=fen_only` применяются **идентично** при построении индекса и при запросе. Иначе расстояния бессмысленны (см. ADR-168 §5 — главная ловушка). Это жёсткое требование к обеим стадиям.

## 3. Замер стоимости (факт)

Сеть t1-256x10, ONNX+onnxruntime, 16-ядерная машина:
- **~176 позиций/с** в один процесс (4 потока); вектор — 256 чисел;
- за 5 минут один процесс — **~53k позиций**; на всех ядрах (~4 процесса) — ориентировочно **~150–200k позиций**;
- корпус «глазами» (50–200k) укладывается в минуты, не часы. Прод-железо может считать иначе — порядок тот же.

Замер — только получение вектора; чтение PGN и запись в базу добавляют небольшие накладные.

## 4. Вытекающие задачи

- **backend:** таблица `position_embedding` + pgvector-индекс; пакетный конвейер эмбеддинга корпуса (на базе PoC-инструмента); сервис/утилита кодировщика запроса; маршрут `positions/similar`.
- **devops:** включить расширение **pgvector** в Postgres (прод/дев).

## 5. Риски

- **pgvector отсутствует** — требует включения расширения (devops), до этого индекс не построить.
- **Рассогласование стадий** (перспектива/история при построении ≠ при запросе) → мусорные соседи. Закрывается §2.5.
- **Размер онлайн-прохода:** один прогон сети на запрос — по замеру дёшев, но зависит от того, где живёт кодировщик; для «глазами» приемлемо.
- **Качество на глаз субъективно** — фиксируем это как проверку гипотезы, не как метрику; при переходе к продукту нужны числовые критерии (вне scope этого ADR).

## 6. Границы

ADR описывает **внутреннюю проверку**. Вне scope: публичный UI, полное индексирование прод-архива, вывод целевых векторов (φ*), генерация планов, поиск доминанты — открываются отдельными ADR по результатам «проверки глазами».
